# ADR-042: 요청 속도는 고른 간격을 지키고, 워크스페이스 단위 한도는 따로 다룬다

> 상태: 승인
> 결정일: 2026-10-28

## 맥락

- request-limits 문서(2026 개정)는 한도를 **60초 창**으로 적는다 — 연결마다 분당 180회(Business · Enterprise 600회),
  창 안의 몰아치기는 허용한다. data source 조회는 따로 초당 약 3회다
- 같은 워크스페이스의 연결들이 함께 쓰는 한도가 따로 있다. 429 의 `additional_data.rate_limit_reason` 이
  `public_api_space_request_rate_limit` 이고, 문서는 그 대기가 **1분을 넘을 수 있다**고 적는다
- 지금 클라이언트는 `Retry-After` 를 60초에서 자른다. 공용 한도의 대기가 그보다 길면 서버가 말한 시각보다 먼저 두드려
  429 를 다시 맞고 재시도 횟수만 버린다
- workspace-block-limits 문서(2026-09-01): 멤버가 둘 이상인 Free 워크스페이스는 블록 한도를 넘기면 사흘 유예 뒤 블록을
  만드는 요청이 403 `restricted_resource` + `additional_data.block_limit` 로 거절된다. 지금은 노트마다 같은 거절을
  받으러 가고, 실패 사유는 영어 원문만 남는다

## 선택지

| 안                                                                              | 좋은 점                                          | 나쁜 점                                                                                                            |
| ------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| A. 창(60초 · 180회) 계산기로 바꿔 몰아치기를 허용                               | 작은 동기화가 빨라진다                           | 프로젝트 규칙(초당 3회 이하)을 바꾼다. data source 조회(초당 3회)는 따로 세야 한다. 빨라지는 것은 처음 몇 초뿐이다 |
| **B. 고른 간격(350ms · 동시 3)을 지키고, 워크스페이스 단위 한도만 따로 다룬다** | 두 한도(분당 180 · 조회 초당 3) 모두 늘 안쪽이다 | 몰아치기를 쓰지 않는다                                                                                             |

## 결정

B.

1. **간격은 그대로** — `rateLimitIntervalMs` 350ms 는 초당 약 2.86회다. 분당 180회와 data source 조회 초당 3회
   **둘 다** 안쪽이므로 조회를 따로 세지 않는다
2. **공용 한도의 대기는 5분까지 지킨다** — `rate_limit_reason` 이 `public_api_space_request_rate_limit` 이면
   `Retry-After` 상한이 5분이다. 연결 하나의 한도는 예전처럼 60초. 대기마다 재시도 로그가 남고, 로그에 어느 한도인지 적는다
3. **블록 한도(403)는 사유를 지키고 할 일을 붙인다** — `additional_data.block_limit` 이 실린 403 만 블록 한도로 본다
   (문서가 메시지 글자로 가르지 말라고 한다). 실패 사유는 「Notion 에서 플랜을 올리면 풀린다」 를 앞에 붙이고 Notion 원문을
   그대로 싣는다
4. **막힌 동안 만들기 요청은 보내지 않는다** — 페이지 · DB 만들기와 블록 덧붙이기는 5분 동안 같은 거절을 바로 돌려준다.
   본문 교체 · 속성 · 읽기는 막지 않는다(블록을 늘리지 않는 쓰기는 서버가 판정한다). 5분이 지나면 다시 보내 본다 — 그 사이
   플랜을 올렸을 수 있다

## 트레이드오프

- 몰아치기를 쓰지 않아 작은 동기화(수십 요청)가 창 방식보다 몇 초 느리다
- 공용 한도에 걸리면 한 요청이 최대 5분 기다린다. 말없이 멈추지 않도록 대기마다 로그가 남는다
- 블록 한도에 막힌 뒤 5분 안에 플랜을 올려도, 그 5분 동안의 만들기는 실패로 남는다 — 다음 push 가 다시 보낸다

## 영향

- `notion/client.ts` — `isWorkspaceBlockLimit` · `NotionBlockLimitError` · `rateLimitReasonOf`, `withRateLimit` 의
  `createsBlocks`, `extractRetryAfter` 의 상한
- 프로젝트 규칙 「async-sema 로 3 req/s 제한」 은 그대로다
