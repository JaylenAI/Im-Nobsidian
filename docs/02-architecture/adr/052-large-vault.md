# ADR-052: 큰 볼트 — 요청 간격은 «시작 시각 예약» · 발견 스캔은 그대로

> 상태: 승인
> 결정일: 2026-10-31
> 「Notion API 한계를 빼고 모두 동기화」 계획의 P10

## 맥락

1,000 노트 볼트를 실제 Notion 에 처음 올리고 받는 시간을 쟀다(분당 180회 플랜). 세 가지가 나왔다.

1. **첫 push 가 429 를 거듭 맞았다** — `Retry-After` 가 40초까지 갔다. 요청 간격 게이트는 칸(`concurrency` 3)마다 «마지막 요청
   시각» 을 읽고 모자란 만큼 잔 뒤 나갔다. 세 칸이 같은 시각을 읽고 같이 자고 같이 나가, 350ms 간격이 실제로는 초당 8회 남짓이었다
   (시험: 아홉 요청이 80ms 안에 셋씩 몰려 나감)
2. **로컬 처리가 노트 수의 제곱으로 늘었다** — 메모리 Notion 으로 5,000 노트를 재 CPU 프로파일을 떴다. 상태 DB 가 질의마다 SQL 을
   다시 준비했고(3초), P9 의 대소문자 무시 링크 조회는 색인이 없고 두 조건을 OR 로 묶어 아직 없는 노트로 가는 링크마다 표를 다 훑었다
3. **push 뒤 첫 pull 이 바뀐 것 없이 10분** — 추적하는 페이지마다 안에 DB 가 있는지 묻는 발견 스캔(F21 의 안전망)이다

## 결정

1. 요청마다 **나갈 시각을 먼저 잡고** 기다린다(`nextRequestAt`). 잠든 사이 다른 칸이 같은 자리를 잡지 못한다. 깬 뒤 다른 칸이 429 를
   맞아 쿨다운이 걸렸으면 쿨다운 뒤로 다시 줄을 선다. 빠르기는 `rateLimitIntervalMs` 하나가 정하고, `concurrency` 는 느린 응답을
   기다리는 칸 수일 뿐이다
2. 상태 DB 는 SQL 글자마다 문장을 한 번만 준비한다. 위키링크 같음 조회는 따로 묻고 색인 둘(`COLLATE NOCASE`)을 더한다 — 스키마 6.
   같음 조회가 색인을 타는지는 SQLite 의 조회 계획으로 시험한다(`OR` · 콜레이션은 오류 없이 색인을 놓친다)
3. 발견 스캔은 **줄이지 않는다** — 문서에 비용을 적는다

## 이유

- 1: 고친 뒤 같은 1,000 노트 첫 push 가 429 없이 18분(분당 56 노트 — 노트당 요청 약 3회 × 분당 171회)에 끝났다. 고치기 전에는 칸
  수를 낮추라고 안내했는데, 그것이 빠르기를 정하는 값이 아니었다
- 2: 5,000 노트 로컬 처리가 15.7초 → 9초, 1,000 → 5,000 이 5배(비례). 맨 앞이 `%` 인 LIKE(별칭 · 경로 꼬리)는 색인으로 못 고친다 —
  어디에도 없는 링크만 그 둘에서 훑고, 5,000 노트에서 1초 남짓이다
- 3: API 로 페이지 안에 인라인 DB 를 만들면 그 페이지의 수정 시각이 바뀐다(실측 — 문단을 더할 때와 같다). 그러면 수정 시각으로
  거를 수 있을 듯하지만, Notion 화면에서 더하거나 다른 DB 를 페이지 안으로 옮기는 경우는 재지 못했다. 블록을 지울 때 수정 시각이
  바뀌지 않는 것은 이미 쟀다. 스캔은 처음 한 번(DB 가 없는 볼트)과 `--force` 때만 돈다 — 한 번의 10분이 놓친 DB 보다 싸다

## 트레이드오프

- 기본 간격은 모든 플랜에 맞춘 값이다. Business · Enterprise(분당 600회)는 `rateLimitIntervalMs` 를 낮춰야 빨라진다 — 그 플랜에서
  재지 않았다
- 첫 pull 의 발견 스캔 동안 출력이 없다 — TROUBLESHOOTING 에 적었다
