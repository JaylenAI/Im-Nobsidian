# ADR-010: 증분 pull 기준 시각 — 시작 시각에 적고, 받지 못한 변경 앞으로 묶는다

> 상태: 승인
> 결정일: 2026-09-27

## 맥락

증분 pull 은 `last_pull_at − 15분(안전창, F20)` 이후에 고친 페이지만 Notion search 로 받는다.
그러므로 `last_pull_at` 은 «이보다 앞의 원격 변경은 모두 볼트에 받았다» 는 약속이어야 한다.
v0.3.x 는 pull 이 **끝난** 시각을 적었고, 그 약속이 네 경우에 깨졌다. 네 경우 모두 오류 없이
원격에서 그 페이지를 다시 고치기 전까지 빠졌다(`pull --force` 로만 복구).

| 경우                                      | 왜 빠지나                                                    |
| ----------------------------------------- | ------------------------------------------------------------ |
| 재시도까지 실패한 새 페이지 · 수정        | 다음 조회 창이 그 수정 시각을 이미 지났다                    |
| 중단(취소)된 pull 이 건너뛴 항목          | 같은 이유 — 플러그인의 「동기화 취소」 가 이 경로다          |
| 경로를 좁힌 pull(`--path`)의 범위 밖 변경 | 범위 밖은 보지도 않았는데 기준 시각은 옮겼다                 |
| 조회 뒤 · pull 도중의 원격 편집 (긴 pull) | pull 이 안전창(15분)보다 길면 끝난 시각 − 15분이 편집보다 뒤 |

`status` 는 push 도 올리는 `last_sync_at` 을 기준으로 조회해, pull 이 받을 변경을 「없음」 으로
보고할 수 있었다. pull 도 `last_pull_at` 이 없으면 `last_sync_at` 으로 대신해, push 만 한 볼트의
첫 pull 은 그 전에 원격에만 있던 페이지를 받지 못했다.

## 결정

1. **pull 을 시작한 시각을 적는다** (`sync/pull-watermark.ts` `nextPullWatermark`).
2. **받지 못한 변경이 있으면 그중 가장 이른 수정 시각으로 묶는다.** 「받지 못한」 = 감지했지만
   적용을 마치지 못한 것(재시도까지 실패 · 중단으로 건너뜀). 충돌로 기록된 것은 처리한 것으로
   본다(충돌 해결 흐름이 따로 있다). 삭제는 묶지 않는다 — 증분은 휴지통을 보지 못해 삭제는
   전체 대조로만 잡힌다.
3. **경로를 좁힌 pull 은 기준 시각을 옮기지 않는다.**
4. **기준 시각은 `last_pull_at` 뿐이다.** 없으면 전체 대조한다. `last_sync_at` 은 표시용
   「마지막 동기화」 로만 남는다.
5. **pull 과 status 는 같은 규칙을 읽는다** (`incrementalWatermark`) — DB 모드 · deleteSync ·
   추적 0건 · `--force` 면 전체 대조.
6. 안전창(15분)과 조회 시작 시각 계산도 같은 모듈이 한 벌만 갖는다 (`incrementalSearchSince`).

## 이유

- **스스로 낫는다.** 받지 못한 변경은 다음 조회 창에 다시 들어와 다시 시도되고, 실패하면
  매번 `failed[]` 로 보고된다. 따로 적어 둘 목록(대기 id 표)이 없어 그 목록이 틀어질 일도 없다.
- **시작 시각은 보수적이다.** 조회는 시작 뒤에 하므로 시작 시각 앞의 편집은 이번 조회가 봤고,
  뒤의 편집은 다음 조회가 본다.
- 경로를 좁힌 pull 을 옮기지 않으면 곧 들어올 변경 패널의 「이 항목만 pull」 이 나머지 원격
  변경을 목록에서 지우지 않는다.

## 트레이드오프

- **실패가 계속되면 조회 창이 그 시각에 머문다.** 그동안 워크스페이스에서 고친 페이지가 search
  결과에 계속 들어와 조회가 길어진다(search 한 요청에 100건). 그 대신 실패는 매번 보고된다.
  검토한 대안 — 받지 못한 페이지 id 를 따로 적어 두고 다음에 하나씩 다시 읽기 — 는 비용이
  일정하지만, 다시 읽다 일시 오류가 나면 그 id 를 또 잃지 않게 따로 챙겨야 하고 경로를 좁힌
  pull 이 범위 밖 수백 건을 목록에 쌓는다. 먼저 단순한 쪽을 택하고, 조회가 길어지는 것이 실측되면
  바꾼다.
- 증분 결과가 검색 색인 지연(안전창 15분)보다 늦게 잡히는 경우는 여전히 남는다 — 주기적 전체
  대조(Phase A `feature/fast-change-detection`)가 잡는다.
- `last_pull_at` 이 없는 볼트(push 만 한 볼트)는 첫 pull 이 전체 대조라 느리다(1회).
