# ADR-018: 원격 삭제는 목록에 없다는 것만으로 가르지 않고, 원격에 물어 확인한다

> 상태: 승인
> 결정일: 2026-09-28

## 맥락

deleteSync 가 켜지면 pull 은 전체 대조를 한다 — 루트 아래 페이지를 순회해 추적 레코드와 견주고, 목록에 없는
추적 레코드를 «원격에서 사라진 것» 으로 보고 볼트에서 지웠다. 플러그인은 deleteSync 를 늘 켠다.

목록은 완전하지 않다.

| 무엇이 빠지나              | 왜                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| **DB 행 전부**             | 순회는 `child_page` 만 따라간다. 행은 자식 페이지가 아니다 — DB 조회로만 보인다            |
| 깊은 가지 · 갓 만든 페이지 | 순회는 마감(90초)에 잘리고, 그때 합치는 search 는 색인이 늦다(R12-A 가 줄였지만 0 이 아님) |
| 다른 DB 로 옮긴 행         | 그 DB 의 조회에 나온다                                                                     |

첫째가 S-12 다. 행은 매 pull 마다 «사라진 페이지» 가 돼 파일이 지워졌고, 이어지는 DB pull 이 같은 행을 새로
만들었다. 그 사이에 올리지 않은 로컬 행 편집이 사라졌다.

실측(수정 전 빌드, N-05 프로브 컨테이너, 플러그인과 같은 설정 — 페이지 모드 · 자동 발견 DB · deleteSync):

| 회차                    | 결과                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| 바뀐 것이 없는 sync     | `pull.deleted 7 · pull.created 7` — 행 7건을 지우고 다시 만듦. 다음 sync 도 같다 |
| 로컬에서 행 하나를 고침 | 로컬 편집이 사라지고 `push.updated 0` — Notion 에도 가지 않았다                  |
| 행 하나를 휴지통에      | `deleted 7 · created 6` — 사라진 1건이 7건의 삭제에 묻힌다                       |

지정 볼트(발견 DB 166개 · 행 925건)에 deleteSync 를 켜면 매 pull 이 행 925건을 지웠다 다시 받는 셈이다(계산 —
이 볼트는 deleteSync 를 끄고 쓴다).

## 결정

### 1. 행은 그 DB 의 조회로 가른다

- 전체 대조는 **조회하는 DB** 의 행(`db-row`)을 건너뛴다. 조회하는 DB = 설정한 DB + (페이지 모드면) 자동 발견한
  DB − 접근 불가로 뺀 DB. 이번 pull 이 조회하는 목록과 같다.
- DB pull(`DatabaseSyncer.pullDatabase`)이 조회를 마친 뒤, 조회에 없던 **이 DB 의** 추적 행을 가른다.
- 접근 불가로 뺀 DB 의 행은 조회하지 않으므로 전체 대조가 페이지처럼 가른다(아래 2 · 3).

### 2. 목록 · 조회에 없으면 원격에 묻는다 (`remotePresence`)

`pages.retrieve` 한 번.

| 답                           | 판정                                            |
| ---------------------------- | ----------------------------------------------- |
| 휴지통 · 보관 · 없음(404)    | 사라졌다 → 지운다                               |
| 그 밖의 오류(429 · 5xx · 망) | 모른다 → 이번에는 둔다. 다음 대조가 다시 묻는다 |
| 살아 있다                    | 아래 3                                          |

읽지 못한 것을 사라진 것으로 보지 않는다.

### 3. 살아 있으면

- **페이지** — 부모가 동기화 범위면 목록이 빠뜨린 것이다. 둔다. 범위 = 루트 · 목록에 있던 페이지 · 이렇게 살아
  있다고 확인된 페이지(부모가 함께 빠졌을 수 있다 — 범위가 더 늘지 않을 때까지 되풀이한다). 범위 밖(다른 곳 ·
  워크스페이스 맨 위)으로 옮겨졌으면 지운다 — 예전과 같다. 부모를 알 수 없으면(블록 부모를 따라가다 실패) 둔다.
- **행** — 둔다. 다른 DB 로 옮겨졌을 수 있고, 그 DB 를 조회하면 그 pull 이 옮겨 받는다.

### 4. 조회 필터(`pullFilter`)가 있는 DB 는 행의 삭제를 가르지 않는다

조회에 없는 행이 필터 밖인지 지워진 것인지 모른다. 필터 밖으로 나간 행을 pull 마다 물으면 요청이 끝없이 는다.

### 5. `pull --path` 는 범위 안의 행만 지운다 — 페이지와 같다

### 6. 지우는 동작은 하나다 (`applyRemoteDeletion`)

파일(deleteSync 일 때) · 레코드 · 위키링크를 지운다. 페이지(`pullDelete`)와 행이 같이 쓴다 — 로컬 편집을 지키는
규칙을 더할 자리가 한 곳이다.

## 비용

- **평소 0.** 목록에 없는 추적 항목이 없으면 묻지 않는다. 지워진 것 하나마다 `pages.retrieve` 1회.
- 행 판정은 DB 마다 상태 DB 를 한 번 훑는다(`getAll`) — 레코드 1,271건에서 호출당 4.02 ms(실측, 지정 볼트
  상태 DB 사본 · better-sqlite3). 발견 DB 166개면 pull 당 약 0.7초. 플러그인(sql.js)은 재지 않았다.

## 결과 · 한계

- `status` 와 `pull --dry-run` 도 같은 감지를 거친다 — 목록이 빠뜨린 페이지 · 조회하는 DB 의 행을 원격 삭제로
  세지 않는다. 행의 삭제는 DB pull 에서 가르므로 `pull --dry-run` 에는 나오지 않는다 — dry-run 이 DB 경로를
  타지 않는 한계(F-a)와 같다.
- 필터 DB 에서 휴지통으로 간 행은 볼트에 남는다. 필터는 설정 DB 에만 있다 — 플러그인은 설정 DB 를 쓰지 않는다.
- 조회하지 않는 DB 로 옮긴 행은 추적이 남고, pull 마다 한 번씩 묻는다.
- 원격에서 지운 노트에 올리지 않은 로컬 편집이 있어도 지운다. 이 ADR 밖이다 — 지우는 동작이 하나로 모였으니
  그 자리에서 막는다(다음 브랜치).
