### R9 — "268페이지 pull 이 멈춘다"의 근본 원인

증상은 진행 로그가 특정 지점(102/268, 158/268 — **비결정적**)에서 멈춘 채 프로세스만
살아 있는 것이었다. CPU 0, 소켓 0, stdout 백프레셔 없음.

`process.getActiveResourcesInfo()` 가 결정적이었다 — `_getActiveHandles()` 는 타이머를
보고하지 않아 "대기 타이머 없음"이라는 **오독**을 만들었지만, 실제로는 `advanced.concurrency`
와 정확히 같은 개수의 `Timeout` 이 살아 있었다. 즉 워커 전원이 타이머 위에서 자고 있었다.

원인은 `NotionClient.withRateLimit` 이 **rate limit 슬롯을 쥔 채** 재시도 전체를 돌린 것.
재시도 1건이 슬롯 하나를 최대 5분(60초 × 5회) 점유하므로, 불운한 요청 3건이면 클라이언트
전체가 멈춘다. 게다가 재시도는 로그를 한 줄도 남기지 않아 죽은 프로세스와 구분되지 않았다.

세 겹으로 봉합:

1. **백오프는 슬롯을 놓은 뒤에 기다린다** — 한 요청이 남을 막지 못한다.
2. **429 는 `cooldownUntil` 전역 게이트로 함께 쉰다** — 슬롯 점유 대신 워크스페이스
   신호로 다루어 재시도 폭풍을 막는다.
3. **모든 재시도를 경고로 남긴다** — `Notion API 재시도 1/5 — 3750ms 대기 (status 429 · ...)`.

R9a·R9b 는 같은 증상의 **다른 경로**를 함께 막는다 — 상한 없는 첨부 다운로드(무한 대기)와
합성 경로 전체(페이지 1건 처리)의 시간 상한. 세 상한의 관계는
`docs/05-guides/TROUBLESHOOTING.md` 에 표로 공시했다.

R9d 는 R9c 가 켜 준 로그 덕분에 드러났다. 라이브 429 폭풍에서 기록된 대기값 11개가 전부
지수 백오프 격자 위에 떨어져 있었고 — 즉 `Retry-After` 경로를 한 번도 타지 않았다 —
추적해 보니 SDK 가 주는 `Headers` 인스턴스를 인덱스로 읽고 있어 `extractRetryAfter` 가
통째로 죽은 코드였다. 자세한 경위는 `journal/2026-07-27.md §R9d`.

R9e·R9f 는 R9b 의 **적용 범위 공백**을 메운다. R9b 는 "항목 1건 상한"을 도입하면서
오케스트레이터의 페이지 루프 4곳에만 걸었는데, 지정 볼트 887개 파일 중 629개가 DB 행
이라 정작 **보호받지 못하는 쪽이 다수**였다. 첨부 업로드도 같았다. `withDeadline` 호출
지점을 전수로 훑어 사각지대를 확인했고, 지금은 사용자가 세는 단위(페이지·행·첨부) 1건
전부에 상한이 걸린다. DB 단위·전체 단위에는 일부러 걸지 않는다 — 500행 DB 가 오래
걸리는 것은 정지가 아니라 정상이기 때문이다.

### R10 — 페이지 링크가 끊긴 채 남던 네 갈래

`[[notion:<id>]]` 는 최종형이 아니라 **중간형**이다 — pull 1차 변환이 page mention 과 라벨
달린 페이지 링크를 이 형태로 환원해 두면 id → 볼트 경로 역조회가 `[[제목]]` 을 만든다.
그 역조회가 **변환 시점**과 **pull 마감 후처리** 두 곳에서 돌고, 후처리가 필요한 이유는
정방향 참조다(A→B 인데 B 가 같은 pull 의 나중에 만들어지는 경우).

- **R10-A**: 후처리가 공용 함수 대신 자기 정규식(`/\[\[notion:([a-f0-9-]+)\]\]/`)을 들고
  있어 **별칭 형태를 아예 매치하지 못했다.** 지정 볼트에서 별칭 없는 형태는 13건 전부
  해소, 별칭 형태는 대상이 볼트에 실재하는 2건이 미해소로 갈렸다. 해소 지점을
  `converter/notion-id-links.ts` 하나로 합치고, 압축형(32 hex)·하이픈형(36자) 두 id 표기를
  모두 받게 하고, 이 표기의 `[[X|X]]` 자기별칭을 접게 했다.
- **R10-B**: 끝내 해소되지 않은 링크(볼트 밖·미접근 페이지, **25건/16파일**)를 그대로
  남기면 옵시디언이 `notion:26d2…` 라는 이름의 노트를 가리키는 끊긴 링크로 그리고, 클릭
  시 그 이름의 빈 노트를 만들자고 해 볼트를 오염시킨다. 같은 breadcrumb 한 줄의 url 기반
  링크는 이미 동작하고 있었으므로, 해소를 **전부 시도한 뒤에만**
  `[라벨](https://www.notion.so/<id>)` 로 격하한다. 왕복은 1차 변환의
  `NOTION_LABELED_PAGE_LINK_RE` 가 `[[notion:<id>|라벨]]` 로 환원해 닫힌다.
- **R10-C**: A·B 를 넣고 다시 pull 해 실측하니 `[[notion:…]]` 25→0, URL 링크 0→25 로
  둘 다 맞았는데 **`[[X|X]]` 45건/12파일이 그대로였다.** 라이브 프로브로 원본 블록을 뜯어
  보니 그 breadcrumb 은 page mention 이 아니라 **라벨 달린 상대 링크**(`[ETC](/p/<id>)`)라,
  `[[notion:<id>]]` 중간형을 아예 거치지 않고 후처리 안의 **다른 정규식**이 처리하고
  있었다 — R10-A 가 고친 바로 옆줄이고, 접기가 없었다. 세어 보니 이 접기 규칙은 네 곳에
  복제돼 있었다. 그래서 위키링크 출구를 `utils/wikilink-title.ts` 의
  `formatWikilink(target, label?)` **하나로** 합치고 네 곳이 전부 이를 부르게 했다.
- **R10-D**: C 를 넣고 또 받아 재니 세 수치는 다 맞았는데 **네 번째 수치**가 걸렸다 —
  미해소 `/p/<id>` 상대링크 **89건/10파일**. 상태 DB 대조로 대상 11개가 전부 볼트 밖임을,
  코드펜스 0건으로 예시 텍스트가 아님을 확인했다. R10-B 가 고친 것과 같은 상황인데 표기만
  다르다: `/p/<id>` 는 Notion 앱 안에서만 뜻이 있어 옵시디언은 `p/<id>` 라는 없는 파일을
  가리키는 끊긴 링크로 그린다. R10-B 는 비대칭의 **절반**만 없앴던 것이다. 이번엔 사례가
  아니라 모듈 경계를 고쳐, `notion-id-links.ts` 가 표기별 해소·격하를 **한 쌍씩** 갖게 하고
  오케스트레이터에는 규칙을 한 줄도 남기지 않았다. 89건 중 80건이 각주라 `#<blockId>`
  앵커는 살린다(버리면 각주 80개가 전부 페이지 최상단으로 떨어진다).

R9a·R9e·R9f 와 같은 결함군(같은 계약이 여러 경로에 있고 한쪽만 갱신 누락)이고, 이 패스들은
2026-06-02 Phase 1 의 **M4** 로 이미 한 번 어긋난 전력이 있다. 그래서 이번엔 사례가 아니라
성질을 두 겹으로, **표기별로** 잠갔다 — 후처리 결과가 항상 `격하(해소(x))` 합성과 바이트
단위로 같아야 하고, 같은 대상·같은 라벨이면 url 표기와 id 표기가 볼트 안(→ 같은 위키링크)
에서도 볼트 밖(→ 같은 URL)에서도 **같은 바이트**를 내야 한다.

라이브 clean-slate E2E `full` — R10-C 반영본과 R10-D 반영본 **둘 다** 전 게이트 통과:
`pull 1193 · analyze CLEAN · repull 멱등(0) · pushdry 멱등(0) · sync 멱등(0) · roundtrip 무손실`.
`repull 멱등(0)` 이 격하의 고정점을 실증한다 — 격하된 링크를 가진 파일이 두 번째 pull 에서
한 건도 재기록되지 않았다(앵커 달린 80건 포함).

볼트 실측으로 89건이 **사라진 게 아니라 동작하는 링크가 됐음**을 확인했다: 미해소 상대링크
89→0, 절대 URL 25→**114건**(= 25 + 89, 그중 앵커 보존 80건/5파일). `[[notion:]]` 0건 ·
`[[X|X]]` 0건 유지.

### R11 — 침묵 유실을 볼 수 있게 만들기

R10 머지 후 볼트 파일 수 기준선(**1193** vs 이전 기록 **887**)을 추적하다 시작됐다. 차이는
개선이 아니라 **과거의 유실**이었다 — 볼트의 db-row 925건이 전부 2026-07-17 이전 생성분이고,
그날의 pull 은 DB 행 **296개**를 놓친 채 `audit-vault 결함 0 · 해시 불일치 0 · repull churn 0`
을 전부 통과했다. 질문은 "무엇이 틀렸나"가 아니라 **"왜 아무 게이트도 못 봤나"** 였다.

| 게이트              | 보는 성질                    | 미발견을 잡는가                |
| ------------------- | ---------------------------- | ------------------------------ |
| `analyze` 무결성    | 볼트 안 구조(충돌·중복·고아) | ✗ — 원격을 안 본다             |
| `repull` churn 0    | 멱등성                       | ✗ — 매번 같이 놓치면 churn 0   |
| `pushdry` churn 0   | 멱등성                       | ✗ — 로컬에 없으니 밀 것도 없다 |
| 재-pull 바이트 동일 | 멱등성                       | ✗ — 동일하게 빠진다            |
| 해시 일치           | 존재하는 파일의 충실도       | ✗ — 없는 파일은 대조 대상 밖   |
| **`verify` 완결성** | **원격 집합 = 볼트 집합**    | **✓ (R11-B 신설)**             |

전부 **멱등성**이거나 **볼트 내부 성질**이다. 체계적 미발견은 정의상 멱등하다 — 매번 같은
행을 똑같이 놓치면 두 번째 실행 결과가 첫 번째와 같다. **재현 가능한 유실은 멱등성 게이트에
보이지 않는다.**

- **R11-A** — `detectRemoteChanges()` 의 DB 갈래만 `queryDatabase()` 인라인 페이지네이션(1차
  data source)으로 열거했다. 같은 계약을 `pullDatabase` 는 `queryAllDatabasePages()`(전 소스)로
  지키고 있어 한쪽만 어긴 비대칭 — R9a·R9e·R9f·R10-A·R10-C·R10-D 와 같은 결함류의 일곱 번째다.
  `deleteSync: true` 면 미발견에 그치지 않고 **한 경로가 만든 파일을 다른 경로가 지우는 진동**이
  된다. 인라인 사본을 지우고 SSOT 하나만 부르게 봉합.
- **R11-B** — `audit/completeness.ts` 가 database 별로 원격 행 id **집합**과 볼트 db-row id
  **집합**을 대조한다. 카운트가 아니라 집합이라 "미발견 1 + 잔재 1" 이 상쇄되지 않고, 대조
  대상은 볼트가 아니라 오케스트레이터가 조립해(설정 + `discovered_dbs` 캐시 + DB 모드 루트)
  **통째로 미발견된 DB** 도 보이며, 조회 실패는 통과로 접지 않는다. 표면 셋:
  `orchestrator.verifyCompleteness()` · `nobsi verify [--json]` · E2E 기본 베이스라인 `verify`.
- **R11-C** — CLI 가 `setTimeout(() => process.exit(0), 100)` 으로 강제 종료하며 각 명령이 세운
  `process.exitCode = 1` 을 **전부 덮어썼다**. **모든 CLI 실패가 종료코드 0 으로 나갔고**, 셸도
  CI 도 감지할 수 없었다(node 프로브로 실측). `utils/exit.ts` 로 계약을 분리.

셋은 사슬이다 — R11-C 가 살아 있으면 R11-B 의 E2E 게이트는 **작동하지 않는다**(verify 가 아무리
실패해도 0 으로 끝나 하니스가 통과로 읽는다). 새 게이트를 붙이면서 그 게이트를 무력화하는
결함을 같이 발견한 셈이다.

### R12 — 페이지 목록을 정하던 스톱워치

R11 일지가 남긴 숙제. `verify` 는 DB 행만 봤는데 정작 회차별 변동이 큰 쪽은 페이지였다
(258 → 268 → **342**, 같은 워크스페이스에서 +74·약 28%). 원인은 무작위가 아니었다 —
R11 실행 로그 한 건 안에 두 경로가 **모두** 찍혀 있다.

```
초기 PULL     서브트리가 큼(93701ms) → search 폴백으로 전환   →  268
REPULL(522.9s) 폴백 로그 없음 = BFS 로 완주                    →  churn 0
```

**어느 경로가 도는지를 90초 스톱워치가 정하고, 두 경로의 결과 집합은 같지 않다.**
그런데 게이트는 침묵한다 — `churn = created + updated` 라서 두 번째 열거가 **더 작으면**
만들 것도 고칠 것도 없다. 즉 **일치와 축소가 게이트 눈에는 똑같다**. R11 에서 배운 사각지대가
페이지 쪽에 그대로 남아 있었던 것이다.

- **R12-A** — 폴백이 **부분 결과를 버렸다**. `DiscoveryTooLargeError` 가 순회 부분 결과를
  payload 로 싣고 오케스트레이터가 **순회 ∪ search** 합집합을 쓰게 봉합. 미발견으로 끝나지도
  않는다 — `orchestrator.ts:1930` 은 이번 열거에 없는 추적 페이지를 전부 `deleted` 로 만들어,
  `deleteSync: true` 면 **그날의 API 지연에 따라** 실제 노트가 지워지고 다음 pull 이 되살리는
  진동이 된다(R11-A 의 구조가 페이지 쪽에서 재현). 합집합은 `_childParentIds` 가 부모 관계를
  이 목록에서 얻으므로 폴더노트 분류에도 이득이고, BFS 가 한 일은 지금도 이미 수행된 뒤
  버려지던 것이라 **추가 비용이 0** 이다.
- **R12-B** — search 폴백의 `resolveBlockOwner` 가 부모 조회 실패를 `null` 로 조용히 접었다.
  그 블록에 중첩된 페이지는 통째로 빠지는데 로그 한 줄 없었다 — 같은 파일의 직접 순회는
  경고를 남기고 있어, 또 한 번 **한쪽 경로만 침묵**하는 비대칭.
- **R12-C** — `verify` 가 `{ databases, pages, complete }` 로 페이지까지 대조한다. 페이지 축은
  **일부러 pull 과 다른 열거**(workspace search)를 쓴다 — 같은 경로로 두 번 세면 그 경로의
  편향을 둘 다 물려받는다(DB 축과 정반대 규칙인 이유는 행의 열거 방법이 하나뿐이기 때문).
  볼트에만 있는 페이지는 **실패로 보지 않는다**(미push 로컬 노트·root 자신·색인 지연이 전부
  정상) — 거짓 적색을 내는 게이트는 곧 무시당한다.

R12-A 는 여덟 번째, R12-B 는 아홉 번째 "같은 계약이 두 경로에 있고 한쪽만 안 지킨다" 사례다.

**라이브 clean-slate E2E 전량 통과(EXIT=0)** — `verify 완결(행 925=925 · 쪽 343/343)` ·
repull/pushdry/sync 멱등(0) · roundtrip 무손실. 볼트 md 1268 · `.base` 166 · 첨부 1331 ·
폴더 301 / 레코드 1268(file 271 · folder-note 72 · db-row 925).
`file 271 + folder-note 72 = 343` 이 `Vault pages: 343` 과 일치해, 게이트가 세는 집합이
실제 볼트 레코드와 같은 것을 본다는 것까지 확인됐다.

이 실행에서 R12-A 는 **실제로 발동했다**(`예산 96490ms 초과 → 순회 80 ∪ search 343 →
343건`). 다만 순회 80 이 search 343 의 부분집합이라 **합집합이 보탠 건 0 이다** — 오늘의
초록은 "74건을 되찾았다"가 아니라 "폴백이 도는 실행에서도 두 경로가 어긋나지 않았다"는
관측이다. R12-A 는 어긋나는 날의 하한을 고정하고, 어긋나는지 보는 눈이 R12-C 다.

### P8 — 게이트가 없으면 결함은 "통과"한다

기존 게이트가 못 잡는 이유는 단순하다. `repull churn 0`·`pushdry churn 0`·재-pull 바이트
동일은 **볼트 내부 성질**이고, 왕복 무손실은 **pull 과 push 의 상호 일관성**이다. 볼트에
쓰인 결과가 Obsidian 에서 어떻게 **보이는가**는 어느 쪽도 보지 않는다.

`tests/render/vault-render.gate.test.ts` 는 NFM 원본을 orchestrator 와 같은 순서로
(`notionEnhancedToObsidian` → `BlockSpacer`) 통과시킨 뒤 ① 렌더 결함 린트 ② 구조 드리프트
③ 연속 5행 이상 본문 삼킴 ④ 산문 보존율 99% ⑤ **칼럼 비율 값·순서**(P10) ⑥ 왕복 안정성을
본다. 회귀가 나면 **어느 노트의 몇 번째 줄**인지까지 실패 메시지에 찍힌다.

### P10 — 열 구조는 살아 있고 폭만 무너지는 손실

NFM 은 칼럼을 `<column ratio="62.5">` 로 내보낸다. 실코퍼스 120노트에서 칼럼 203개 중
**181개가 비율을 갖고, 그중 100개가 비균등**이다. pull 이 속성을 버리면 볼트에는 열
**개수**만 남고, push 가 `<column>` 으로 재조립하며 사용자가 잡아 둔 폭이 **매번 균등
분할로 되돌아간다** — R8 의 D-EMPTY-COLUMN 과 같은 종류의 레이아웃 손실이다(그때는 칼럼
수, 이번엔 칼럼 폭).

구분 마커가 비율을 싣고(`%%im-nobsidian:column:ratio=62.5%%`) push 가 정준형 속성으로
되돌린다. 설계 결정 셋:

- **비율은 십진수만 통과**시킨다 — 검증 없이 속성 값을 마커 페이로드로 옮기면 `%%` 나
  개행이 든 값 하나가 마커를 두 동강 내 **그 자리의 칼럼 경계 전체**가 무너진다.
- 마커 패턴은 `columnSepSource("capture"|"ignore")` **하나를 pull·push·legacy 세 경로가
  공유**한다. 한 곳만 갱신되는 순간 그 경로가 경계를 놓쳐 **여러 칼럼이 하나로 접힌다** —
  실제로 legacy(`block-converter`) 의 split 이 리터럴 비교라 그 상태가 될 뻔했다.
- legacy 경로는 비율을 **재현하지 않는다**. 블록 API `column.width_ratio` 의 단위가 NFM
  백분율과 달라, 확인되지 않은 값을 밀어 넣으면 폭이 **잘못 덮어써진다**. 비워 두면 Notion
  이 기존 폭을 유지한다.

**지표 생존 확인** — 새 게이트 지표가 초록인 것만으로는 뜻이 없다(죽은 지표의 0 과 깨끗한
코퍼스의 0 은 출력이 같다). `packages/core/src` 만 되돌려 재실행해 **합성 2노트 · 실코퍼스
34노트에서 실패**하는 것을 먼저 확인했다.

**검증**: 신규 유닛 7/7 · 렌더 게이트 7/7(합성 8노트 · 실코퍼스 120노트 양쪽) ·
`pnpm -r typecheck` 클린 · core **1446** · cli 51 · plugin 149.

### P11 — 지표가 초록인데 화면은 깨져 있던 결함

사용자가 볼트에서 직접 잡아낸 결함이다. `Blog` 노트가 `>` 와 백틱이 날것으로 보이는
상태였는데 **그 노트는 게이트 코퍼스 120개 안에 있었고 게이트는 7/7 초록이었다.**

원인은 NFM 의 **비대칭 들여쓰기**다. NFM 은 경계 펜스와 `<table>` 태그만 탭으로
들여쓰고 내부 줄은 열 0 에 둔다. 경계를 열 0 으로 평탄화해야 `> ` 를 붙여도 CommonMark
펜스 규칙(들여쓰기 ≤3칸)을 지키는데, 그 순간 내용 안의 열 0 백틱과 **구분할 근거가
사라진다**. 프롬프트 템플릿·마크다운 튜토리얼처럼 코드 안에 백틱이 든 문서는 흔하고,
펜스가 순서대로 짝지어지며 경계가 한 칸씩 밀린다 — 실측 `Blog` 노트에서 코드블록
5개 → **37개**, 본문 **8,200행**이 코드블록 안에 갇혔다.

기존 지표가 전부 통과한 이유가 핵심이다. 삼켜진 본문은 **사라지지 않는다.** 코드블록
안에 그대로 남아 산문 보존율·본문 삼킴·글자 수가 모두 맞는다. 경계 자체를 보는 지표가
없었을 뿐이다.

- **짝짓기**(`findFenceClose`) — 들여쓰기까지 같은 닫는 펜스를 우선한다. 다만 NFM 이
  닫는 줄의 들여쓰기를 흘리는 경우가 실제로 있어(여는 `\t\t`, 닫는 열 0) 없으면 첫
  느슨한 줄로 물러난다. 이 물러섬이 없으면 멀쩡한 블록이 파일 끝까지 열린 것으로 잡힌다.
- **폭 확장**(`widenAmbiguousFences`) — 경계 펜스를 내용의 **어떤 펜스보다 한 틱 길게**
  내보낸다. 평탄화 뒤에도 "N개는 N개 이상으로만 닫힌다"는 CommonMark 규칙이 경계를
  지켜 준다. 내용에 백틱이 없으면 확장하지 않는다.
- **컨테이너 단위 구간**(`containerBlockEnds`) — 토글 헤딩 자식 구간을 줄 단위로
  끊으면 닫는 펜스만 밖으로 밀려나고 끝 마커가 코드 **안으로**(`pnpm build` 와 ` ``` `

### 하니스가 본문을 읽게 만들었다 (렌더 감사 core 이관)

2차 E2E 가 "무결성 CLEAN" 으로 P11 을 통과시킨 이유는 단순하다 — `analyze.mjs` 는 파일

갈라진다). `analyze.mjs` 가 이를 import 해 볼트 전량을 린트하고 결함이 있으면 exit 1.

솔직히 적어 둔다 — **이 배선이 있었어도 P11 은 못 잡았다.** ①–⑧ 은 파일 하나로 판정

**후** 마크다운이다). 잡히는 것은 P1–P7 계열이고, 그건 그것대로 2차 E2E 가 놓친 것들이다.

## R13 — 게이트를 넓히자마자 나온 결함 (dev 머지 완료)

3차 E2E 직후 볼트를 세어 보니 **FS 1,267 vs DB 1,268** 이었다. `roundtrip` 단계가 프로브
폴더를 `rm -rf` 하고 다시 pull 했을 때 **페이지 28개는 `✓ 28 restored` 로 돌아왔는데
db-row 1개만 돌아오지 않았다.**

원인은 이 프로젝트의 상습 결함군 — **같은 계약이 두 경로에 있고 한 경로만 그것을 안
지킨다**(R9a·R9e·R10-D·R11-A 와 동형). `pullDatabase` 의 행 루프는 원격이 안 바뀌었으면
로컬 파일이 있는지 **묻지도 않고** 건너뛴다. 복원 판정 코드는 `pullDatabasePage` 안에
멀쩡히 있지만 도달하지 못한다. 그런데 오케스트레이터의 페이지 복원 경로
(`detectMissingLocalFiles`)는 db-row 를 제외하면서 "행은 database-syncer 가 같은 판정을
이미 거치므로"라고 적어 두었다 — **양쪽 다 상대가 한다고 믿어 아무도 안 했다.**

노출면은 다수 쪽이다: 지정 볼트 1,268 레코드 중 **925개(73%)가 db-row**.

| 게이트          | 왜 통과했나                                                 |
| --------------- | ----------------------------------------------------------- |
| `analyze`       | FS→DB(고아) 한 방향만 봤다 — DB→FS 축이 없었다              |
| `verify`        | **상태 DB 의 id 집합**끼리 맞춘다 — 레코드만 있으면 925=925 |
| `repull`/`sync` | 그 행을 건너뛰므로 애초에 churn 0                           |
| 렌더 린트       | 없는 파일은 읽을 것도 없다                                  |

봉합 넷: ① 존재 확인을 스킵 조건에 넣는다(선택적 predicate 주입은 버렸다 — 바로 그 실패
모드를 재생산한다. 비용은 pull 당 순차 `stat` 925회로 580초 pull 대비 무시 가능)
② 복원을 `updated` 와 가른다(`DatabaseSyncResult.restored`) — 합치면 dry-run 과 churn 이
"원격이 바뀌었다"고 거짓말한다 ③ 페이지 변경 0건인 **조용한 pull** 에서 설정된 DB 가 있으면
`pullAll()` 도 디스커버리도 건너뛰고 `emptyResult` 로 빠져나가던 경로를 막았다(①만으로는
그 경로에서 여전히 복원 안 됨) ④ `analyze.mjs` 에 **DB→FS 축**을 세웠다.

회귀 가드 `tests/sync/db-row-restore-deleted.test.ts` 4케이스 — 수정 전 4/4 실패, 후 4/4 통과.
실피해는 프로브 1건, **실콘텐츠 0건**(전수 대조 확인).
