## 왜 게이트가 전부 통과했나 — 삼켜진 본문은 사라지지 않는다

R11 때와 같은 표를 세워 보면 이번에도 답이 바로 나온다.

| 게이트            | 보는 성질                    | 경계 파손을 잡는가                        |
| ----------------- | ---------------------------- | ----------------------------------------- |
| 산문 보존율       | 원본 텍스트가 볼트에 있는가  | ✗ — 코드블록 **안에** 그대로 있다         |
| 본문 삼킴 지표    | 글자 수가 줄었는가           | ✗ — 한 글자도 안 줄었다                   |
| 구조 드리프트     | 태그 수가 맞는가             | ✗ — 태그를 삼킨 게 아니라 **감싼** 것     |
| 원시 HTML 노출    | `<tag>` 가 날것으로 보이는가 | ✗ — 코드블록 안이라 노출로 안 세어진다    |
| repull / pushdry  | 멱등성                       | ✗ — 매번 똑같이 깨지면 churn 0            |
| roundtrip 무손실  | 왕복 후 원본과 같은가        | ✗ — 깨진 채로 왕복해도 깨진 채로 돌아온다 |
| **경계 드리프트** | **코드블록 개수·코드 행수**  | **✓**                                     |

기존 7종은 전부 **"내용이 남아 있는가"** 를 본다. 그런데 이 결함은 내용을 **지우지
않는다** — 자리만 옮긴다. 옮겨진 자리가 코드블록 안이라 사람 눈에는 완전히 깨져 보이지만,
어떤 보존율 지표에도 걸리지 않는다. **자리를 안 보는 지표는 자리 결함을 못 잡는다.**

2차 전량 E2E 도 같은 이유로 초록이었다. 그 실행의 요약은 이랬다 — 그 시점 볼트의 지목
노트가 코드블록 37개로 부풀어 본문 8,200행을 삼킨 채로.

```
  pull       md 1268개
  analyze    CLEAN
  verify     완결(행 925=925·쪽 343/343)
  repull     멱등(0)   pushdry  멱등(0)   sync  멱등(0)
  roundtrip  무손실
✓ E2E 전체 통과
```

## 원인 — NFM 의 비대칭 들여쓰기와 평탄화의 충돌

NFM 은 컨테이너 안 코드펜스를 이렇게 낸다. **경계만** 들여쓰고 **내용은 열 0** 이다.

````text
	<details>
	<summary>롤백
		```bash
git checkout v1.2.3
pnpm build
```
	</details>
````

즉 NFM 에서는 **탭 들여쓰기 그 자체가 경계 표시**다. 내용과 경계를 이것으로 구분한다.

그런데 볼트로 쓸 때는 경계를 열 0 으로 평탄화해야 한다. Obsidian 은 "4칸 이상 들여쓰기는
코드블록"을 **절대 들여쓰기** 기준으로 적용하므로, 인용 접두 `> ` 가 붙고 중첩이 겹치면
구조 탭이 그대로 남아서는 안 된다(P1·P2 에서 이미 겪은 규칙이다).

평탄화하는 순간 **경계 표시가 사라진다.** 경계 펜스도 열 0, 내용 안의 백틱도 열 0 —
구분할 근거가 없다. Obsidian 은 펜스를 순서대로 짝짓고, 사용자 코드 안에 있던 ` ``` ` 가
구조 블록을 닫아 버린다. 그다음 진짜 닫는 펜스가 **새 블록을 열고**, 그 뒤 본문 전체가
코드로 빨려 들어간다.

한 문장으로: **경계를 지우는 변환을 하면서 경계를 다른 방법으로 복원하지 않았다.**

## 봉합 — 네 곳

### ① 펜스 짝짓기가 들여쓰기까지 본다 (`findFenceClose`)

내용 펜스가 구조 블록을 닫지 못하게, 여는 줄과 **같은 들여쓰기**의 닫는 줄을 고른다.

단, 정확 일치만 요구하면 안 된다. NFM 은 **닫는 줄의 들여쓰기를 흘리는 경우가 실제로
있다** — 여는 줄 `\t\t`, 닫는 줄 열 0. 엄격하게만 두면 멀쩡한 블록이 파일 끝까지 열린
것으로 잡혀 거짓 적색이 난다. 그래서 **정확 일치 우선 · 없으면 첫 느슨한 줄로 폴백**이다.

### ② 경계 펜스를 내용보다 길게 낸다 (`widenAmbiguousFences`)

들여쓰기를 지우고도 경계를 지키려면 **다른 표시**가 필요하다. CommonMark 의 규칙을 쓴다 —
여는 펜스는 **길이 이상**의 펜스로만 닫힌다. 그래서 경계 펜스를 내용 안의 가장 긴
펜스보다 **한 틱 길게** 내보낸다(내용이 3틱이면 경계는 4틱, 내용이 4틱이면 5틱).

평탄화 뒤에도 사용자 코드 안의 3틱은 4틱 경계를 닫을 수 없다. 지워진 구분을 CommonMark 가
대신 지켜 준다.

### ③ 자식 구간이 컨테이너를 통째로 삼킨다 (`containerBlockEnds`)

이건 ①②를 넣고 나서야 드러난 별개 결함이다. 토글 헤딩의 자식 구간 스캔이 줄마다
들여쓰기를 보는데, 컨테이너 **내부** 줄은 이미 예외 처리돼 있었지만 **닫는 펜스**는
아니었다. 열 0 인 닫는 줄이 `startsWith(childIndent)` 를 통과 못 해 거기서 구간이 끊기고,
그 자리에 `%%im-nobsidian:toggle-heading:end%%` 가 **사용자 코드 안으로** 끼어들었다.

````text
	```bash
git checkout v1.2.3
pnpm build
%%im-nobsidian:toggle-heading:end%%   ← 여기
```
````

줄 단위 판정을 버리고 `containerBlockEnds` 로 **컨테이너 전체를 한 번에 건너뛴다**.
경계 들여쓰기 SSOT(`container-indent.ts`)에 얹어, 같은 규칙을 쓰는 다른 스캐너도
같은 함수를 부르게 했다.

### ④ 코드 안 `<table>` 은 구조가 아니다 (`convertNotionTables`)

경계를 고치고 나서 "코드 안에 든 다른 구조 태그는 없나" 훑다가 나왔다. 실코퍼스 120노트를
펜스 단위로 재스캔하니 코드 **펜스** 안에 `<table` 20행 · `<tr` 114행 · `<td` 159행이
있었다 — **한 노트**에 몰려 있는, 사용자가 적어 둔 HTML 예제 코드다.

`convertNotionTables` 가 이를 구조로 오인해 치환하고 있었다. 그 노트에서 `<table` 29→4 ·
`<tr` 158→1 로 예제가 통째로 사라졌다. `codeInteriorRanges`/`isInsideRanges` 로 코드 내부
오프셋을 건너뛰게 했다.

> 첫 스캔은 틀렸다. `classifyContainerLines` 를 썼는데 그 함수는 **표 내부도 `code` 로
> 표시**해서 `<tr>` 990행/36노트가 나왔다 — 전부 진짜 Notion 표였다. 펜스만 보는 스캔으로
> 다시 짜서 위 수치를 얻었다. 코드 **전용** 지표에 컨테이너 통합 분류기를 쓰면 안 된다.

## 게이트 — 경계를 8번째 지표로

`codeBoundaryDrift(raw, pulled)` 로 원본과 볼트의 **코드블록 개수·코드 행수**를 대조한다.

오라클은 **구현을 재사용하지 않고 독립적으로** 짰다. 이유가 둘이다 — ① 구현을 빌려 쓰면
구현이 틀린 방식 그대로 틀려서 오라클이 아니게 된다. P11 을 잡아낸 것이 바로 이 독립성이다
② `classifyContainerLines` 는 위에 적은 대로 표 내부를 `code` 로 표시해 코드 전용 지표에는
**잘못된 도구**다.

오라클을 짜다 한 번 헛디뎠고, 그게 오히려 규칙 하나를 확인해 줬다. 처음엔 닫는 펜스를
**정확 일치만** 요구했더니 합성 코퍼스 픽스처(여는 `\t\t` · 닫는 열 0 — 일부러 NFM 을
흉내 낸 것)에서 블록이 EOF 까지 열린 것으로 잡혀 거짓 실패했다. 구현과 같은 이유로
**정확 우선 · 느슨한 폴백**이 필요하다.

**지표가 실제로 발화하는지 먼저 확인했다.** 죽은 지표의 0 과 깨끗한 코퍼스의 0 은 출력이
같아 구분이 필요하다.

| 대상                              | `codeBoundaryDrift` 반응                          |
| --------------------------------- | ------------------------------------------------- |
| 수정 **전** 빌드가 만든 실제 볼트 | `코드블록수 5→37` · `코드행수 9695→9188` — 발화 ✓ |
| 수정 **후**                       | `[]` — 무반응 ✓                                   |

## 곁다리 — 마커 노출은 결함이 아니었다

같은 스크린샷에 `%%im-nobsidian:synced:…%%` 도 보였다. P11 의 증상인지(마커가 코드 안에
갇혀 원시 노출) 확인했다.

```
마커 총 23개 · 코드블록 안에 갇힌 것 0개
```

아니었다. 원본 1행을 직접 뜯어보니 열 0 의 **문법상 균형 잡힌** `%%…%%` 주석이고 URL 도
퍼센트 인코딩(`%23`)돼 있어 마커를 깨는 `%%` 가 없다. Obsidian 은 이런 주석을 읽기 모드·
Live Preview 에서 숨긴다 — 설계대로다. 편집 모드에서만 보인다.

가설을 세우고 반증한 것을 남겨 둔다. 안 그러면 다음에 같은 스크린샷을 보고 또 P11 을
의심한다.

## 남는 것

- 이 트랙의 결함류는 **"경계를 지우거나 덜 명시하는 변환"** 이다. P1(구조 탭 → 4-space
  확장) · P2(콜아웃 깊이) · P6(태그명 경계 미확인으로 128행 삼킴) 이 전부 같은 종류였고,
  P11 이 그중 가장 순수한 형태다 — 펜스의 **문자**와 **길이**는 지켰는데 **들여쓰기**를
  버렸다.
- 게이트를 늘릴 때는 **어떤 성질을 보는가**를 먼저 적어야 한다. 7종이 전부 "내용이 남아
  있는가"였다는 건 지표를 세는 동안 아무도 눈치채지 못했다. 다음 지표를 넣을 땐
  `INVARIANT_COVERAGE_MATRIX.md` 에 성질 축으로 먼저 올린다.
