# 2026-07-28 (2) — R12: 스톱워치가 정하던 페이지 목록 (디스커버리 경로 경합 · 침묵한 폴백 · 페이지 완결성)

> R11 일지 말미에 남긴 숙제를 그대로 집는다. `verify` 는 DB 행만 봤고, 정작 회차별 변동이
> 큰 쪽은 페이지였다. 그 변동은 무작위가 아니라 **어느 디스커버리 경로가 도느냐**의
> 문제였고, 그걸 정하는 건 90초짜리 스톱워치 하나였다.

## 증거부터 — 같은 워크스페이스, 같은 날, 다른 개수

R11 실행 로그를 줄 번호로 다시 읽었다. 추론이 아니라 한 실행 안에서 두 경로가 모두
관측된다.

```
line 24    (초기 PULL)  [Im-Nobsidian] 서브트리가 큼(subtree discovery exceeded time
                        budget (93701ms)) → 워크스페이스 search 기반 디스커버리로 전환
line 696~703 (REPULL, 522.9s)  폴백 로그 없음  →  BFS 로 완주  →  churn 0
```

| 실행       | 페이지(file + folder-note) |  db-row | 합계     |
| ---------- | -------------------------: | ------: | -------- |
| 2026-07-17 |                        258 |     629 | 887      |
| 2026-07-27 |                        268 |     925 | 1193     |
| 2026-07-28 |                    **342** | **925** | **1267** |

db-row 는 925 로 안정됐고 R11-B 게이트가 지킨다. 페이지는 같은 워크스페이스인데 **+74
(약 28%)** 흔들렸다. 그리고 그 실행은 `repull churn 0` 을 통과했다.

## 왜 churn 0 이 이걸 못 잡나

`churn = created + updated` 다. 두 번째 열거가 **더 작으면** 만들 것도 고칠 것도 없으니
churn 은 0 이다. 즉 **일치**와 **축소**가 게이트 눈에는 똑같이 보인다. R11 에서 "멱등성 ≠
완결성"을 배웠는데, 그 사각지대가 페이지 쪽에 그대로 남아 있었던 것이다.

## R12-A — 경합 대신 합집합

`getChildPagesRecursive` 는 시간 예산(90초)을 넘기면 예외를 던지고, 오케스트레이터는
그때까지 순회한 **부분 결과를 통째로 버린 뒤** `getPagesUnderRootViaSearch` 로 갈아탔다.
두 열거는 같은 집합을 내지 않는다 — 순회는 깊이를 따라가고 search 는 색인에 오른 것만
본다. 어느 쪽이 도는지를 API 응답 속도가 정한다.

미발견으로 끝나지도 않는다. `orchestrator.ts:1930` 은 **이번 열거에 없는 추적 페이지**를
전부 `deleted` 로 만든다. `deleteSync: true` 면 그날의 API 지연에 따라 실제 노트가 지워지고
다음 pull 이 되살리는 **생성↔삭제 진동**이 된다 — R11-A 에서 본 것과 같은 구조가 페이지
쪽에서 재현되는 것이다.

봉합은 버리지 않는 것이다. `DiscoveryTooLargeError` 가 부분 결과를 payload 로 싣고,
오케스트레이터가 **순회 ∪ search** 를 쓴다.

```ts
} catch (error) {
  if (!(error instanceof DiscoveryTooLargeError)) throw error;
  const viaSearch = await this.notionClient.getPagesUnderRootViaSearch(rootPageId);
  const byId = new Map<string, PageObjectResponse>();
  for (const page of [...error.partial, ...viaSearch]) byId.set(normalizeNotionId(page.id), page);
  underRoot = [...byId.values()];
}
```

세부 둘:

- **디듀프를 여기서 먼저 한다.** 아래 `remotePages` 차단점도 디듀프하지만, 그 전에 도는
  `_childParentIds` 루프의 `extractParentId` 가 block 부모마다 API 를 부를 수 있어 중복을
  남기면 요청이 두 배로 샌다.
- **예산 초과가 아닌 오류는 삼키지 않는다.** `instanceof` 로 갈라, 401 같은 진짜 실패가
  "그냥 search 로 해 보자"로 둔갑하지 않게 한다.

합집합은 폴더노트 분류에도 그대로 이득이다. `_childParentIds`(orchestrator 1889~1895) 가
부모 관계를 이 목록에서 얻기 때문 — 실측에서도 `file` 은 198→270 으로 늘었는데
`folder-note` 는 70→72 에 그쳤던 게 이 비대칭의 흔적이다. 비용도 0 이다. BFS 가 한 일은
지금도 이미 수행된 뒤 버려지고 있었다.

## R12-B — 폴백이 조용히 흘리던 페이지

`getPagesUnderRootViaSearch` 안의 `resolveBlockOwner` 는 블록 부모 조회가 실패하면
`blockOwner.set(bid, null)` 로 접었다. 그 블록에 중첩된 페이지는 결과에서 통째로 빠지는데
**로그 한 줄도 남지 않는다**. 같은 파일의 직접 순회 경로는 스킵할 때 경고를 남기고 있었다
— 또 한 번, **같은 계약이 두 경로에 있고 한쪽만 안 지키는** 비대칭이다. 유실을 관측
가능하게 맞췄다.

## R12-C — `verify` 를 페이지까지

`verifyCompleteness()` 가 `{ databases, pages, complete }` 를 낸다. 설계 결정 셋:

1. **일부러 pull 과 다른 열거를 쓴다.** DB 쪽에서는 정반대 규칙을 세웠었다 — 행은 열거
   방법이 하나뿐이라 검증기가 다른 규칙을 쓰면 게이트가 통과해도 pull 은 놓친다. 페이지는
   사정이 반대다. 열거 경로가 둘이고 **둘이 같은 집합을 내지 않는다는 게 애초의 결함**이다.
   같은 경로로 두 번 세면 그 경로의 편향을 둘 다 물려받는다.
2. **미발견만 실패로 본다.** 볼트에만 있는 페이지는 정상일 수 있다 — 아직 push 하지 않은
   로컬 노트, root 페이지 자신(search 열거는 root 를 제외한다), search 색인 지연. 이걸
   실패로 접으면 게이트가 거짓 적색을 내고, 거짓 적색이 반복되면 게이트는 무시당해 없는
   것과 같아진다. `localOnlyIds` 는 정보성으로만 싣는다.
3. **볼트 쪽은 `fileType !== "db-row"` 로 고른다.** 페이지형 타입을 열거하면
   (`file`·`folder-note`·`folder-only`) 새 타입이 생겼을 때 한쪽만 낡아 조용히 게이트를
   빠져나간다. "행이 아닌 것은 전부 페이지"가 이 대조가 실제로 뜻하는 바다.

DB 모드에는 root 서브트리가 없어 `pages: null` 로 건너뛰되, **없는 대조가 전체 판정을
끌어내리지는 않는다**(끌어내리면 DB 모드는 영원히 실패한다).

## 검증

오프라인 게이트: 테스트 **1576건**(core 1376 · cli 51 · plugin 149) 전량 통과 · tsc ×3 ·
eslint · build 클린.

R12 회귀 21건과 **변이 검증 6종** — 통과가 아니라 "제거하면 무너지는가"로 잠금을 증명한다.

| 변이(옛 동작 복원)                    | 실패 |
| ------------------------------------- | ---: |
| 합집합 → 부분 결과 폐기               |    2 |
| `DiscoveryTooLargeError` payload 제거 |    1 |
| R12-B 경고 제거                       |    1 |
| 페이지 열거 실패를 통과로 접기        |    2 |
| `localOnlyIds` 를 실패로 승격         |    1 |
| 페이지 판정을 전체 판정에서 제외      |    2 |
| DB 모드에서도 페이지 대조 수행        |    1 |

합집합 변이가 **2건**을 깨는 게 핵심이다. 하나는 신규 생성 누락, 다른 하나는
`deleteSync: true` 에서의 **오삭제** — 유실과 파괴를 따로 잠갔다.

한 번 헛디딘 곳도 기록해 둔다. R12-A 클라이언트 테스트를 즉답 목으로 짰더니 마감이
지나지 않아 BFS 가 정상 완주해 예외가 아예 안 났다. 코드 결함이 아니라 **테스트가
무의미했던 것**이다. 목이 예산의 2배를 실제로 태우게 고쳐 결정적으로 만들었다.

### 라이브 clean-slate E2E

지정 볼트(`Im-Nobsidian-Test`)를 비우고 `run.sh full`:

```
reset  볼트 초기화        pull      md 1268개              repull     멱등(0)
init   OK                 analyze   CLEAN                  pushdry    멱등(0)
                          verify    완결(행 925=925        sync       멱등(0)
                                         ·쪽 343/343)      roundtrip  무손실
✓ E2E 전체 통과 (EXIT=0)
```

볼트 상세: md 1268 · `.base` 166 · 첨부 1331 · 폴더 301 / 레코드 1268(file 271 ·
folder-note 72 · db-row 925) · dedup 접미사 158건(정상 disambiguation).
`file 271 + folder-note 72 = 343` 이 `verify` 의 `Vault pages: 343` 과 정확히 일치한다 —
게이트가 세는 집합이 실제 볼트 레코드와 같은 것을 보는지까지 이 등식으로 확인된다.

R12-A 는 이 실행에서 **실제로 발동했다**:

```
line 24  서브트리가 큼(subtree discovery exceeded time budget (96490ms))
         → 순회 부분 결과 80건에 워크스페이스 search 기반 디스커버리를 합칩니다
line 25  디스커버리 합집합: 순회 80 ∪ search 343 → 343건
```

정직하게 적어 둔다 — **이 실행에서는 순회 80 이 search 343 의 부분집합이라 합집합이
더 준 것이 없다**(80 ∪ 343 = 343). 즉 오늘의 초록은 "R12-A 가 74건을 되찾았다"는 증거가
아니라, **폴백이 발동한 실행에서도 두 경로가 어긋나지 않았다**는 관측이다. R12-A 의 값은
어긋나는 날 **덜 찾는 일이 없도록** 하한을 고정하는 데 있고, 어긋나는지를 보는 눈이
R12-C 다. 오늘은 그 눈이 처음 켜졌고 343/343 으로 맞았다.

REPULL(529.1s)에는 폴백 로그가 없다 — BFS 가 예산 안에 완주했고 churn 0 이었다. R11 때와
같은 구도(1회차 폴백 · 2회차 BFS)인데, 이번엔 **두 경로가 같은 수를 냈다는 사실 자체가
게이트로 남는다**. R11 에서는 이걸 확인할 방법이 아예 없었다.

> R11 실행 대비 페이지가 342 → 343 으로 하나 늘었다. 합집합이 보탠 것이 아니므로
> (위에서 0 건) search 색인에 하나가 더 올라온 워크스페이스 쪽 변동으로 본다.
> 결함으로 다루지 않되, 페이지 수가 회차마다 흔들린다는 R12 의 출발점과 같은 현상이라
> 기록해 둔다.

## 교훈

1. **"안 바뀐다"는 "빠짐없다"의 증거가 아니다 — 두 번째로 배웠다.** R11 은 행에서, R12 는
   페이지에서 같은 사각지대를 만났다. churn 이 세는 건 created+updated 뿐이라 **축소가
   일치처럼 보인다**. 게이트를 새로 만들 때는 "이 지표가 0 인 실패 시나리오"를 먼저 적어야
   한다.
2. **폴백은 대체가 아니라 보강이어야 한다.** 경로 B 로 갈아타면서 경로 A 의 결과를 버리면,
   둘 중 무엇이 도느냐를 그날의 지연이 정하게 된다. 합집합이면 최소한 **덜 찾는 일은
   없다**.
3. **같은 계약이 두 경로에 있으면 한쪽은 언젠가 빠진다 — 여덟·아홉 번째.** R9a·R9e·R9f·
   R10-A·R10-C·R10-D·R11-A 에 이어 R12-A(부분결과 폐기)·R12-B(경고 없음)가 같은 결함류다.
   이제는 새 기능을 볼 때 "이 계약을 지켜야 하는 경로가 몇 개인가"부터 센다.
