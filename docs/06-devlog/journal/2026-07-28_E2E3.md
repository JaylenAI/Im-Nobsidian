# 2026-07-28 (4) — 3차 전량 E2E · 본문을 안 읽던 분석기 · 그 자리에서 나온 R13

> 2차 E2E 는 "무결성 CLEAN" 을 찍고 exit 0 으로 끝났다. 같은 볼트에 본문 8,200행이
> 코드블록 안으로 삼켜진 노트가 있었다(P11). 게이트가 거짓말을 한 게 아니라 — **그
> 게이트는 본문을 한 글자도 읽지 않는다.** 파일 개수와 `page_id` 매핑만 봤다.
> P11 일지가 결함을 고쳤다면, 이 일지는 **왜 아무도 못 봤는지**를 고친다.
>
> 그리고 그렇게 고친 분석기가 자기 자리에서 새 결함을 하나 잡았다(R13). 게이트를
> 넓히면 결함이 나온다 — 없던 결함이 생긴 게 아니라, 볼 수 있게 된 것이다.

## 1. 사각지대의 정체

`scripts/e2e/analyze.mjs` 는 두 진실원을 교차검증했다.

| 진실원                | 보는 것                             | 못 보는 것  |
| --------------------- | ----------------------------------- | ----------- |
| 파일시스템            | `.md`/`.base`/첨부/폴더 개수        | 파일 **안** |
| 상태 DB(`sync_state`) | `page_id` ↔ 경로 ↔ `file_type` 매핑 | 파일 **안** |

둘 다 초록이면 `clean: true` 다. 노트 본문이 통째로 회색 코드 상자가 되어 있어도
개수는 맞고 매핑도 맞다. 사람이 여는 것은 본문인데, 하니스는 봉투만 셌다.

한편 렌더 규칙 자체는 이미 있었다 — P8 에서 만든 `tests/render/rules.ts` 다. 문제는
**있는 자리**였다. 테스트 트리 안에 있으니 게이트(코퍼스)만 쓸 수 있고, 볼트를 훑는
하니스는 손이 닿지 않았다. 같은 잣대를 두 곳이 나눠 갖지 못해 한쪽만 초록인 상태가
구조적으로 가능했던 것이다.

## 2. 규칙을 출하 코드로 옮긴다

`packages/core/src/audit/render.ts` 를 만들고 **원본 대조가 필요 없는 규칙**만 옮겼다.
한 파일만 보고 판정할 수 있어야 하니스가 볼트를 훑는 데 쓸 수 있기 때문이다.

| 옮긴 것 (`src/audit/render.ts`)        | 남긴 것 (`tests/render/rules.ts`)       |
| -------------------------------------- | --------------------------------------- |
| ① 콜아웃 4칸+ 들여쓰기                 | 구조 드리프트(원본 NFM 과 헤딩/표 대조) |
| ② 토글헤딩 속성 누수 `{toggle="true"}` | 내용 소실(원본 문자 잔존율)             |
| ③ NFM 컨테이너 태그 누수               | **코드블록 경계 드리프트**(P11 오라클)  |
| ④ NFM 전용 태그 누수                   |                                         |
| ⑤ 코드펜스 4칸 들여쓰기                |                                         |
| ⑦ 표 구분행 고아                       |                                         |
| ⑧ 코드펜스 홀수                        |                                         |

테스트 쪽은 **재선언하지 않고 재수출**한다. 같은 규칙의 사본이 둘이 되는 순간 둘은
갈라지기 시작한다.

```ts
export {
  lintRenderedMarkdown as lintRendered,
  RENDER_LINE_RULES as LINE_RULES,
  SEPARATOR_BODY,
} from "../../src/audit/render.js";
```

`audit/` 에 놓은 것도 의도적이다. 이미 `classifyBodyFidelity`(내용이 남았는가)와
`verifyPageCompleteness`(빠짐없이 왔는가)가 거기 있다. 여기 붙는 축은 **사람 눈에 어떻게
보이는가**다. 셋이 서로의 사각지대를 맡는다 — P11 결함이 정확히 "내용도 다 있고 개수도
맞는데 화면이 깨진" 형태였다.

## 3. 하니스 배선

`analyze.mjs` 가 세 번째 진실원을 갖는다. 볼트의 모든 `.md` 를 읽어 린트하고, 결함이
있으면 **exit 1** 이다.

```js
import { lintRenderedMarkdown } from "../../packages/core/dist/index.js";
```

루트 `node_modules` 에 워크스페이스 링크가 없어(pnpm) 빌드 산출물을 상대경로로 직접
가리킨다. 하니스는 어차피 빌드 후 실행되므로 추가 전제가 아니다.

솔직히 적어 둔다 — **이 배선이 있었어도 P11 은 못 잡았다.** ①–⑧ 은 파일 하나로 판정
가능한 것들이고, P11 은 "원본이 5블록인데 볼트가 37블록"이라 원본이 있어야 안다.
볼트에는 대조본이 없고 `sync.db` 의 `base_snapshot` 도 **변환 후** 마크다운이다. 잡히는
것은 P1–P7 계열(콜아웃 오파싱·태그 누수·표 사망·펜스 홀수)이고, 그건 그것대로 2차
E2E 가 놓친 것들이다.

## 5. 그리고 R13 — 게이트를 넓히자마자 나온 결함

E2E 직후 볼트를 세어 보니 **FS 1,267 vs DB 1,268** 이었다. 한 건이 어긋난다.

```
✗ __e2e_probe__/F21-Child-DB-Probe/F21 프로브 행.md [db-row]
```

`roundtrip` 단계는 `rm -rf __e2e_probe__` 로 프로브 네임스페이스를 통째로 지우고 다시
pull 한다. 페이지 28개는 `✓ 28 restored` 로 돌아왔는데 **db-row 1개만 돌아오지 않았다.**

### 원인 — 같은 계약이 두 경로에 있고 한쪽만 안 지킨다

`database-syncer.ts` 의 행 루프는 원격이 안 바뀌었으면 **로컬 파일이 있는지 묻지도 않고**
건너뛴다.

```ts
const misplaced = !isDirectDbRowPath(dbConfig.localFolder, record.obsidianPath);
if (page.last_edited_time === record.notionLastEdited && !misplaced) continue; // ← 여기
```

복원 판정 코드는 그 아래 `pullDatabasePage` 안에 멀쩡히 있다(`localExists` →
`resolvePullConflict` → `write`). **도달하지 못할 뿐이다.**

그런데 오케스트레이터의 `detectMissingLocalFiles`(R0 의 페이지 복원 경로)는 db-row 를
일부러 제외하면서 이유를 이렇게 적어 두었다 — "db-row 는 매 pull 마다 database-syncer 가
전 행을 훑으며 같은 복원 판정을 이미 거치므로". **그 전제가 틀렸다.** 양쪽 다 "상대가
한다"고 믿어 아무도 안 하는 상태였다. R9a·R9e·R10-D·R11-A 와 같은 결함군이다.

### 왜 어떤 게이트도 못 잡았나

| 게이트          | 왜 통과했나                                                 |
| --------------- | ----------------------------------------------------------- |
| `analyze`       | FS→DB(고아)만 봤다. DB→FS 방향 축이 아예 없었다             |
| `verify`        | **상태 DB 의 id 집합**끼리 맞춘다 — 레코드만 있으면 925=925 |
| `repull`/`sync` | 그 행을 건너뛰므로 애초에 churn 이 0                        |
| 렌더 린트(§2)   | 없는 파일은 읽을 것도 없다                                  |

즉 이 결함은 **모든 초록 신호와 공존한다.** 지정 볼트 1,268 레코드 중 **925개(73%)가
db-row** 이므로 노출면은 다수 쪽이었다.

### 고친 것

1. **존재 확인을 스킵 조건에 넣는다**(`database-syncer.ts`). 선택적 predicate 를 주입하는
   대안은 버렸다 — "같은 계약을 두 경로가 나눠 갖고 한쪽이 잊는" 바로 그 실패 모드를
   재생산하기 때문이다. 비용은 pull 당 순차 `stat` 925회(≈수십 ms, 580초 pull 대비 무시).
2. **복원을 `updated` 와 가른다**(`DatabaseSyncResult.restored`). 합쳐 세면 dry-run 과
   멱등성 게이트가 "원격이 바뀌었다"고 거짓말한다. 페이지 경로가 이미 같은 이유로
   `restored` 를 분리해 보고하므로 어휘도 맞춘다.
3. **조용한 pull 의 DB 경로 누락도 함께 막았다**(`orchestrator.pull`). 페이지 변경이 0건일
   때, 설정된 DB(`notion.databases`)가 하나라도 있으면 `pullAll()` 도 디스커버리도 거치지
   않고 `emptyResult` 로 빠져나갔다 — 1의 수정만으로는 그 경로에서 여전히 복원이 안 된다.
   지금은 두 DB 소스를 모두 거친 뒤에야 "변경 없음"이라 말한다.
4. **분석기에 DB→FS 축을 세운다**(`analyze.mjs`). 추적 레코드인데 실물이 없으면 위반이다.
   이 축이 처음부터 있었으면 R13 은 3차 E2E 의 `analyze` 단계에서 바로 붉게 떴다.

회귀 가드는 `tests/sync/db-row-restore-deleted.test.ts` 4케이스(복원됨 · 리모트 본문으로
복원 · 파일 멀쩡하면 종전대로 스킵하고 API 도 안 늘림 · `updated` 와 안 섞임). 수정 전
4/4 실패, 수정 후 4/4 통과.
