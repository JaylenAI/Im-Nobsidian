# 2026-07-28 — R11: 침묵 유실을 볼 수 있게 만들기 (다중 data source · 완결성 게이트 · 삼켜진 종료코드)

R10 머지 후 볼트 파일 수 기준선(**1193** vs 이전 기록 **887**)의 차이를 추적하다가 시작됐다.
차이는 개선이 아니라 **과거의 유실**이었다 — 볼트의 db-row 925건이 전부 2026-07-17 이전
생성분이었고, 그날의 pull 은 296개 DB 행을 놓친 채 `audit-vault 결함 0 · 해시 불일치 0 ·
repull churn 0` 을 전부 통과했다.

그래서 이번 트랙의 질문은 "무엇이 틀렸나"가 아니라 **"왜 아무 게이트도 못 봤나"** 였다.

브랜치: `feature/db-completeness-gate` (R11-A · R11-B · R11-C).

## 왜 기존 게이트가 전부 통과했나

기존 게이트를 성질별로 세워 보면 답이 바로 나온다.

| 게이트              | 보는 성질                    | 미발견을 잡는가                |
| ------------------- | ---------------------------- | ------------------------------ |
| `analyze` 무결성    | 볼트 안 구조(충돌·중복·고아) | ✗ — 원격을 안 본다             |
| `repull` churn 0    | 멱등성                       | ✗ — 매번 같이 놓치면 churn 0   |
| `pushdry` churn 0   | 멱등성                       | ✗ — 로컬에 없으니 밀 것도 없다 |
| 재-pull 바이트 동일 | 멱등성                       | ✗ — 동일하게 빠진다            |
| 해시 일치           | 존재하는 파일의 내용 충실도  | ✗ — 없는 파일은 대조 대상 밖   |
| **`verify` 완결성** | **원격 집합 = 볼트 집합**    | **✓**                          |

전부 **멱등성**(재실행해도 안 바뀐다)이거나 **볼트 내부 성질**이다. 체계적 미발견은
정의상 멱등하다 — 디스커버리가 매번 같은 행을 똑같이 놓치면 두 번째 실행 결과가 첫
번째와 같으므로 churn 은 0 이고 해시도 전부 일치한다. **재현 가능한 유실은 멱등성
게이트에 보이지 않는다.**

## R11-A — DB 모드 원격 변경 감지가 1차 data source 만 훑었다

Notion API `2025-09-03` 부터 database 는 **`data_sources[]` 를 소유**하고 행은 소스별로
조회한다. 코드에는 이 열거가 두 벌 있었다.

| 경로                       | 열거 방식                             | 범위               |
| -------------------------- | ------------------------------------- | ------------------ |
| `pullDatabase`             | `queryAllDatabasePages()`             | **전 data source** |
| `detectRemoteChanges()` DB | `queryDatabase()` 인라인 페이지네이션 | **1차 소스만**     |

R9a·R9e·R9f·R10-A·R10-C·R10-D 와 **정확히 같은 결함류**다 — 같은 계약이 두 경로에 있고
한쪽만 그 계약을 지킨다.

증상은 미발견에 그치지 않는다. `deleteSync` 를 켜면 **파괴적 진동**이 된다:

```
pullDatabase       → 2번째 소스의 행을 정상 생성
detectRemoteChanges → 그 행이 "원격에 없다"고 보고 → 고아 판정 → 로컬 파일 삭제
다음 pull          → 다시 생성 → 다시 삭제 …
```

한 경로가 만든 파일을 다른 경로가 지운다. 지정 볼트는 `deleteSync: false` 라 유실만
났지만, 문서가 권하는 설정(`deleteSync: true`)에서는 데이터가 사라진다.

봉합은 인라인 사본을 지우고 SSOT 를 부르게 하는 것 하나다:

```ts
const allPages = await this.notionClient.queryAllDatabasePages(this.config.notion.databaseId!);
remotePages = allPages.map((p) => ({ id: p.id, last_edited_time: p.last_edited_time }));
```

회귀 3건(`tests/sync/db-mode-multi-datasource.test.ts`)으로 ① SSOT 를 부르는지 ② 2번째
소스의 행이 실제로 생성까지 가는지 ③ `deleteSync: true` 에서 그 행을 **지우지 않는지**
를 잠갔다. 옛 구현으로 되돌리면 3건 전부 빨간불.

> 테스트를 짜다 OOM(4 GB heap)을 냈다. 원인은 프로덕션이 아니라 목이었다 — `getPage`
> 목이 **어떤 id 에든** DB 부모를 돌려줘 부모 해소 체인이 끝나지 않았다. 목은 실제
> 트리처럼 **종단(workspace)** 을 가져야 한다.

## R11-B — "빠짐없다"를 보는 게이트를 새로 만들었다

`packages/core/src/audit/completeness.ts` 는 database 별로 **원격 행 id 집합**과 **볼트
db-row id 집합**을 대조한다. 설계에서 중요한 결정 셋:

**① 카운트가 아니라 집합.** 원격 925 · 볼트 925 라도 "미발견 1 + 잔재 1" 이면 수는
맞고 내용은 틀리다. 상쇄되는 게이트는 게이트가 아니다. 전용 테스트로 잠갔다 —
`remoteTotal === localTotal` 인데 `complete === false`.

**② 대조 대상은 볼트가 아니라 오케스트레이터가 조립한다.** "볼트가 추적 중인 DB" 만
보면 **통째로 미발견된 DB** 는 영원히 안 보인다(볼트에 흔적이 없으니 대상에도 못 오른다).
그래서 설정 `notion.databases[]` + 디스커버리 캐시 `discovered_dbs` + DB 모드 루트 DB 를
합쳐 넘긴다. `discovered_dbs` 키를 아는 곳은 오케스트레이터 하나로 유지했다 — 호출부가
캐시 표현을 각자 해석하면 표현이 바뀔 때 한쪽만 낡는다.

**③ 조회 실패를 통과로 접지 않는다.** 권한이 빠졌거나 DB 가 지워졌으면 `failures` 로
올리고 `complete = false`. 그 DB 만 총계에서 빼고 나머지는 계속 대조한다.

표면은 셋이다.

| 표면                                | 용도                       |
| ----------------------------------- | -------------------------- |
| `orchestrator.verifyCompleteness()` | 코어 API                   |
| `nobsi verify [--json]`             | 사람 · CI                  |
| E2E `verify` 단계                   | 기본 베이스라인(읽기 전용) |

회귀 15건(완결성 단위 11 · 배선 4 · CLI 4). 배선 테스트는 캐시 JSON 이 깨져도 나머지로
검증을 **계속**하고, 그 상황이 통과로 둔갑하지 않는지까지 본다.

## R11-C — CLI 가 모든 실패를 종료코드 0 으로 삼키고 있었다

R11-B 의 E2E 단계를 붙이다 드러났다. `packages/cli/src/index.ts` 끝에:

```ts
program.parseAsync().then(() => {
  setTimeout(() => process.exit(0), 100); // ← 무조건 0
});
```

better-sqlite3 핸들과 rate limiter 타이머가 이벤트 루프를 잡고 있어 강제 종료가 필요한
건 맞다. 그런데 인자를 0 으로 못박아, 각 명령이 실패마다 세워 둔 `process.exitCode = 1`
(init·pull·push·sync·resolve)을 **전부 덮어썼다**. 즉 **모든 CLI 실패가 종료코드 0 으로
나갔다** — 셸도 CI 도 실패를 감지할 수 없었다. node 프로브 두 개로 실측 확인했다
(하드코딩 0 → exit 0 / `process.exitCode ?? 0` → exit 1).

`packages/cli/src/utils/exit.ts` 로 계약을 이름 붙여 꺼냈다:

```ts
export function scheduleForcedExit(proc, schedule = setTimeout): void {
  schedule(() => proc.exit(resolveExitCode(proc.exitCode)), FORCED_EXIT_DELAY_MS);
}
```

"강제 종료한다"와 "성공으로 종료한다"가 다시 한 줄에 섞이지 않게 하는 게 요점이다.
회귀 7건, `proc.exit(0)` 로 되돌리면 2건 빨간불.

**세 결함은 사슬로 묶여 있다.** R11-C 가 살아 있으면 R11-B 의 E2E 게이트는 **작동하지
않는다** — `nobsi verify` 가 아무리 실패해도 0 으로 끝나 하니스가 통과로 읽는다.
새 게이트를 붙이면서 그 게이트를 무력화하는 결함을 같이 발견한 셈이다.

### 라이브 clean-slate E2E

지정 볼트(`Im-Nobsidian-Test`)를 비우고 `run.sh full`:

```
reset  볼트 초기화        pull      md 1267개      repull     멱등(0)
init   OK                 analyze   CLEAN          pushdry    멱등(0)
                          verify    완결(925=925)  sync       멱등(0)
                                                   roundtrip  무손실
✓ E2E 전체 통과 (EXIT=0)
```

`verify` 가 처음으로 초록을 냈다 — 원격 925행 = 볼트 925행, database 166개 전수 대조.
R11-A 이전 코드로는 2번째 이후 data source 의 행이 `detectRemoteChanges` 에 안 잡혔다.

볼트 상세: md 1267 · `.base` 166 · 첨부 1331 · 폴더 301 / 레코드 1267(file 270 ·
folder-note 72 · db-row 925) · dedup 접미사 158건(정상 disambiguation).

### 이 초록이 덮지 않는 것 — 페이지 쪽은 아직 게이트가 없다

`verify` 는 **DB 행만** 본다. 정작 회차별 변동이 큰 쪽은 페이지다.

| 실행       | 페이지(file + folder-note) |  db-row | 합계     |
| ---------- | -------------------------: | ------: | -------- |
| 2026-07-17 |                        258 |     629 | 887      |
| 2026-07-27 |                        268 |     925 | 1193     |
| 2026-07-28 |                    **342** | **925** | **1267** |

db-row 는 925 로 안정됐고 이제 게이트가 지킨다. 반면 페이지는 같은 워크스페이스인데
**+74(약 28%)** 흔들린다. 이번 실행 로그가 원인을 그대로 보여준다 —

```
PULL   [Im-Nobsidian] 서브트리가 큼(93701ms) → 워크스페이스 search 기반 디스커버리로 전환
REPULL (폴백 로그 없음 = BFS 경로로 완주)  →  churn 0
```

**첫 pull 은 search 경로, 재 pull 은 BFS 경로로 돌았다.** 어느 경로가 도는지를 90초
스톱워치가 정하고, 두 경로의 결과 집합은 같지 않다. 그런데 `repull churn 0` 이다 —
BFS 가 더 적게 찾아도 created/updated 는 0 이라 멱등성 게이트는 침묵한다. R11 에서 배운
것과 정확히 같은 구조가 페이지 쪽에 그대로 남아 있다.

`deleteSync: true` 면 이건 유실로 끝나지 않는다. `orchestrator.ts:1930` 은 이번 열거에
안 잡힌 추적 페이지를 전부 `deleted` 로 만든다 — R11-A 의 create↔delete 진동이 페이지
쪽에서, 그것도 **그날의 API 지연에 따라** 재현된다.

→ R12 로 분리한다: ① 경합 대신 **합집합**(BFS 부분결과를 버리지 않는다) ② search 폴백의
부모 해소 실패 침묵 제거 ③ `verify` 를 페이지까지 확장.

## 교훈

1. **멱등성 ≠ 완결성.** churn 0 · 해시 일치 · 바이트 동일은 전부 "재실행해도 안 바뀐다"를
   본다. 재현 가능한 유실은 그 성질을 만족한다. 296개 행이 그렇게 사라졌다.
2. **게이트를 늘리기 전에 게이트가 실패를 말할 수 있는지 확인한다.** R11-C 를 못 봤으면
   R11-B 는 항상 초록인 장식이었다.
3. **같은 계약이 두 경로에 있으면 한쪽은 언젠가 빠진다.** R9a·R9e·R9f·R10-A·R10-C·R10-D
   에 이어 R11-A 까지 일곱 번째다. 사례를 고치지 말고 경로를 합쳐야 한다.
