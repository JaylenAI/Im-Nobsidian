## 설정 DB · DB 모드의 행 push

원인(코드): 설정 DB(`notion.databases`)의 행은 오케스트레이터의 변경 목록에서 빠지고, 페이지 push 뒤
`DatabaseSyncer.pushAll` 이 따로 올렸다. 그 경로는 바뀔 때마다 모든 속성과 본문을 통째로 보냈다. Notion
쪽 변경이 있어도 수정 시각을 덮어 다음 pull 이 받지 못했고, 충돌 행도 올렸다. WAL 과 입양이 없었고,
이름 변경은 같은 해시일 때만 경로를 옮겨 적었다(Notion 제목은 그대로). dry-run · `--path` · 삭제는 이
행들을 보지 않았고, 행 이름의 하위 폴더에 든 노트는 영영 올라가지 않았다. DB 모드는 생성만 페이지
경로의 분기였다 — 조상 폴더를 Notion 페이지로 만들었고, 생성 요청이 적용됐는지 모르면 새로 만들었다.

수정(`fix/configured-db-row-push`, ADR-015): 설정 DB 의 행과 DB 모드의 새 노트가 자동 발견 DB 의
행과 같은 경로(`pushCreateRow` · `pushRowUpdate` · `pushMove` · `pushDelete`)를 탄다.
`DatabaseSyncer` 의 push 경로와 변경 감지의 `excludeFromMoves` 를 지웠다. DB 모드 행의 레코드는
`file` · `folder-note` 그대로다.

  이어서 설정 DB pull(`DatabaseSyncer.pullAll`)이 같은 행을 다시 본다. 충돌이 아니면 페이지 루프가
  수정 시각을 적어 두므로 두 번째는 건너뛴다(c4 의 `1 updated`). 충돌이면 수정 시각을 올리지 않으므로
  두 번째도 본문을 다시 받아 같은 충돌을 한 번 더 센다(`pullUpdate` · `pullDatabase`). 자동 발견 DB 도
  같은 모양일 것이다(확인하지 않음).
  → `feature/fast-change-detection` 에서 pull 경로를 다시 짜며 고친다.
- **이름을 바꾼 행의 frontmatter 제목** (c6). Notion 제목은 새 파일 이름을 따르지만 로컬 frontmatter 의
  `title: 행 B` 는 그대로다 — 그 행이 Notion 에서 바뀌어 다시 받을 때 맞춰진다(c7 에서 되살린 파일은
  `title: 행 B2`). push 는 볼트에 쓰지 않는다. 행을 받아 쓰는 렌더러는 frontmatter 에 늘 제목을 적는다.
- **되살리거나 받은 행 파일의 모양** (c4 · c7). 행 렌더러가 frontmatter 순서를 바꾸고 빈 속성을 `null`
  로 적고(`메모: null`), 끝 줄바꿈을 떨군다 — 로컬에서 쓴 모양과 다르다. 해시는 받은 내용으로 적어 다음
  push 가 올리지 않는다. 끝 줄바꿈은 Phase 2 변환 왕복, 나머지도 그때 본다.

## frontmatter 읽기 (S-13)

원인(코드): 노트의 frontmatter 를 읽는 여섯 곳 중 다섯이 gray-matter 를 옵션 없이 불렀다. 옵션 없이
부르면 파싱 «전에» 글을 키로 캐시 자리를 만든다 — 파싱이 실패해도 `data: {}` 인 자리가 남아 같은 글의
둘째 호출은 «frontmatter 없음» 을 돌려준다(S-13). 캐시와 별개로 gray-matter 의 여닫는 줄이 Obsidian 과
달랐다. 첫 줄이 `---` 로 «시작»하면 여는 줄로 보고 다음 `---` 줄(없으면 끝)까지를 YAML 로 읽는다 —
Notion 의 구분선으로 시작하는 페이지를 pull 한 노트가 이 모양이다. 여는 줄이 `---js` 면 그 사이를
JavaScript 로 `eval` 한다.

수정(`fix/frontmatter-parse-cache`, ADR-016): 노트의 frontmatter 는 `splitFrontmatter` 한 곳에서
읽는다. 첫 줄과 닫는 줄이 `---` 뿐일 때, 그 사이가 키-값 YAML 일 때만 frontmatter 다(Obsidian 1.13.7
`getFrontMatterInfo` 와 같다). gray-matter 에는 옵션 객체를 넘기고, 깨진 YAML 은 매번 던진다.

## 같은 분 안의 Notion 편집 (N-05)

원인(실측 + 코드): Notion 의 `last_edited_time` 은 분 단위로 잘린다. pull · push 는 본 시각 하나만 적고

## local-first 가 지킨 노트 (F-h)

원인(코드 + 실측): 양쪽이 바뀐 노트를 local-first 는 로컬을 지키고 원격을 받지 않는다. 그런데 페이지 pull(`pullUpdate`)은
그때 파일을 쓴 경우와 같은 모양(`{ path }`)을 돌려줘, 받은 것으로 세고(`updated`) `writtenPaths` 에 넣었다.
`orchestrator.sync()` 는 pull 이 쓴 경로를 이어지는 push 에서 뺀다 — 방금 받은 글을 다시 올리지 않으려는 장치다.
원격을 본 기록도 적지 않으니 다음 sync 도 같았다. 이 경로를 쓰는 것은 플러그인의 Sync 단추 · 볼트 이벤트 자동
동기화 · `nobsi watch -i` 다 — local-first 에서 양쪽이 바뀐 노트는 이 셋으로는 영영 올라가지 않았고, 알림은 매번
`Pull(~1)` 이었다. CLI `sync` 는 pull · push 를 따로 불러 push 는 올렸지만, CLI `pull` 과 함께 받지 않은 노트를
「수정 1」 로 셌다. 증분 pull 은 검색이 행도 페이지 경로로 넘기므로 행도 같았다.

수정(`fix/pull-skip-not-written`):

- pull 이 원격 하나를 처리한 결과를 한 타입으로 모았다 — `written` · `unchanged` · `skipped` · `conflict`
  (`sync/pull-outcome.ts`). 행(DatabaseSyncer)이 이미 쓰던 모양을 페이지도 쓴다. 받은 것으로 세는 것은 `written`
  뿐이다 — 예전에는 반환 자리가 `unchanged: true` 를 빠뜨리면 받은 것이 됐다.
- local-first 가 지킨 노트는 `skipped` — 세지 않고 본 것도 적지 않는다. 이어지는 push 가 로컬을 올려 원격을
  맞추면 그때 적는다. 행의 «원격 그대로» 건너뜀은 `unchanged` 로 가른다(세지 않는 것은 같다).

## deleteSync 가 DB 행을 지웠다 만듦 (S-12)

원인(코드 + 실측): deleteSync 가 켜지면 pull 은 루트 아래 페이지를 순회해 추적 레코드와 견주고, 목록에 없는 추적
레코드를 원격 삭제로 냈다(`detectRemoteChanges`). 순회는 DB 행을 보지 않는다 — 행은 자식 페이지가 아니라 DB
조회로만 보인다. 그래서 행은 매 pull 마다 «사라진 페이지» 가 돼 파일이 지워졌고, 이어지는 DB pull 이 같은 행을
새로 만들었다. 그 사이에 올리지 않은 로컬 행 편집이 사라졌다. 플러그인은 deleteSync 를 늘 켠다(`main.ts`).
`status` 도 같은 감지를 써 행을 모두 원격 삭제로 보였다.

수정(`fix/delete-sync-db-rows`, ADR-018):

- 행은 그 DB 의 조회로 가른다. 전체 대조는 조회하는 DB(설정 DB + 발견 DB − 접근 불가)의 행을 건너뛰고, DB pull
  이 조회에 없던 이 DB 의 추적 행을 가른다(`DatabaseSyncer.pullDeletedRows`).
- 목록 · 조회에 없는 것은 원격에 묻는다(`sync/remote-deletion.ts` 의 `remotePresence`) — 휴지통 · 보관 · 404 일
  때만 지운다. 묻지 못하면 이번에는 둔다. 살아 있는 페이지는 부모가 동기화 범위면 목록이 빠뜨린 것이라 두고,
  범위 밖으로 옮겨졌으면 예전처럼 지운다. 살아 있는 행은 둔다(다른 DB 로 옮겨졌을 수 있다).
- 조회 필터가 있는 DB 는 행의 삭제를 가르지 않는다. `pull --path` 는 범위 안의 행만 지운다.
- 지우는 동작(파일 · 레코드 · 위키링크)을 `applyRemoteDeletion` 하나로 모았다 — 페이지와 행이 같이 쓴다.
  `isTrashedOrArchived` 는 `notion/client.ts` 의 모듈 함수로 뺐다.

## 충돌 해결이 Notion 에 닿지 않음 (N-06)

원인(코드 + 실측): 플러그인의 「충돌 해결」 은 전체 pull 로 충돌을 모은 뒤 `ConflictResolver` 만 불렀다.
`ConflictResolver` 는 볼트 파일과 상태 DB 만 바꾼다 — 고른 결과를 Notion 에 올리지 않는다. 상태는 `synced`, 지난
동기화 사본은 해결 결과가 되니, 다음 pull 은 «로컬 무변경 + 원격 바뀜» 으로 보고 원격으로 덮었다. 고른 «로컬 유지»
· «자동 병합» · «복제» 가 다음 자동 동기화에 사라졌다. CLI `resolve` 는 오케스트레이터(`resolveConflict`)를 거쳐
올렸지만, 그 경로에도 둘이 비어 있었다.

- 올리다 실패하면 상태 `synced` · 사본은 해결 결과로 남았다 — 다음 pull 이 역시 로컬을 덮었다.
- 해소할 목록(`listConflicts`)이 원격을 읽지 못하면 원격을 빈 문자열로 두었다 — «자동 병합» 이 원격 쪽 줄을 모두
  지운 결과(`<<<<<<< LOCAL … ======= >>>>>>> REMOTE`)를 로컬 파일에 썼다.

수정(`fix/plugin-conflict-resolve`):

- 플러그인은 오케스트레이터로 푼다(`SyncController.resolveConflicts`). pull 없이 `listConflicts` → 양쪽이 이미 같은
  것은 `clearStaleConflicts` 로 표시만 푼다 → 하나씩 묻고 `resolveConflict`. 창을 닫으면 «남음», 실패하면 이유를
  알리고 다음 것을 묻는다. 끝에 해결 · 남음 · 실패 수를 알린다. 동기화 중에는 풀지 않고, 푸는 중에는 자동 동기화가
  돌지 않는다. 모달은 고르지 않고 닫혀도 한 번 알린다 — 예전에는 아무것도 알리지 않았다.
- 올리지 못하면 충돌로 되돌린다(`propagateOrReopen`) — 사본 · 상태를 해결 전으로. 볼트 파일(병합 결과 ·
  `.conflict` 사본)은 사용자가 고른 것이라 둔다.
- 해소할 목록은 원격을 읽지 못하면 노트 경로와 이유를 담아 실패한다. 상태 표시(`status()`)의 미리보기는 예전처럼
  원격을 비운 채 둔다.
- 단추 이름 · 설명은 `conflict-choices.ts` 한 곳에 두고 모달과 알림이 같이 쓴다. 설명은 Notion 에 무슨 일이
  일어나는지까지 말한다. `ConflictResolver` 에는 «Notion 에 올리지 않는다» 를 적었다.

## 수정과 삭제가 겹친 노트 (원격 삭제 · 로컬 편집 / F-f)

원인(코드 + 메모리 Notion 재현): 한쪽에서 지우는 사이 다른 쪽에서 고치면 지우는 쪽이 늘 이겼다.

- **Notion 삭제 · 로컬 편집** — pull 은 사라진 노트를 전략을 보지 않고 지웠다(`applyRemoteDeletion`). local-first
  도 같았다. 그 편집은 Notion 에 간 적이 없으니 어디에도 남지 않았다. 행도 같다.
- **로컬 삭제 · Notion 편집(F-f)** — push 는 원격을 보지 않고 휴지통으로 보냈다(`pushDelete`). 본문을 바꿀 때는
  원격을 보고 거절하는데(N-05) 지울 때만 빠져 있었다. pull 하지 않은 그 편집은 Notion 휴지통에만 남았다.

수정(`fix/pull-delete-local-edit`, ADR-019):

- 원격 삭제 — 지난 동기화 뒤 파일이 바뀌었으면(해시) 전략을 따른다. remote-first 는 지운다. local-first 는 파일을
  두고 추적만 놓아 이어지는 push 가 새 페이지 · 같은 DB 의 새 행으로 만든다. manual · duplicate 는 파일과 추적을
  두고 **원격 삭제 충돌**(`remoteChange.type === "deleted"`, 원격 본문 없음)로 남긴다. 페이지와 행이 같은 함수를
  쓴다(ADR-018 에서 모았다).
- 원격 삭제 충돌의 해소는 둘뿐이다(`applicableChoices`) — 로컬 유지(추적을 놓고 곧바로 새 페이지로 만든다. 옛
  페이지는 휴지통에 둔다) · 삭제 따르기(파일도 지운다). 병합 · 복제는 거절한다. 전략으로 풀면 duplicate 는 로컬
  유지, manual 은 거절(`choiceForStrategy`). 새 페이지를 만들지 못하면 이유를 알리고 파일을 둔다 — 다음 push 가
  만든다. 해소 목록(`listConflicts`) · 상태 미리보기는 원격이 사라진 충돌 레코드를 원격 삭제 충돌로 보인다.
- CLI `resolve` 는 «Notion 에서 삭제된 노트» 를 알리고 그 뜻의 선택지만 보인다 — `로컬 유지 (Notion 에 새 페이지로
다시 만들기)` · `삭제 따르기 (Obsidian 파일도 지우기)`. 일괄(`--strategy`)은 먼저 몇 건이 무엇이 되는지 알린다.
  `status` 는 충돌 사유를 «deleted in Notion, local edits not pushed» 로 가른다.
- 플러그인 모달은 줄 비교 대신 «Notion 에서 삭제된 노트입니다» 를 보이고 단추 둘만 둔다. 알림도 같은 말을 쓴다
  (`conflict-choices.ts`).
- 로컬 삭제(F-f) — 휴지통으로 보내기 전에 원격에 묻는다(`remotePresence`). 이미 사라졌으면 추적만 놓는다. 살아
  있고 바뀌었거나 바뀌었는지 모르면(`remoteDrift` ≠ none — 본문 · 제목 · 속성) 지우지 않고 이유를 남긴다. 이어지는
  pull 이 편집과 함께 되살려 받는다. 읽지 못하면 그 오류로 실패한다. local-first · push 전용 · 한 번도 동기화하지
  않은 레코드는 예전처럼 지운다(`overwritesRemote`).
- 원격 삭제 변경을 만드는 곳이 셋이었다(전체 대조 · 행 조회 · 해소 목록) — `remoteDeletionChange` 하나로 모았다.
  `strategyToChoice` 는 `choiceForStrategy` 로 바꿨다(전략 → 선택지가 충돌 종류를 본다).

검증:

## 코드 안의 임베드 (S-18)

원인(코드 + 메모리 왕복 시험): push 의 `EmbedResolver` 는 본문 전체에서 `![[…]]` 를 찾았다. 위키링크 · 주석 ·
홀로 남은 마커 떼기는 이미 코드를 피하는데(`md-regions`) 임베드만 코드 펜스 · 인라인 코드를 가리지 않았다.

- 코드 펜스 안의 `![[a.png]]` 가 자리표시자 줄이 되어 Notion 의 코드 블록에 그대로 보였다.
- 인라인 코드 `` `![[b.pdf]]` `` 는 둘로 쪼개지고 그 사이에 자리표시자 줄이 들어갔다. 한 문단이 세 블록이 되고,
  다시 받으면 노트의 그 줄이 쪼개진 채 돌아왔다.
- 볼트에 그 파일이 있으면 올렸다 — 옛 코드에 메모리 왕복 시험을 돌려 확인했다
  (`expected [ 'a.png', '계약서.pdf' ] to deeply equal []`).
- **찾은 것 하나 더** — 코드 안에 자리표시자 모양의 글이 있으면(형식을 설명하는 노트) push 가 그 블록을 미디어로
  바꾸고 지웠다. `materializeLocalMedia` 가 블록 종류를 가리지 않고 글에서 마커를 찾았다. pull 의
  `LocalImageRestorer` 도 코드 안의 같은 글을 임베드로 바꿔, 받은 노트의 코드가 바뀌었다. 이 레포의 ADR-009 표에도 그런
  글이 인라인 코드로 있다. 옛 push 가 코드 펜스 안에 심은 자리표시자도 같은 길을 탔을 것이다 — 코드 블록이 이미지로
  바뀐다. 코드와 단위 시험으로 확인했고, 실 Notion 에서 v0.3.2 로 재현하지는 않았다.
- 인라인 코드 판정(`mapOutsideInlineCode`)이 빈 줄을 넘어 짝을 찾았다. 두 문단에 하나씩 있는 홑 백틱 사이를 통째로
  코드로 여겨, 그 사이의 위키링크를 링크로 올리지 않았다. 임베드도 같은 가드를 쓰게 되어 함께 고쳤다.

- `EmbedResolver` 는 코드 밖 조각에만 임베드 · 이미지 링크를 바꾼다(`mapOutsideCode`, `ae65662`). 자리표시자를 자기
  줄로 떼어 낼지는 조각이 아니라 원문 줄을 보고 정한다 — 인라인 코드에 붙은 임베드는 조각의 맨 앞 · 끝이지만 줄의
  맨 앞 · 끝이 아니다.
- 자리표시자는 push 가 quote 로만 심으므로 quote 블록만 자리표시자로 본다. pull 은 코드 밖에서만 임베드로 되돌린다
  (`38d4979`).

## 코드 펜스 언어 (S-20)

원인(실측 · 코드): push 는 펜스의 정보 문자열을 그대로 보냈고, Notion 코드 블록의 언어는 정해진 90개다. 프로브 페이지
두 장에 펜스 168개를 `pages.create` · `replace_content` 로 올려 저장된 언어를 읽었다 — 둘이 같다(ADR-021 맥락 표).

- 정식 이름과 Notion 이 아는 별칭(`ts` · `py` · `sh` · `md` · `yml` · `text` …)은 정식 이름으로 저장된다. 정식 이름
  `ascii art` · `java/c/c++/c#` 과 Notion 이 모르는 것(`zsh` · `console` · `golang` · 언어 없음 · `dataview` ·
  `dataviewjs` · `tasks` · 속성 붙은 정보)은 javascript 가 된다 — Notion 에서 Dataview 쿼리가 JavaScript 로 칠해졌다.
- `~~~` 펜스는 코드 블록이 아니라 이스케이프된 문단이 된다. 네 백틱 이상 펜스는 정보를 세 백틱 뒤부터 읽고, 코드 속의
  백틱 세 개 줄에서 블록을 가른다. 코드 블록 캡션은 markdown 으로 오가지 않는다.
- pull 은 Notion 이름을 그대로 적었다. Notion 에서 고친 뒤 처음 받으면 노트의 `ts` 가 `typescript`, `dataview` 가
  `javascript` 로 바뀌어 Dataview 쿼리가 죽었다.
- 블록 방식 push(`preferMarkdownApi: false`)의 martian 은 정보의 첫 낱말만 제 표로 옮겨 `plain text` · `llvm ir` 같은
  여러 낱말 이름을 잃고, `text` 를 vb.net 으로 보냈다.

수정(`fix/code-language`, ADR-021):

- push 는 Notion 이름만 보낸다(`CodeLanguageGuard`, 전처리 46). 모르는 것은 `plain text`. 코드에 백틱 세 개 줄이
  없으면 `~~~` · 긴 펜스를 백틱 세 개 펜스로 보낸다. 언어 목록의 주인은 SDK 타입(`LanguageRequest`)이다 — SDK 에
  언어가 늘거나 줄면 타입 오류가 난다.
- pull 은 받기 직전의 로컬 노트에서 원래 표기를 찾는다(`CodeLanguageRestorer`, 후처리 36 · `localContent`). 코드가
  같은 펜스는 펜스 기호와 정보를 그대로 되돌리고, Notion 에서 코드를 고친 블록은 Notion 언어가 같은 것끼리 짝지어
  정보만 되돌린다. 언어가 다르면 Notion 에서 바꾼 것이니 그쪽을 따른다.
- 설정 DB 의 행도 같다. 행을 옮기며 받을 때는 옛 자리의 노트를 읽는다.
- 블록 방식은 만든 블록의 언어를 같은 코드의 펜스 언어로 덮는다(`applyFenceLanguages`).
- 로컬 노트를 읽지 못하면 이유를 남기고 Notion 이름으로 받는다 — 받기는 멈추지 않는다.

## 코드 속 펜스 모양 줄 (S-25)

원인(코드 · 단위 시험): 코드 블록이 어디서 닫히는지를 BlockSpacer 와 `mapOutsideCodeFences` 가 따로 정했다. 둘 다 여는
펜스의 문자 셋으로 시작하는 펜스 줄이면 닫았다. CommonMark 는 같은 문자 · 여는 것 이상의 길이 · 뒤에 공백만 있고 여는
쪽보다 3칸 넘게 들여쓰지 않은 줄에서만 닫는다.

- 네 백틱 펜스에 담은 마크다운 예제의 백틱 세 개 + `bash` 줄에서 블록을 닫았다. 받을 때 BlockSpacer 가 그 뒤 코드를
  문단으로 보고 코드 사이에 빈 줄을 끼웠다.
- 올릴 때 `mapOutsideCodeFences` 가 같은 줄에서 코드 구간을 닫았다. 그 뒤 코드 속 `%%…%%` 를 주석으로 지우는 등 본문처럼
  고쳤다 — 주석 제거 · 각주 · 이스케이프 정규화가 이 가드를 쓴다.
- 여는 것보다 짧은 펜스 · 더 깊이 들여쓴 펜스 줄에서도 닫았다.

수정(`a44cd1b`): 여는 줄 · 닫는 줄 판정을 `md-regions` 한 곳(`openCodeFence` · `closesCodeFence` · `indentWidth`)에 두고
BlockSpacer 와 `mapOutsideCodeFences` 가 함께 읽는다. 정보 문자열에 백틱이 있는 백틱 줄은 펜스가 아니라 인라인 코드다.
CRLF 노트의 줄 끝 `\r` 은 공백으로 본다. 아래 S-24 가 목록 안 코드의 경계 펜스를 넓히는 것이 이 판정에 기댄다.

검증:

- 단위: md-regions 8 · BlockSpacer 6 · 주석 제거 1 시험 추가. 변이 14개를 모두 잡는다.
- 실볼트(읽기 전용): 노트 1271개 · 인용 밖 코드 블록 274개에서 옛 규칙과 닫는 줄이 다른 파일은 0개다. 이 수정으로 push
  본문이 바뀌는 노트는 없다.

## 목록 안 코드 블록 (S-24)

원인(실측 · 코드): Notion 은 목록 항목의 자식 코드 블록을 경계 펜스만 탭으로 들여쓰고 코드 줄은 열 0 에 둔 채 내보낸다.
프로브 19장과 실데이터 E2E 의 export 가 모두 이 모양이다. 콜아웃 · 토글의 코드는 `dedentContainerBody` 가 맞추는데 목록
항목은 빠졌다.

- Obsidian 은 항목 내용 폭보다 얕은 코드 줄에서 목록과 코드 블록을 끝낸다. 목록 안에는 빈 코드 블록이, 목록 밖에는 코드가
  문단으로 보였다. 실볼트 12파일 · 37곳.
- BlockSpacer 는 목록 자식 펜스를 새 블록으로 떼어 앞뒤에 빈 줄을 넣었다 — 목록 전체가 느슨한 목록이 되었다.
- 렌더 감사 ⑤ 는 목록 자식의 4칸 펜스를 결함으로 셌고, 목록 밖으로 샌 코드는 잡지 못했다. 렌더 게이트가 이 결함을 볼 수
  없었다.
- 변환기 시험 둘이 Notion 이 코드 줄까지 탭으로 들여쓴다고(대칭) 가정해 이 결함을 가렸다.

## 달러 기호 · 블록 수식 (S-21)

원인(실측 · 코드): push 전처리 `MathNormalizer` 가 본문 전체 — 코드까지 — 에 정규식 둘을 걸었다. 인라인 `$…$` 는 안쪽
공백을 자르고, 블록 `$$…$$` 는 `$$` · 식 · `$$` 세 줄로 다시 썼다. pull 은 맞게 받았다. 실볼트에서 `$` 가 든 노트 31장 중
9장의 push 본문이 바뀌었고 모두 손상이었다. Notion 이 올린 markdown 을 읽는 방식은 ADR-023 의 표에 있다.

- 수식이 아닌 달러가 수식이 됐다 — `$5 and $10` 은 Notion 에서 수식 「5 and」 가 된다. 「집 $5/월」 은 앞 달러와 짝지어져
  공백이 빠졌다.
- 코드가 바뀌었다 — 인용 속 인라인 코드 · 코드 속 템플릿 리터럴의 공백이 빠지고, 셸의 `$$` 가 코드 밖 수식의 `$$` 와
  짝지어져 그 사이 본문까지 옮겼다.
- 콜아웃 안 블록 수식의 닫는 `$$` 를 줄머리(`> `) 없이 세워 콜아웃 밖으로 꺼냈다. 프로브에서 Notion 은 그 `$$` 부터 뒤
  문단을 수식 블록으로 삼켰다. Notion 에서 받은 「첫 자식이 수식인 콜아웃」 노트 4장(`> [!note] $$` 로 여는 모양)을
  로컬에서 고쳐 올리면 이렇게 된다.
- 글 사이 `$$x$$` 를 세 줄로 갈랐다. Notion 은 원래 인라인 수식으로 읽는데, 가르면 빈 수식과 글이 된다.

수정(`fix/math-in-code`, ADR-023):

- `MathNormalizer` 는 인라인 수식을 건드리지 않는다. Obsidian 1.13.7 의 토크나이저와 Notion 이 같은 규칙으로 수식을
  가린다 — 노트 그대로 보내면 두 쪽이 같은 곳을 수식으로 본다.
- 블록 수식은 코드 밖에서, 두 `$$` 가 줄의 처음(인용 표시 · 들여쓰기 뒤)과 끝일 때만 줄머리째 `$$` · 식 · `$$` 줄로 편다.
  글 사이 `$$x$$` · 짝이 인용 · 목록 밖으로 넘어간 것 · 빈 식은 둔다.
- BlockSpacer 가 목록 자식 수식을 항목에 붙이고 구조 탭을 4칸으로 편다 — S-24 의 코드 블록과 같게. Notion 은 목록 자식
  수식을 `$$` · 식 줄 모두 탭으로 내보낸다. 예전에는 앞에 빈 줄을 끼워 느슨한 목록 · 탭으로 받았다(실볼트 0곳, 프로브
  모양).
- 공개 API: `MathNormalizer` 가 인라인 수식의 안쪽 공백을 자르지 않고 코드 안을 보지 않는다.

원인(코드): 오케스트레이터는 실행마다 원격을 본 시각(`observation.seenAt`)과 새 경로 선점 장부(`claimedPaths`)를 쥔다. 겹치면

## dry-run 이 상태를 바꾸고 실제와 다르게 셈 (N-01 · N-02 · N-03)

찾은 것:

- N-01: 원격 페이지 변경이 없으면 `pull --dry-run` 이 조기 반환 경로로 가 설정 DB · 발견 DB 의 행을 실제로
  받고, 마감이 기준 시각(`last_pull_at` · `last_sync_at`)을 옮겼다. 페이지 변경이 있으면 거꾸로 DB 행을
  하나도 세지 않았다.
- dry-run 이 원격에서 지운 페이지를 모두 삭제로 셌다. 실제 pull 은 폴더 레코드는 추적만 놓고, 올리지 않은
  로컬 편집이 있는 노트는 전략에 따라 두거나 충돌로 남긴다.
- N-02: deleteSync 가 꺼져 있어도 `push --dry-run` 이 로컬에서 지운 노트를 삭제로 셌다. 실제 push 는
  Notion 에서 지우지 않는다.
- N-03: dry-run 이 끊긴 실행 표시(`push_in_progress` · `pull_in_progress`)를 지우고 끊긴 작업(WAL)을
  정리했다 — 고아 페이지 입양 · 자리표시 제거 · 실패 표시.

수정(`fix/dry-run-side-effects`):

- core: pull dry-run 은 조기 반환 · 마감 전에 끝나고 페이지와 DB 행을 함께 센다. 행은 `pullDatabase` 와 같은
  판정으로 센다 — 조회 · 범위 · 받을 행 · 삭제 확인을 나눠 쓴다(`planDatabase`). DB 도 실제 pull 이 받는 것과
  같게 고른다: 설정 DB 와 발견해 둔 DB, 접근 불가로 뺀 DB 는 빼고, 폴더 충돌(F24)은 읽어 온 사본에서만 가른다.
  증분 감지가 행을 페이지 변경으로도 잡으면 한 번만 센다 — 실제 pull 은 페이지 경로에서 받고 DB 경로는 건너뛴다.
- core: 원격 삭제를 어떻게 반영할지 가르는 판정을 떼어(`decideRemoteDeletion`) pull 과 dry-run 이 같이 쓴다.
- core: 세지 못한 DB 는 이유와 함께 `failed` 에 싣는다. 발견해 둔 DB 가 사라진 것(404)은 실제 pull 처럼
  실패로 세지 않는다.
- core: push dry-run 은 deleteSync 가 꺼져 있으면 지운 노트를 세지 않는다. push · pull dry-run 은 끊긴 실행
  표시 · WAL · 폴더 레코드를 건드리지 않는다.

검증: 새 시험 13건 — dry-run 뒤 볼트(내용 · 수정 시각)와 상태 DB(레코드 · 기준 시각 · 발견 DB 캐시)가
그대로인지 보고, 곧이어 돌린 실제 실행과 수를 견준다. 뮤테이션 21종 모두 잡힘 — 처음 19, 남은 둘(볼트에서도 폴더를 지운 경우 · DB 모드에 남은 발견 캐시)은
시험을 더해 잡았다. 전량 2549 통과 · 11 건너뜀, 린트 · 타입 · 포맷 · 빌드 초록.

남은 것 · 한계:

- 이번 pull 이 새로 발견할 DB 의 행은 세지 않는다 — 받아 봐야 안다.
- 본문을 받지 않으므로, 받아 보고 같으면 쓰지 않을 것 · local-first 가 지킬 것 · 충돌로 남길 것도 고침으로
  센다. 같은 분 안의 편집(«확인 안 됨»)은 페이지만 내용으로 가르고 행은 고침으로 센다.
- 새 행의 경로는 지금 상태 기준이다. 같은 pull 에서 만든 행과 이름이 겹치면 실제 경로에는 id 가 붙는다.
- 끊긴 생성을 입양할 노트도 dry-run 은 새로 만들 것으로 센다.
- 실제 pull 은 발견 DB 를 읽지 못하면(404 밖) `failed` 에 싣지 않고 경고 로그만 남긴다 — pull 이 성공으로
  끝나 사용자는 그 DB 를 받지 못한 줄 모른다. dry-run 은 싣는다. 실제 pull 쪽은 따로 고친다.

## 발견 DB 를 읽지 못해도 pull 이 성공으로 끝남

찾은 것(바로 위 dry-run 수정 중):

- 발견해 둔 DB 의 행 조회가 404 밖의 오류(연결 끊김 · 5xx)로 실패하면 경고 로그만 남기고 `failed` 에 싣지
  않았다. pull 은 성공으로 끝나 사용자는 그 DB 를 받지 못한 줄 몰랐다. 캐시에는 남아 다음 pull 이 받기는 했다.
- 블록 스캔(`getChildDatabaseIds`)이 실패한 페이지는 이유를 가리지 않고 권한 없음으로 보고 넘겼다. 스캔은
  발견 캐시가 빌 때만 하므로, 캐시가 한 번 차면 그 페이지 아래의 DB 는 `pull --force` 전까지 찾지 않았다.
- 찾은 DB 의 설정(제목 · 조회 가능 여부)을 404 밖의 오류로 읽지 못해도 로그만 남았다. 캐시에 들지 않아 다시
  찾지도 않았다. 연결된 보기의 원본도 같았다.
- 발견 전체가 멈춰도(상태 DB 읽기 오류 등) 로그만 남았다.

수정(`fix/discovered-db-failures`):

- core: 넷 모두 이유와 함께 `failed` 에 싣는다. 행 조회 실패는 그 DB 폴더를, 스캔 · 설정 실패는 부모
  페이지의 볼트 경로(루트면 빈 경로)를 적는다.
- core: 읽지 못한 페이지와 DB 를 상태 메타 `discovery_retry` 에 적어, 캐시가 차 있어도 다음 pull 이 그것만
  다시 본다. 다시 봐서 읽히면 목록에서 지운다.
- core: 권한 없음(403 `restricted_resource`)은 404 처럼 건너뛴다 — 다시 봐도 같다(`isNotionAccessDenied`).
- cli: 빈 경로의 실패를 `/` 로 보인다. `sync` 는 받기 ▼ · 올리기 ▲ 로 가른다.

검증: 새 시험 core 6건 · cli 2건 — 실패가 이유와 함께 실리고, 곧이어 돌린 pull 이 그 DB 를 받는지 본다.
404 는 실패가 아니고 접근 불가 목록에 든다. 뮤테이션 11종 모두 잡힘 — 연결된 보기 원본의 재시도는 시험을
더해 잡았다. 전량 2557 통과 · 11 건너뜀, 린트 · 타입 · 포맷 · 빌드 초록.

남은 것 · 한계:

- 플러그인은 실패 수만 보이고 이유는 보이지 않는다 — U-03 에서 다룬다.
- 발견이 도중에 멈추면 이번 pull 이 받은 페이지 · 행 본문에서 찾은 DB 는 캐시에 남지 않는다. 캐시가 이미
  차 있었으면 다음 pull 이 그 DB 를 다시 찾지 않을 수 있다 — `pull --force` 가 처음부터 찾는다. 코드로 본
  것이고 시험하지 않았다.
- 권한 없음(403) 페이지를 나중에 통합에 공유했을 때 그 아래 DB 를 찾는지는 확인하지 못했다.

## 변경 목록 · 진행 표시의 옮김 · DB 행 (sync-status-api)

찾은 것:

- push 가 옮긴 노트를 「수정」 으로 셌다 — 이름만 바꾼 노트도 `updated 1` 이었다. 옮긴 폴더는 수에만 들고
  진행 항목으로 알리지 않았다.
- 변경 목록(`status` · `statusLocal`)이 폴더 이동을 싣지 않았다. CLI `status` 는 옮긴 노트를 목록과 수에서
  통째로 뺐고, 지운 노트는 수만, 원격 변경은 내부 id 로 보였다. 옮긴 노트의 레코드는 옛 경로라 `synced` 에
  겹쳐 셌다.
- `sync` 는 받기 · 올리기 항목을 한 콜백으로 알려 화면이 둘을 가를 수 없었다. CLI `sync` 는
  `orchestrator.sync()` 를 쓰지 않고 pull · push 를 따로 불렀다(F-j).
- 실제 pull 은 DB 행을 진행 항목으로 알리지 않았다 — 행이 대부분인 볼트(실볼트 887 파일 중 629)는 pull 내내
  진행 표시가 멈춰 보였다. dry-run 은 행을 보였고, 새 페이지는 내부 id 로 보였다.
- CLI 에 되돌리기가 없었다. 옮긴 노트의 새 자리를 되돌리려 하면 「추적하지 않는 새 노트」 라고 거절했다.

수정(`feature/sync-status-api`, 커밋 7개 — 커밋마다 전량 게이트 초록):

- core: `PushResult.moved` — 옮긴 노트 · 폴더는 여기서만 센다(`updated` 와 겹치지 않는다). 진행 항목에
  `operation: "move"`, `sync` 는 `direction: "pull" | "push"` 를 적는다. `StatusResult.folderMoves`
  (`FolderMoveChange`) — Notion 에 반영할 폴더와 볼트 쪽만 바꿀 DB 폴더. `status` 도 push 와 같은 판정
  (`planLocalChanges`)을 쓴다.
- core: 실제 pull 이 설정 DB · 발견 DB 의 행을 받고 지울 때마다 알린다(`RowProgress`). 행은 조회해야 몇
  개인지 알아 받을 행 수만큼 전체를 늘린다 — 현재 수는 하나씩 오르고 전체를 넘지 않는다. dry-run 은 새
  페이지를 Notion 제목으로 보인다(받기 전에는 자리를 모른다).
- core: `discardLocalChange` 가 옮긴 노트의 새 자리는 옛 자리를 알리며 거절한다.
- cli: `status` 가 옮김(폴더 먼저) · 지운 노트 목록 · 원격 변경 이름(노트는 경로, 새 페이지는 제목) · 원격
  옮김 수를 보이고, 되돌릴 수 있는 변경이 있으면 `discard` 를 안내한다. `push` · `watch` · JSON 이 옮김을
  싣고 JSON churn 에 더한다. `sync` 는 `orchestrator.sync()` 를 쓰고 ▼ Pull · ▲ Push 아래에 항목을 가른다.
  새 명령 `nobsi discard <경로...>` — 경로마다 결과를 보이고 하나라도 못 되돌리면 종료 코드 1.
- plugin: 변경 패널이 옮긴 폴더를 폴더 행으로(↑ 는 그 폴더의 이동을 올림), 옮긴 노트를 어디서 왔는지와
  함께 보인다. Push · Sync 알림에 이동 수를 따로 적는다.

검증: 새 시험 21건(core 11 · cli 8 · plugin 2) — 메모리 볼트 · 메모리 Notion · 실제 상태 DB 로 폴더 이동 ·
옮기며 고친 노트 · DB 폴더 이동 · 행 진행(설정 DB · 발견 DB · 삭제 · 페이지와 함께)을 끝까지 돌린다.
뮤테이션 34종 모두 잡힘 — 발견 DB 행 진행 · 옮긴 노트와 새 노트 가르기는 시험을 더해 잡았다. 전량 2578
통과 · 11 건너뜀, 린트 · 타입 · 포맷 · 빌드 초록. svelte-check 는 기존 4건(쓰지 않는 변수) 그대로다.

남은 것 · 한계:

- 옮긴 노트는 되돌리지 않는다 — 파일을 옛 자리로 옮기면 된다(`discard` 가 그 자리를 알린다).
- dry-run 의 새 페이지는 제목이다 — 받을 자리(부모 · 자식 페이지)는 받을 때 정해진다.
- 진행의 전체 수는 행을 조회한 뒤 는다 — 처음 보인 전체가 끝의 전체가 아니다. 실패한 항목은 알리지 않아
  현재 수가 전체에 못 미치고 끝날 수 있다(페이지도 같다).
- 설정 DB 의 `pullAll` 이 통째로 던지면 경고 로그만 남는다(DB 마다의 실패는 싣는다) —
  `feature/fast-change-detection` 에서 본다.
- 실볼트 E2E 는 릴리스 전에 한 번에 돌린다.

## 변경 패널 · CLI 의 줄 비교 (plugin-changes-view)

찾은 것:

- 변경 패널은 무엇이 바뀌었는지(A/M/D · 옮김 · 원격)만 보였다. 항목을 누르면 노트가 열릴 뿐이라, 올리기(↑) ·
  되돌리기(↺) · 받기(↓) 전에 무엇이 어떻게 바뀌었는지 볼 곳이 없었다.
- 줄 비교가 세 벌이었고 셋 다 달랐다. 플러그인 충돌 창과 core `generateDiff`(CLI `resolve`)는 같은 번호의 줄끼리
  견줬다 — 앞에 한 줄만 더해도 그 뒤 모든 줄이 바뀐 것으로 보였고, 파일 전체를 찍었다. CLI `diff` 는 jsdiff 를
  따로 불러 문맥 4줄 · `===` 줄로 찍었다.
- CLI `diff` 는 옮긴 노트와 지난 동기화 사본이 없는 고친 노트를 빈 줄로 넘기고 성공으로 끝났다.
- 실제 Obsidian(1.13.7)에서 줄 비교를 열자 바뀐 줄의 글이 보이지 않았다. 바탕은 `--background-modifier-error`,
  글은 `--text-error` 인데 기본 테마에서 둘이 같은 색이다(실측: 어두운 #fb464c · 밝은 #e93147, 성공 쪽도 같음).
  옛 충돌 창도 2026-05-23(`24d1b0c`)부터 같은 규칙이었다. happy-dom 화면 시험은 색을 계산하지 않아 몰랐다.

수정(`feature/plugin-changes-view`, 커밋 7개 — 커밋마다 전량 게이트 초록):

- core: `lineDiff` — jsdiff `structuredPatch` 를 감싼 줄 비교. 문맥은 3줄이고, 바뀐 양이 2,000 을 넘으면 통째로
  바꾼 것으로 낸다. 결과는 `DiffHunk` · `DiffLine`(옛 번호 · 새 번호, 끝 줄바꿈 없음은 바뀐 줄에만)이다.
  `formatUnifiedDiff` 가 Git 식 글을 만들고, 부호는 `DIFF_SIGN` 하나다. `generateDiff` 도 이것을 쓴다.
- core: `localChangeDiff` 는 지난 동기화 사본과 볼트를, `remoteChangeDiff` 는 지난 동기화 사본과 Notion 의 지금 글을
  견준다. 원격 글은 pull 과 같은 변환이고 첨부는 내려받지 않는다. 둘 다 잠그지 않는다 — 긴 pull 중에도 볼 수
  있다. 다음 경우는 이유를 담아 거절한다: 변경 목록이 본 레코드와 지문이 다를 때, 사본이 없을 때, 새 페이지 ·
  폴더일 때.
- plugin: 변경 패널의 항목을 누르면 줄 비교 창이 열린다(`ChangeDiffModal` · `ChangeDiffView` · `DiffLines`). 창은
  옛 번호 · 새 번호 · 부호와 묶음 사이 ⋯, 끝 줄바꿈 없음을 보인다. 노트 열기는 ↗ 로 옮겼다. 아직 받지 않은 새
  페이지는 누를 수 없고, 이유를 말풍선으로 보인다. 충돌 창도 같은 `DiffLines` 를 쓴다.
- plugin: 바뀐 줄은 옅은 바탕(`rgba(var(--color-red-rgb), 0.15)`)에 보통 글색으로 쓰고, 부호만 오류 · 성공
  색으로 칠한다. CSS 가드 시험(`tests/styles.test.ts`)을 두었다 — 같은 색일 수 있는 바탕 · 글 변수를 한 규칙에
  함께 쓰지 않는지, `styles.css` 가 `src/styles/main.css` 와 같은지 본다.
- cli: `diff` 가 `localChangeDiff` · `lineDiff` · `formatUnifiedDiff` 를 쓴다 — 플러그인과 같은 비교(문맥
  3줄)다.
  - 옮긴 노트는 `rename from` · `rename to` 뒤에 비교한다. 내용이 같으면 그렇다고 알린다.
  - 비교하지 못한 노트는 이유를 보이고 종료 코드 1 로 끝낸다.
  - `--remote` 는 옮긴 노트의 Notion 쪽 이름을 옛 자리로 적고, 같은 글이면 「(Notion 과 내용이 같습니다)」 를
    찍는다.
  - `resolve` 의 충돌 비교도 같은 모양 · 색이다(`printUnifiedDiff`). jsdiff 의존성은 core 로 옮겼다.

## 변경 패널의 충돌 목록 · 작업 단계 · 오류 띠 색 (plugin-panel-conflicts)

찾은 것 — 격리 Obsidian(1.13.7)에 옛 빌드(`6e17973`)를 올리고, 프로브 컨테이너 아래 Notion 페이지로 재현했다:

- 로컬 새로고침(볼트 편집 · pull 뒤 · 충돌 창을 닫은 뒤)이 `statusLocal` 의 `conflicts` 를 실었다. 이것은 원격까지
  본 충돌이라 로컬 조회에서는 늘 빈 목록이다. 상태 DB 에 `배추.md` 가 충돌로 남아 있는데 패널은 「⚠ 충돌 0건」 을
  보이고, 충돌 목록과 「충돌 해결」 단추가 사라졌다.
- 플러그인을 다시 불러오면 상태바는 Ready, 패널은 충돌이었다.
- pull 이 쓴 노트의 볼트 이벤트가 부른 로컬 새로고침이, 도는 작업의 단계를 「충돌」 로 덮었다. 새 페이지 4개를
  받는 pull 에서 도는 동안 233번 적었는데 79번이 「동기화 중」 이 아니었고 Pull 단추가 풀려 있었다(동기화 중 6.25초
  → 진행 0.8초 → 충돌 · 단추 풀림 0.4초 → 진행 0.65초 → 충돌 · 단추 풀림 3.55초).
- 자동 동기화(볼트 이벤트)가 끝난 뒤 목록을 새로고치지 않아, 올린 노트가 4초 뒤에도 변경으로 남았다. 그 항목을
  누르면 「지난 동기화 기록이 변경 목록과 맞지 않습니다 — 새로고침한 뒤 다시 보세요 (시금치 2.md)」 가 떴다.
- 실패 이유가 다음 편집에 지워졌다. 충돌 중인 노트를 되돌리면 core 가 거절해 오류 띠가 뜬다(「충돌 중인 노트는
  충돌 해결에서 고르세요 — 배추.md」). 다른 노트를 고치자 띠가 사라지고 패널은 「충돌 0건」, 상태바는 Error 로
  남았다. ↻ 로 원격까지 본 뒤에도 상태바는 Error 였다.
- 오류 띠 · 충돌 배지 · 올려 둔 취소 단추가 `--background-modifier-error` 바탕에 `--text-error` 글이었다. 1.13 기본
  테마에서 둘이 같은 색이라 대비가 1.0 이다(어두운 · 밝은 테마 모두). 사용자 화면에서도 글 없는 빨간 띠로 보였다.

수정(`fix/plugin-panel-conflicts`, 커밋 2개 + 문서):

- plugin: 패널의 충돌은 상태 DB 의 충돌 기록(`conflictRecords`)이다 — CLI `status` 와 같다. 원격을 읽지 않아도
  알므로 로컬 새로고침도 싣는다.
- plugin: 컨트롤러가 패널에 보낸 단계 · 진행 · 오류를 기억한다(`emitState`). 로컬 새로고침은 작업이 끝났을 때만
  단계를 정한다(`settle` — 충돌이 남았으면 충돌, 아니면 준비됨, 상태바도 같이). 그 밖에는 목록만 바꾸고 단계는
  그대로 다시 싣는다. 지난 실패 이유는 다음에 끝까지 돈 작업이나 ↻ 가 걷는다.
- plugin: 자동 동기화가 끝나면 목록을 새로고친다. 되돌리기 · 충돌 해결도 끝나면 단계를 정한다.
- plugin: 오류 띠는 옅은 빨강 바탕에 보통 글색과 왼쪽 빨간 선, 충돌 배지와 올려 둔 취소 단추는 옅은 빨강 바탕이다.
  짙기는 `--im-nobsidian-tint`(main.css) 하나로 두고 줄 비교와 함께 쓴다. CSS 가드 시험이 컴포넌트의 `<style>` 과
  올려 둔 상태(`:hover` 등)까지 본다 — 평소 규칙의 글색과 상태 규칙의 바탕이 나뉜 경우도 잡는다.

## 플러그인을 다시 불러와도 옛 컴포넌트 CSS 가 남음 (plugin-component-css)

찾은 것:

- 변경 패널 색 수정(`fix/plugin-panel-conflicts`)을 격리 Obsidian 에 올리고 플러그인을 다시 불러왔는데, 오류 띠
  글의 대비가 그대로 1.0 이었다. 문서의 `<style id="svelte-b4tuhn">` 는 옛 규칙 그대로였고, 새 빌드의 대시보드도
  같은 해시(`svelte-b4tuhn`)를 썼다.
- Svelte 5.56 의 기본 `cssHash` 는 파일 이름으로 해시를 만든다(`compiler/validate-options.js`). `append_styles` 는
  같은 id 의 `<style>` 이 이미 있으면 넣지 않고, 컴포넌트를 내려도 지우지 않는다(`internal/client/dom/css.js`).
  그래서 사용자가 플러그인을 업데이트해도 Obsidian 을 다시 켜기 전까지 컴포넌트 CSS 는 옛 것이다.
  `styles.css`(main.css)는 Obsidian 이 플러그인과 함께 넣고 빼므로 해당 없다.

수정(`fix/plugin-component-css`):

- plugin: 빌드의 Svelte 컴파일 옵션을 `svelte-options.mjs` 로 옮기고, 해시를 컴포넌트 이름과 CSS 내용으로
  만든다(`svelte-${hash(name + css)}`). 고친 CSS 는 새 id 로 들어가고, 남은 옛 `<style>` 은 옛 해시의 요소만
  가리킨다.
- 시험: CSS 를 고치면 해시가 바뀌는지, 같은 CSS 는 파일 경로와 무관하게 같은 해시인지, 빌드가 이 옵션을 쓰는지
  본다.

검증:

- 새 시험 3건 — 전량 2,655 → 2,658 통과 · 11 건너뜀, 빌드 · 린트 · 포맷 · 타입 초록.
- 뮤테이션 5/5 가 잡혔다 — 기본 해시로 되돌림 · 파일 경로 해시 · 이름만 해시 · 외부 CSS · 빌드가 제 옵션을 씀.
- 같은 소스를 다른 폴더(스크래치 작업 트리)에서 빌드해도 `main.js` 가 바이트 단위로 같다(`39ee58f1`). 원래
  설정도 폴더마다 같았다 — esbuild-svelte 가 상대 경로를 넘긴다.
- 업데이트 경로 실측(격리 Obsidian 1.13.7):
  - 남은 컴포넌트 `<style>` 을 지워 새로 켠 것과 같게 한 뒤 옛 빌드(`6e17973`)를 올려 다시 불러오면, 대시보드는
    `svelte-b4tuhn` 이고 오류 띠 대비는 1.0 이다.
  - 이 브랜치의 빌드로 바꾸고 **다시 불러오기만** 하면 대시보드가 `svelte-kudf9h` 를 쓰고, 그 `<style>` 은 새
    규칙이다. 대비(어두운 · 밝은)는 오류 띠 8.95 · 11.93, 충돌 배지 3.62 · 3.15, 올려 둔 취소 단추 3.62 · 3.15 —
    다시 켠 뒤와 같다.

한계:

## 상태 DB 를 닫고 다시 열 때 기록이 사라짐 (plugin-state-db-close)

찾은 것(격리 Obsidian 1.13.7, dev `5d206c7` 빌드, 상태 DB 를 실볼트 크기인 7MB 로 키워 표시용 메타 키로 잼):

- 계획은 「설정을 바꿀 때 앞 DB 의 쓰기를 기다리지 않고 같은 파일을 다시 읽는다」 였다. 재 보니 이 길로는 사라지지
  않았다(0/40 — 원래 크기 20회 · 7MB 20회). Obsidian 의 파일 어댑터가 `exists` · `readBinary` · `writeBinary` 를
  한 줄(`queue`)로 세워, 먼저 부른 쓰기가 늘 읽기보다 먼저 끝난다(1.13.7 `app.js` 의 데스크톱 어댑터).
- 실제로 사라지는 것은 둘이었다.
  - **쓰는 사이에 바뀐 기록.** `flush()` 가 쓰기가 끝난 뒤에 «바뀜» 을 내려, 쓰는 사이의 변경이 파일에 가지
    않았다. 5초 주기 쓰기가 도는 동안 sync 가 기록을 쓰면 이렇게 된다. 그 뒤로 바뀐 것이 없으면 닫을 때도 쓰지
    않는다. 쓰기를 띄우고 그 사이에 바꾼 뒤 설정을 바꾸면 5/5, 다시 불러오면 3/3 이 사라졌다.
  - **작업 중에 다시 불러오기(업데이트 · 끄고 켜기).** Obsidian 은 onunload 의 비동기 일을 기다리지 않는다. 옛
    인스턴스가 도는 작업을 멈추고 마지막 쓰기를 마치기 전에 새 인스턴스가 파일을 읽었다(2/2, 사과.md 만 pull
    하는 중에 다시 불러옴). 옛 파일을 읽은 새 인스턴스는 다음 쓰기로 옛 인스턴스의 마지막 기록을 덮는다 — 만든
    페이지의 기록이 빠지면 다음 push 가 같은 페이지를 또 만든다.

수정(`fix/plugin-state-db-close`):

- plugin `SqlJsStateDB`: 쓰기를 한 줄로 세우고(앞 쓰기가 끝난 뒤에 그때의 DB 를 내보낸다), «바뀜» 을 내보낼 때
  내린다. 못 쓰면 «바뀜» 을 되살리고 이유를 던진다. `close()` 는 남은 쓰기를 마친 뒤에 닫고, 못 쓰면 닫지 않고
  이유를 던진다. 주기 쓰기가 실패하면 처리되지 않은 거부로 두지 않고 이유를 경고로 남긴다.
- plugin `main.ts`: `closeStateDb` 가 닫기를 기다리고, 못 쓰면 DB 를 쥔 채 이유를 던진다(다음 초기화가 다시
  닫는다). onunload 는 닫는 일을 창 전역에 알리고(`state-db-handoff.ts` — 두 인스턴스는 main.js 를 따로 평가해
  모듈 변수를 나누지 못한다), 새 인스턴스는 그것이 끝난 뒤에 파일을 읽는다(`readStateDbFile`).

검증:

- 새 시험 14건 — 전량 2,669 → 2,683 통과 · 11 건너뜀, 빌드 · 린트 · 포맷 · 타입 초록. 쓰기 시험은 실제 sql.js 로
  파일에 남은 DB 를 다시 열어 보고, 옛 쓰기가 가장 늦게 끝나는 차례로도 돌린다.
- 뮤테이션 13/13 이 잡혔다 — 쓰기 뒤에 «바뀜» 내림, 쓰기를 한 줄로 세우지 않음, 실패 때 «바뀜» 을 되살리지 않음,
  한 번 실패하면 뒤 쓰기가 모두 실패, 닫기가 쓰기를 기다리지 않음, 못 써도 닫음, 주기 쓰기 실패를 알리지 않음,
  플러그인이 닫기를 기다리지 않음, 못 닫았을 때 DB 를 놓음, 닫는 일을 알리지 않음, 새 인스턴스가 기다리지 않음,
  마지막 닫기만 기다림, 앞 인스턴스가 닫다가 실패하면 새 인스턴스가 열지 못함.
- 실측(격리 Obsidian 1.13.7, 7MB DB), 사라진 횟수 수정 전 → 후:
  - 쓰는 사이에 바꾼 뒤 설정 변경: 5/5 → 0/5
  - 쓰는 사이에 바꾼 뒤 다시 불러오기: 3/3 → 0/3

  - 설정 변경만 · 다시 불러오기만: 0/40 → 0/20 · 0/10
- 잰 뒤 표시용 메타를 지우고 VACUUM 해 DB 를 원래 크기(120KB)로 되돌렸다. 볼트 노트 · 변경 패널(시금치 3,
  충돌 배추, 레코드 14)은 재기 전과 같다.

한계:

- 작업 중에 다시 불러오면 새 인스턴스는 옛 작업이 끝날 때까지 기다린다 — 실측 14.0초(pull 을 시작하고 약 1.5초

## 상태 DB 를 읽지 못하면 빈 DB 로 열어 기록을 덮음 (plugin-state-db-read)

찾은 것(앞 절 끝에 적은 것, 격리 Obsidian 1.13.7 · dev `ce37f8e` 빌드):

- `readStateDbFile` 이 읽기 실패를 모두 «처음(파일 없음)» 으로 보고 null 을 돌려, 빈 DB 로 초기화했다. 데스크톱
  어댑터의 `exists` 는 `fs.access` 가 실패하면 false 를 돌려줄 뿐 던지지 않고, 던지는 것은 `readBinary`
  (`fs.readFile`) 다 — 파일은 있는데 읽지 못할 때다: 권한, 다른 프로그램(백신 · 클라우드 동기화)이 쥔 파일, 입출력
  오류.
- 재현: 상태 DB 파일을 쓰기만 되게(`chmod 200`) 하고 플러그인을 다시 불러왔다.
  - 알림 없이 초기화가 끝나고 DB 기록은 0건(파일에는 14건), 상태바 Ready, 패널 「준비됨 · 아직 동기화 안됨 ·
    변경된 파일 13」 — 모든 노트가 새 노트로 보였고 충돌 기록도 사라졌다.
  - 그 상태에서 무엇이든 한 번 쓰면(표시용 메타 하나로 흉내) 5초 주기 쓰기가 파일을 빈 DB 로 덮었다 — 122,880 →
    110,592 B, 동기화 기록 14 → 0건, 충돌 1 → 0건, 마지막 pull · push · sync 시각도 사라졌다. 여기서 Push 를
    누르면 노트 13개의 페이지를 Notion 에 또 만든다(Notion 에 중복을 만들지 않으려고 재지 않았다).

수정(`fix/plugin-state-db-read`):

- `readStateDbFile`: 파일이 없을 때만 null. 읽지 못하면 「상태 DB 를 읽지 못함 (.im-nobsidian/sync.db): 이유」 로
  던진다 — 초기화가 실패하고 빈 DB 를 열지 않는다.
- 초기화가 실패한 이유를 둔다(`initFailure`). 명령(Push · Pull · Sync · 상태 · 충돌 해결 · 줄 비교 · DB 뷰)과
  인라인 DB 뷰가 「설정을 먼저 완료해주세요」 대신 까닭을 가려 보인다 — 설정이 비었나, 초기화가 실패했나(그
  이유), 아직 초기화 중인가. 9곳에 흩어져 있던 같은 문구를 `notReadyReason()` 하나로 모았다.
- 변경 패널: 초기화가 실패하면 오류 단계와 이유를 보이고, 새로고침을 누르면 초기화를 다시 해 본다 — 파일을 쥔
  프로그램이 놓은 뒤에 플러그인을 다시 불러오지 않아도 된다. 오류 중에는 「변경 사항 없음」 을 띄우지 않고,
  마지막 동기화를 모르면 그 줄을 뺀다 — 읽지 못한 것을 없다고 하지 않는다.

## 상태 DB 쓰기가 도중에 끊기면 파일이 잘리고, 잘린 파일을 빈 DB 로 엶 (plugin-state-db-atomic-write)

찾은 것(격리 Obsidian 1.13.7 · 작업대):

- 상태 DB 는 바뀌면 5초마다 파일을 통째로 쓴다. 예전에는 어댑터 `writeBinary` 로 썼는데, 1.13.7 데스크톱 어댑터는
  `fs.writeFile` 로 제자리에 쓴다 — 파일을 비우고 처음부터 쓰므로 쓰는 도중에 프로세스가 죽으면 잘린 파일이
  남는다. 어댑터의 `rename` 은 대상이 있으면 던져(「Destination file already exists!」) 갈아 끼우기에 쓸 수 없다.
- 작업대(실볼트 DB 크기인 7MB 파일): 쓰기를 되풀이하는 자식 프로세스를 쓰는 도중에 50번 죽이면 제자리 쓰기는
  40번 파일이 깨졌다(0바이트 29 · 잘림 11).
- SQLite 는 0바이트 · 1바이트 파일을 «빈 DB» 로 연다. 한 페이지 이상 잘린 파일은 첫 조회에서 「database disk image
  is malformed」, 16바이트처럼 머리가 깨진 파일은 「file is not a database」 를 던진다.
- 격리 Obsidian, 수정 전 빌드 `b7968372`(아래 첫 커밋까지):
  - 0바이트: 알림 없이 빈 DB 로 열렸다 — 기록 0건(파일에는 14건이었다), 상태바 Ready, 패널 「준비됨 · 아직 동기화
    안됨 · 변경된 파일 13」. 여기서 Push 를 누르면 기록 없는 노트 13개의 페이지를 새로 만든다(`pushCreate` —
    Notion 에 중복을 만들지 않으려고 재지 않았다).
  - 64KB 로 잘림: 「초기화 실패: database disk image is malformed」 — 어느 파일이 왜 안 열리는지, 무엇을 하면
    되는지 말하지 않는다.

수정(`fix/plugin-state-db-atomic-write`):

- `a5d8f3f` 한 번에 갈아 끼운다 — 옆 임시 파일(`sync.db.tmp`)에 다 쓰고 `fsync` 로 디스크에 내린 뒤 이름을 바꾼다.
  쓰는 도중에 죽어도 파일은 옛 것이거나 새 것이다. 어댑터 대신 Node `fs` 를 쓴다(플러그인은 데스크톱 전용).
- `45a93ab` 저장된 파일을 확인한다 — 동기화 기록 표(`sync_metadata`)가 없으면 「저장된 상태 DB 파일에 동기화
  기록이 없음 (N바이트)」, SQLite 가 열지 못하면 「저장된 상태 DB 파일을 열지 못함 (SQLite 의 이유)」 로 던진다
  (`SavedStateDbError`). 초기화는 이 경우에만 치우는 법을 붙인다 — 볼트 폴더의 `.im-nobsidian/sync.db` 를 사본으로
  바꾸거나 옮긴 뒤 동기화 사이드바에서 새로고침, 옮기면 짝을 잃어 다음 push 가 페이지를 새로 만든다는 것까지.
  wasm 을 띄우지 못한 것 같은 다른 실패에는 붙이지 않는다 — 멀쩡한 기록을 치우게 된다. 열지 못한 DB 는 닫는다
  (새로고침으로 다시 해 볼 때마다 메모리에 쌓이지 않게).
- 모의 sql.js 는 저장 데이터를 버려 「기존 데이터로 열기」 시험이 아무것도 보지 못했다 — 실제 sql.js 시험
  (`sqljs-state-db-open.test.ts`)으로 옮겼다.

한계:

- `fsync` 는 파일만 디스크에 내린다 — 이름 바꾸기를 담은 폴더는 내리지 않아, 전원이 나가면 옛 파일로 돌아갈 수
  있다(잘린 파일은 아니다). 전원 차단은 재지 않았다.
- Windows 에서는 다른 프로그램(백신 · 클라우드 동기화)이 파일을 쥐고 있으면 이름 바꾸기가 실패할 수 있다 — 그
  쓰기는 실패로 남고 바뀐 것은 다음 쓰기가 다시 쓴다. Windows 에서 재지 않았다.
- 깨진 파일은 안내만 한다. 치우는 것은 사용자가 파일 관리자에서 한다 — `.im-nobsidian` 은 Obsidian 파일 탐색기에
  보이지 않는다. 옆으로 치우고 새로 시작하는 단추는 없다.
- 앞부분은 멀쩡하고 뒤쪽 페이지만 깨진 파일은 열 때 모른다 — 그 페이지를 읽는 조회가 그때 던진다. 열 때 무결성
  검사(`PRAGMA quick_check`)는 하지 않았다(열 때마다 전체를 읽는다).
