## "Git 처럼 되는가" — 아니다

push 는 이미 해시 증분이다. 느린 것은 pull 이고, 원인은 한 곳이다 — 원격 무변경이어도
매 pull 이 발견 DB 166개를 전부 `queryAllDatabasePages` 로 다시 읽고 `.base` 를 다시
만든다(`orchestrator.ts:1197` 루프). 페이지 쪽 감지는 이미 search 정렬 + 워터마크 증분이다.

DB 행도 페이지라서 같은 search 결과에 나온다. 그러니 search 한 번으로 "바뀐 행이 속한 DB"
만 골라 pull 하면 된다. search 가 못 보는 것(휴지통 · 인덱스 지연으로 빠진 새 페이지)은
주기적 전체 대조로 잡는다 — S-08 이 바로 그 빈틈이었다.

## S-01 · S-02 — 행은 행으로 보낸다

원인은 한 곳이었다. 행인지를 전역 모드(`parentMode`)로 갈라서, 페이지 모드 볼트가 자동
발견한 DB 의 행(`db-row`)이 페이지 경로로 밀렸다. 페이지 경로는 속성으로 제목만 보내고
나머지 frontmatter 를 본문 첫머리 YAML 블록으로 끼운다.

수정(`fix/db-row-property-push`): 행인지는 레코드가 정하고, 행은 `pushRowUpdate` 로 간다.

| 무엇              | 규칙                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 무엇을 보내나     | 원격이 지난 동기화 뒤 그대로면 지난 동기화 사본과 견줘 바뀐 속성만. 통째로 보내면 로컬이 평문으로만 아는 서식(굵게 · 링크 · 멘션)이 매번 지워진다                                   |
| 원격도 바뀌었으면 | 로컬에서 바꾼 것만 보내고 `notionLastEdited` 를 올리지 않는다 — 올리면 다음 pull 이 원격 변경을 영영 받지 않는다                                                                    |
| 충돌 해소 결과    | 해소가 사본을 먼저 바꾸므로 사본과 견주면 보낼 것이 없다. 원격의 지금 값과 견줘 다른 것을 모두 보내고 본문도 보낸다                                                                 |
| 본문              | 바뀌었을 때만, YAML 없이                                                                                                                                                            |
| 속성 변환         | DB 스키마에 있는 것만. 읽기 전용(수식 · 롤업 · 생성일 등)과 모르는 유형은 보내지 않는다. relation · people 은 하나라도 ID 로 못 바꾸면 통째로 뺀다(일부만 보내면 나머지가 지워진다) |
| 글 속성           | 2,000자 조각 · 100조각 상한. 넘으면 보내지 않는다(요청 전체가 400 이 되어 다른 속성까지 거부된다)                                                                                   |
| 제목              | frontmatter `title`, 없으면 파일 이름 — pull 이 쓰는 제목과 같다                                                                                                                    |
| 원격 행 그리기    | 충돌 · 비교 화면도 pull 과 같은 렌더러. 본문 첫머리의 옛 YAML 블록은 행에서는 버린다                                                                                                |

S-13(gray-matter 캐시)은 이 작업의 단위 시험이 찾았다. 깨진 frontmatter 를 첫 시도에서
거절해도, push 재시도가 같은 글을 다시 읽을 때 캐시가 «frontmatter 없음» 을 돌려줘 행의

통째로 건너뛰고도 `updated` 로 세고 해시를 올렸다. `allow_deleting_content: true` 로 보내면
자식이 지워지기 때문에 넣은 가드(수정2)였다. 실측 규칙과 결정은 ADR-009.

수정(`fix/child-page-body-push`): 삭제를 허용하지 않고 보내고, 거절되면 Notion 이 준 자식
태그를 push 본문의 «그 자식을 가리키던 줄» 에 되돌려 한 번 더 보낸다. 자리가 없는 자식은
페이지 끝으로 옮기고 경고한다 — 지우지 않는다.

실측 — 프로브 볼트. `S-03 프로브` 폴더 노트(자식 페이지 1 · 인라인 DB 1)와 `QA-C 폴더노트`

- 인용(`>`) 안의 자식 태그 · 회의록(meeting note) 자식은 실측하지 못했다.

  않는다(강제 재전송 명령이 없다) — 릴리스 노트에 적는다.

## S-08 원인 — 새 하위 트리의 자식이 증분 pull 에서 빠진다

S-03 실측 중 재현했다. 새로 만든 `S-03 프로브` 와 그 자식 페이지(둘 다 09:47 생성)가 한 번의
증분 pull 에 함께 잡혔는데 폴더 노트만 받고 자식 페이지는 빠졌다. 다음 증분 pull 도
「no changes」 였고 `pull --force` 만 받았다.

원인(코드): `detectRemoteChangesIncremental` 은 추적되지 않은 페이지를 부모가 루트거나 이미
추적 중일 때만 받는다(`isTrackedParent`). 같은 실행에서 새로 받는 부모는 감지가 끝날 때까지
추적 전이라 그 자식이 빠진다. 다음 실행의 조회 창(마지막 pull − 15분)은 그 자식의 수정
시각보다 뒤라 다시 보이지 않는다 — 원격에서 자식을 고치기 전까지 영영 빠진다.
`fix/incremental-new-subtree` 에서 같은 실행의 새 부모도 부모로 인정하게 고친다.

수정: 감지 단계에서 추적되지 않은 새 페이지를 부모와 함께 모은 뒤, 부모가 루트 · 추적 중이거나
**이번에 함께 받기로 한 새 페이지** 이면 받는다. 한 번 훑어서는 깊은 것부터 오는 순서(손자 →
자식 → 부모)를 못 받으므로 더 받을 것이 없을 때까지 되풀이한다. 루트 밖(추적하지 않는 부모
아래)의 새 페이지는 여전히 받지 않는다.

- 단위: `tests/sync/pull-incremental-new-subtree.test.ts` 2 — 손자 · 자식 · 부모 · 루트 밖
  순서로 와도 3건을 제자리 경로로 받고 루트 밖은 건너뛴다 / 다시 증분 pull 하면 0건.
  둘 다 수정 전 코드에서 실패한다(「expected 1 to be 3」 · 「expected 1 to be +0」).
- 실데이터 E2E (프로브 볼트, 10:36 에 3단 하위 트리 생성): 곧바로 한 증분 pull 은 검색 색인
  지연으로 0건(`no changes`, 9.3s). 20초쯤 뒤 증분 pull 이 **3 created · 0 failed** — 세 페이지가
  같은 초(10:37:18)에 `S-08 프로브 — 새 하위 트리 (v0.4)/…/S-08 자식/S-08 손자.md` 까지
  폴더 노트 배치로 기록됐다. 다시 pull · `push --dry-run` 모두 0건.

남는 것: 재시도까지 실패한 항목 · 중단된 pull 이 건너뛴 항목도 다음 조회 창 밖으로 밀려
빠진다(`last_pull_at` 을 끝난 시각으로 올린다) — `fix/pull-watermark` 로 나눈다. 검색 색인
지연이 조회 창(15분)보다 길면 빠지는 경우는 주기적 전체 대조(Phase A)가 잡는다.

## 기준 시각 — 받지 못한 변경이 다음 증분 조회에서 빠진다

S-08 을 고치며 같은 계열의 빈틈을 더 찾았다. 증분 pull 은 `last_pull_at − 15분` 이후에 고친
페이지만 search 로 받는데, `last_pull_at` 을 pull 이 **끝난** 시각으로 적었다. 그래서 이번
실행이 받지 못한 변경 — 재시도까지 실패 · 취소(플러그인 「동기화 취소」)로 건너뜀 · 경로를
좁힌 pull(`--path`)의 범위 밖 — 과 15분보다 긴 pull 도중의 원격 편집이, 다음 pull 이 15분 넘게
뒤에 오면 창 밖으로 밀려 원격에서 다시 고치기 전까지 빠졌다. `status` 는 push 도 올리는
`last_sync_at` 으로 조회해 pull 이 받을 변경을 「없음」 으로 보고할 수 있었고, pull 도
`last_pull_at` 이 없으면 `last_sync_at` 으로 대신해 push 만 한 볼트의 첫 pull 이 그 전에
원격에만 있던 페이지를 받지 못했다.

수정(`fix/pull-watermark`, ADR-010): pull 을 시작한 시각을 적고, 받지 못한 변경이 있으면 그중
가장 이른 수정 시각으로 묶는다. 경로를 좁힌 pull 은 옮기지 않는다. 기준 시각은 `last_pull_at`
뿐이고 pull · status 가 같은 규칙(`incrementalWatermark`)을 읽는다.

- 단위: `tests/sync/pull-watermark.test.ts` 10 — 조회 시각을 지키는 가짜 search 와 고정 시계.
  7개가 수정 전 코드에서 실패한다(「expected +0 to be 1」 × 5 · status 「expected [] …」 ·
  push 만 한 볼트 「expected undefined …」).
- 불변식(실 Notion) 15/15 · 151초.
- 실데이터 E2E (프로브 볼트, 빌드 `3a66a59` + 이 브랜치):

  | 단계                                    | 시각(UTC) | 결과                                                                  |
  | --------------------------------------- | --------- | --------------------------------------------------------------------- |
  | 일반 pull                               | 10:51:12  | 0건. 기준 시각 10:51:12.169 = 시작 시각(끝난 시각 10:51:19 가 아니라) |
  | 프로브 루트 아래 새 페이지 `…24a4` 생성 | 10:51:25  | Notion 이 적은 수정 시각 10:51:00 (분 단위로 내림 — 기준 시각보다 앞) |
  | `pull -p __범위밖__`                    | 10:53:03  | 0건 · 기준 시각 그대로. `status --full` 은 새 페이지 1건을 보여 준다  |
  | `pull -p __범위밖__` (수정 + 15분 뒤)   | 11:19:23  | 0건 · 기준 시각 그대로 10:51:12 — 수정 전 코드는 11:19 로 올렸다      |
  | 일반 pull                               | 11:19:31  | **1 created** · 0 failed                                              |

  수정 전 코드였다면 11:19 의 범위 pull 이 기준 시각을 11:19 로 올려 다음 조회가 11:04 부터가
  되고, 10:51 에 고친 새 페이지는 원격에서 다시 고치기 전까지 빠졌다.

남는 것: 실패가 계속되면 조회 창이 그 시각에 머물러 조회가 길어진다(ADR-010 트레이드오프).
Phase A 의 「바뀐 DB 만 pull」 이 search 로 DB 행 변경을 고를 때도 같은 규칙 — 받지 못한 행이
있으면 그 수정 시각으로 묶는다 — 을 따라야 한다.
