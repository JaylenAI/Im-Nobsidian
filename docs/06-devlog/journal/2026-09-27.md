## "Git 처럼 되는가" — 아니다

push 는 이미 해시 증분이다. 느린 것은 pull 이고, 원인은 한 곳이다 — 원격 무변경이어도
매 pull 이 발견 DB 166개를 전부 `queryAllDatabasePages` 로 다시 읽고 `.base` 를 다시
만든다(`orchestrator.ts:1197` 루프). 페이지 쪽 감지는 이미 search 정렬 + 워터마크 증분이다.

DB 행도 페이지라서 같은 search 결과에 나온다. 그러니 search 한 번으로 "바뀐 행이 속한 DB"
만 골라 pull 하면 된다. search 가 못 보는 것(휴지통 · 인덱스 지연으로 빠진 새 페이지)은
주기적 전체 대조로 잡는다 — S-08 이 바로 그 빈틈이었다.

## S-01 · S-02 — 행은 행으로 보낸다

원인은 한 곳이었다. 행인지를 전역 모드(`parentMode`)로 갈라서, 페이지 모드 볼트가 자동
발견한 DB 의 행(`db-row`)이 페이지 경로로 밀렸다. 페이지 경로는 속성으로 제목만 보내고
나머지 frontmatter 를 본문 첫머리 YAML 블록으로 끼운다.

수정(`fix/db-row-property-push`): 행인지는 레코드가 정하고, 행은 `pushRowUpdate` 로 간다.

## S-08 원인 — 새 하위 트리의 자식이 증분 pull 에서 빠진다

S-03 실측 중 재현했다. 새로 만든 `S-03 프로브` 와 그 자식 페이지(둘 다 09:47 생성)가 한 번의

원인(코드): `detectRemoteChangesIncremental` 은 추적되지 않은 페이지를 부모가 루트거나 이미
추적 중일 때만 받는다(`isTrackedParent`). 같은 실행에서 새로 받는 부모는 감지가 끝날 때까지
추적 전이라 그 자식이 빠진다. 다음 실행의 조회 창(마지막 pull − 15분)은 그 자식의 수정
시각보다 뒤라 다시 보이지 않는다 — 원격에서 자식을 고치기 전까지 영영 빠진다.
`fix/incremental-new-subtree` 에서 같은 실행의 새 부모도 부모로 인정하게 고친다.

수정: 감지 단계에서 추적되지 않은 새 페이지를 부모와 함께 모은 뒤, 부모가 루트 · 추적 중이거나
**이번에 함께 받기로 한 새 페이지** 이면 받는다. 한 번 훑어서는 깊은 것부터 오는 순서(손자 →
자식 → 부모)를 못 받으므로 더 받을 것이 없을 때까지 되풀이한다. 루트 밖(추적하지 않는 부모
아래)의 새 페이지는 여전히 받지 않는다.

- 단위: `tests/sync/pull-incremental-new-subtree.test.ts` 2 — 손자 · 자식 · 부모 · 루트 밖

빠진다(`last_pull_at` 을 끝난 시각으로 올린다) — `fix/pull-watermark` 로 나눈다. 검색 색인
지연이 조회 창(15분)보다 길면 빠지는 경우는 주기적 전체 대조(Phase A)가 잡는다.

## 기준 시각 — 받지 못한 변경이 다음 증분 조회에서 빠진다

S-08 을 고치며 같은 계열의 빈틈을 더 찾았다. 증분 pull 은 `last_pull_at − 15분` 이후에 고친
페이지만 search 로 받는데, `last_pull_at` 을 pull 이 **끝난** 시각으로 적었다. 그래서 이번
실행이 받지 못한 변경 — 재시도까지 실패 · 취소(플러그인 「동기화 취소」)로 건너뜀 · 경로를
좁힌 pull(`--path`)의 범위 밖 — 과 15분보다 긴 pull 도중의 원격 편집이, 다음 pull 이 15분 넘게
뒤에 오면 창 밖으로 밀려 원격에서 다시 고치기 전까지 빠졌다. `status` 는 push 도 올리는
`last_sync_at` 으로 조회해 pull 이 받을 변경을 「없음」 으로 보고할 수 있었고, pull 도
`last_pull_at` 이 없으면 `last_sync_at` 으로 대신해 push 만 한 볼트의 첫 pull 이 그 전에
원격에만 있던 페이지를 받지 못했다.

수정(`fix/pull-watermark`, ADR-010): pull 을 시작한 시각을 적고, 받지 못한 변경이 있으면 그중
가장 이른 수정 시각으로 묶는다. 경로를 좁힌 pull 은 옮기지 않는다. 기준 시각은 `last_pull_at`
뿐이고 pull · status 가 같은 규칙(`incrementalWatermark`)을 읽는다.

- 단위: `tests/sync/pull-watermark.test.ts` 10 — 조회 시각을 지키는 가짜 search 와 고정 시계.
  7개가 수정 전 코드에서 실패한다(「expected +0 to be 1」 × 5 · status 「expected [] …」 ·
  push 만 한 볼트 「expected undefined …」).
- 불변식(실 Notion) 15/15 · 151초.
- 실데이터 E2E (프로브 볼트, 빌드 `3a66a59` + 이 브랜치):

  | 단계                                    | 시각(UTC) | 결과                                                                  |

## S-04 — DB 폴더는 DB 다

원인(코드): push 가 바뀐 파일마다 조상 폴더를 모두 «폴더 페이지» 로 만들었다(`ensureFolderPage`).
폴더가 무엇인지 — 페이지의 폴더 · DB 폴더 · DB 를 품은 페이지의 폴더 — 를 가리지 않아, 자동
발견 DB 의 행 하나만 고쳐도 DB 폴더(`X/DB`)와 DB 를 품은 폴더(`X/B/…` 의 `B`)가 Notion 에 빈
페이지로 생겼다. DB 폴더에 새로 만든 노트는 행이 아니라 그 빈 페이지 아래의 페이지(본문에 속성
YAML)가 됐다. QA 프로브의 `QA-과제-DB` 빈 페이지(`…35c0`)가 그 흔적이다.

수정(`fix/db-folder-page`):

| 무엇                            | 규칙                                                                                                                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 폴더의 자리(`folder-container`) | DB 폴더(설정 · 자동 발견) → DB. 아니면 폴더 노트 `F/F.md` → 폴더 페이지 레코드 `F` → 형제 페이지 `F.md`(DB 를 품은 페이지 · 행의 하위 폴더) 순. 없으면 자리 없음 |
| 먼저 만들 폴더                  | 새로 만들거나 옮기는 «페이지» 의 조상뿐. 행은 DB 에 들고, 이미 있는 페이지의 갱신 · 삭제는 부모를 쓰지 않는다                                                    |
| DB 폴더의 새 노트               | 그 DB 의 행. 속성은 DB 스키마의 속성으로(없는 키는 건너뛰고 알림), 본문에 YAML 없음. 행 갱신(S-01)과 같은 규칙                                                   |
| 행 생성 WAL                     | 페이지와 같이 요청 앞에 적는다. 적용됐는지 모르고 끝나면 DB 에서 같은 제목의 짝 없는 행(휴지통 제외)을 찾아 입양하고 로컬 내용으로 맞춘다                        |

## S-11 — 옮기고 이름을 바꾼 노트

원인(코드): 변경 감지가 이름 변경을 `moved` 로 짝지어도 push 의 `pushMove` 는 레코드를 «새»
경로로 찾아 못 찾고 끝났다 — 그런데 `updated` 로 세어 매 push 가 같은 이름 변경을 다시
보고했다. 다른 폴더로 옮기면 부모를 `pages.update({ parent })` 로 보냈는데 Notion 은 이 필드를
무시한다. 이름과 내용을 함께 바꾸면 짝을 못 찾아 새 페이지를 만들었고, 옮긴 뒤 push 전에 pull

Notion 에서 바꾼 제목이 되돌아갔다.

## S-15 — 폴더 노트가 폴더의 페이지다

원인(코드 · 실측, 위 S-11 실측): push 가 풀 전에 새 파일의 조상 폴더를 모두 폴더 페이지로
만들어, 같은 push 의 새 폴더 노트가 그 아래 같은 제목의 자식이 됐다. 형제는 처리 차례에 따라 두
부모로 갈렸고, 다음 push 가 폴더 레코드를 지워 그다음 pull 이 폴더 페이지를 `(id)` 파일로 받았다.
폴더 노트를 나중에 추가해도 같은 두 겹이 생겼다.

수정(`fix/folder-note-create`, ADR-012):

| 무엇                                    | 규칙                                                                                                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 새 폴더 + 새 폴더 노트                  | 폴더 페이지를 만들지 않는다. 폴더 노트를 풀보다 먼저 폴더가 설 자리(부모 폴더의 자리 · 루트)에 올리고, 같은 폴더의 노트 · 하위 폴더는 그 아래로 (`prepareFolders`)      |
| push 가 만든 폴더 페이지 + 새 폴더 노트 | 폴더 레코드를 폴더 노트 경로로 옮겨 적고 그 페이지의 갱신으로 넘긴다(`adoptFolderPage`) — 새 페이지 없음 · 본문 교체 · 하위 페이지 유지 · 제목은 frontmatter `title` 만 |
| 이어받을 수 없음                        | 폴더 레코드의 이동 WAL · 폴더 노트의 생성 WAL 이 끝나지 않았으면 폴더 노트를 이유와 함께 실패로 — 새 페이지를 만들지 않는다. 다음 push 가 이어받는다                    |
| 폴더의 자리를 마련하지 못함             | 그 폴더 안의 노트 · 하위 폴더만 그 이유로 실패하고 push 는 계속한다. 부모 폴더의 자리가 없으면 루트에 만들지 않는다                                                     |
| 폴더 레코드 정리(`repairFolderRecords`) | 587b405 이전의, 루트를 맨 위 폴더의 페이지로 적은 레코드만 지운다. dry-run 은 지우지 않는다                                                                             |

## S-16 · S-17 — push 가 만든 폴더 페이지는 폴더다

원인(코드, 위 표): pull 이 폴더 레코드(push 가 만든 폴더 페이지, 경로 `A/B`)를 폴더 노트 파일
(`A/B/B.md`)처럼 다뤘다. 고치며 같은 원인의 경로를 둘 더 찾았다.

- **원격 삭제.** `pullDelete` 가 폴더 경로를 파일처럼 지운다. 플러그인은 설정과 무관하게
  `deleteSync: true` 이고(`obsidian-plugin/src/main.ts:262`), 그 어댑터의 `deleteFile` 은
  `vault.trash` 로 폴더도 받아 올리지 않은 노트까지 폴더째 휴지통에 넣는다. CLI 어댑터는 `unlink`
  가 실패해 조용히 넘어간다.
- **DB 폴더 자리의 v0.3 폴더 페이지.** v0.3 이 DB 폴더에 만든 빈 페이지(프로브
  `QA-A 디자인 전수 프로브/QA-과제-DB` `…35c0`)도 폴더 레코드다. S-16 규칙을 그대로 쓰면 그 아래
  페이지와 그 본문이 DB 폴더에 파일로 들어가 행처럼 놓인다.

실측 중 찾고 이 브랜치에서 고치지 않은 것:

- **새 자식의 색인 지연** (r1 · r4). 부모 폴더 페이지의 수정은 바로 보이는데 새 페이지는 search
  색인에 늦게 들어와 그 pull 이 아니라 다음 pull 이 받았다(안전창 15분 안). 부모가 바뀐 것을 보면
  그 자식 목록에서 새 페이지를 바로 찾을 수 있다 — `feature/fast-change-detection`.
- **진행 줄의 `~ updated`** (r1 · r4). 시각만 맞춘 폴더도 진행 줄에는 `~ … updated` 로 찍히고
  요약은 `no changes` 다. 받은 것이 없는 보통 페이지도 같다 — `feature/sync-status-api`.
- **pull 이 쓴 파일의 끝 줄바꿈** (r2). 로컬 원본 `…한다.\n` 을 되살리면 `…한다.` 가 된다. push 는
  차이로 보지 않지만(dry-run 0) 변경 목록에는 차이로 보일 수 있다 — Phase 2 변환 왕복.
- **pull 시간 편차.** 같은 볼트의 변경 없는 pull 이 6.4~17.3초였다. 따로 재지 않았다.
- **플러그인 deleteSync 고정** (코드로만). 폴더 레코드 삭제는 막았지만, 전체 대조가 순회 마감과
  색인 지연으로 페이지를 놓치면 보통 노트도 «원격에서 사라짐» 으로 지울 수 있다 —
  `fix/delete-sync-db-rows`(S-12)에서 지우기 전에 원격을 다시 확인하는 쪽으로 본다.
