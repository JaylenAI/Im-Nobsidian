## F25 — linked view 컨테이너 이중 등록 (steady churn 의 진범)

### 원인

신 API(2025-09-03)에서 **원본이 공유 범위에 있으면 linked view 컨테이너도
`databases.retrieve` 가 성공하고 `data_sources` 가 채워져 온다** — 응답 필드가
원본과 완전 동일해(is_inline·data_sources 등) 응답만으로는 구분 불가(실측).
queryable 판정만 하던 발견 로직이 컨테이너 8개를 원본처럼 캐시에 등록했고,
`register()` 의 knownIds 게이트 탓에 한번 들어가면 `--force` 로도 재판정 불가.

같은 data source 를 2~4개 config 가 각각 pull → 행이 misplaced 판정 →
매 pull 마다 config 큐 순서대로 폴더 릴레이 재배치(rehome) → 마지막 config 가
항상 승자라 "무이동·바이트 동일"로 관측됐다. 카운트 완전 분해:
습관 3행×4 + 하루루틴 1×2 + 할일 16×2 + 스위치온 5×2 + 프로필861 5×2 = **66**
(매 pull "66 updated" 실측과 정확 일치, 유니크 30행).

### 수정 (3층)

1. **발견 단계** (`client.getDatabaseSyncability`): 첫 data source 의
   `parent.database_id` ≠ 자신이면 `linkedOriginalDbId` 반환(+1콜/발견) →
   `buildDiscoveredDbConfig` 가 kind `linked` 로 기존 linkedMap 인프라에 위임
2. **pull 단계 자가 치유** (`databaseSyncer.pullDatabase`): query 결과 첫 행의
   parent 로 판정(추가 API 0회). 원본 폴더를 아는 경우에만 행 소유를 양보하고
   `.base` 를 원본 폴더 필터로 재지향 + orchestrator 가 캐시에서 제거·매핑 기록
3. **폴백**: 원본 미공유 시 컨테이너가 행의 유일 통로이므로 기존대로 행 소유

## F27 — page mention 신형 URL 호스트 미해소

- **증상**: 콜아웃 breadcrumb 의 `<mention-page url="...">제목</mention-page>` 가
  위키링크로 변환되지 않고 raw 태그로 잔존(audit 결함 `mention-page`, 2파일 4건 —
  볼트 전체 raw 태그는 18건)
- **원인**: pull 방향 변환 정규식이 호스트를 `notion.so/<id>` 로만 봤는데, 실제
  API 가 내려주는 URL 은 전부 신형 `app.notion.com/p/<id>` 형식(clean-slate 18건 100%).
  M6(2026-06-02)에서 self-closing/라벨형 두 형태는 통합했으나 호스트 변형은 미대응
- **수정**: `convertPageMentions` 정규식을 `(?:[a-z]+\.)?notion\.(?:so|com)\/(?:p\/)?`
  로 일반화 — `www.notion.so/<id>`·`notion.so/<id>`·`app.notion.com/p/<id>` 모두 흡수.
  id 는 항상 32 hex 라 오탐 위험 낮음. 회귀 테스트 2건(신형 단독 + 신형/구형 혼재)
- **교훈**: Notion URL 호스트/경로는 워크스페이스·API 버전마다 다르다 — id(32hex)를
  앵커로 잡고 호스트는 관대하게 매치해야 미래 변형에도 견딘다
