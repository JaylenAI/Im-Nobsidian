# 2026-07-27 — R9: "pull 이 멈춘다"의 근본 원인 (재시도가 rate limit 슬롯을 점유) · R10: 끊긴 링크와 자기별칭의 네 갈래

R8(빈 칼럼 보존) 머지 후 지정 볼트에서 268페이지 전체 E2E 를 재검증하던 중,
`nobsi pull` 이 진행 로그를 멈춘 채 프로세스만 살아 있는 현상을 재현했다.
브랜치: `fix/download-timeout-guard`(R9a) · `feature/pool-item-timeout`(R9b) ·
`fix/retry-observability`(R9c).

## 증상

```
+ 어떤 노트.md [158/268] created
(이후 아무 출력 없음 — 17분 경과, 프로세스 살아 있음)
```

정지 지점이 **비결정적**이었다(1차 102/268, 2차 158/268). 관측값:

| 항목                  | 실측                                                           |
| --------------------- | -------------------------------------------------------------- |
| 프로세스 상태         | `S (sleeping)`, wchan `ep_poll`                                |
| CPU                   | utime 1301 / stime 121 tick — 샘플 간 **완전 정지**(≈13s/17분) |
| 네트워크 소켓         | fd 24개 중 **0개** (/dev/null·파이프·eventpoll·sync.db 뿐)     |
| stdout                | `writableLength: 0, needDrain: false` — 백프레셔 아님          |
| `_getActiveHandles()` | `{ Socket: 2 }`, `_getActiveRequests()` `[]`                   |

## 오독을 만든 API

처음에는 `_getActiveHandles()` 를 훑어 "대기 중인 타이머 없음"으로 결론냈다. **틀렸다.**
`_getActiveHandles()` 는 타이머를 보고하지 않는다. 같은 프로세스에 `process.getActiveResourcesInfo()`
를 물었더니:

```json
["PipeWrap", "PipeWrap", "Timeout", "Timeout", "Timeout"]
```

**Timeout 3개 = `advanced.concurrency` 기본값 3.** 워커 전원이 타이머 위에서 자고 있었다.
이어서 `Runtime.queryObjects` 로 살아 있는 `Timeout` 인스턴스를 전부 떠서 `_onTimeout`
소스를 읽어 어느 타이머인지까지 특정했다(진단 절차는 아래 §진단 방법).

## 근본 원인 — 백오프가 슬롯을 쥔 채 잔다

`NotionClient.withRateLimit` 이 이 모양이었다:

```ts
await this.sema.acquire();
try {
  ...
  return await this.executeWithRetry(fn); // ← 재시도 + sleep 전체가 이 안에서 돈다
} finally {
  this.sema.release();
}
```

`executeWithRetry` 는 실패 시 최대 60초(`MAX_RETRY_AFTER_MS`)를 자고 다시 던지기를
`maxRetries`(기본 5)회 반복한다. 즉 **재시도 1건이 rate limit 슬롯 하나를 최대 5분
점유**한다. 동시성 기본값이 3이므로 불운한 요청 3건이면 클라이언트 전체가 멈춘다 —
페이지 처리와 무관한 모든 API 호출까지 함께.

여기에 두 번째 문제가 겹쳤다: **재시도는 로그를 한 줄도 남기지 않았다.** 그래서 겉으로는
죽은 프로세스와 구분되지 않았고, 실제로 필자도 "무한 정지"로 오진했다. (아이러니하게도
`extractRetryAfter` 의 주석은 "재시도 대기는 실패해도 로그에 아무 흔적이 남지 않는다"고
이미 적어 두고 있었다.)

## 수정 (R9c)

```ts
for (let attempt = 0; ; attempt++) {
  await this.sema.acquire();
  try {
    await this.waitForTurn();          // 전역 쿨다운 + 최소 요청 간격
    this.lastRequestTime = Date.now();
    return await fn();
  } catch (error) {
    if (!isRetryable(error) || attempt >= this.maxRetries) throw error;
    backoffMs = ...;
    if (retryAfterMs !== null) this.cooldownUntil = ...;   // 429 = 전원 대기
    getLogger().warn(`Notion API 재시도 ${attempt + 1}/${this.maxRetries} — ...`);
  } finally {
    this.sema.release();               // ← 자기 전에 놓는다
  }
  await sleep(backoffMs);              // ← 슬롯 밖에서 잔다
}
```

- **백오프는 슬롯을 놓은 뒤.** 한 요청의 불운이 남을 막지 못한다.
- **429 는 `cooldownUntil` 전역 게이트.** rate limit 은 요청 하나가 아니라 워크스페이스
  전체에 걸린 신호다. 슬롯을 붙잡아 남을 막는 대신, 다 같이 보는 시각으로 함께 쉰다 —
  429 를 맞은 요청만 기다리게 두면 나머지 슬롯이 곧바로 다시 두드려 429 를 재생산한다.
- **모든 재시도를 경고로.** `Notion API 재시도 1/5 — 3750ms 대기 (status 429 · rate_limited · ...)`

## 같은 증상의 다른 경로 (R9a·R9b)

정지 원인을 쫓다가 같은 증상을 만들 수 있는 두 경로를 함께 막았다.

### R9a — 첨부 다운로드에 상한이 없었다

`image-handler.ts` 에는 다운로드 시간 상한 가드가 주석까지 달려 있었는데,
`file-handler.ts:141` 은 **맨 `await fetch(url)`** 이었다. 같은 로직이 두 벌 존재하면
한쪽만 빠지는 일이 실제로 일어난다는 표본. 상한 없는 `fetch` 는 타이머도 소켓도 없이
영원히 매달릴 수 있고, 그 사이 세마포어를 쥐고 있다.

공용 `utils/download-fetch.ts` 로 뽑아 양쪽이 위임하게 하고, 설정 한 개
(`advanced.mediaDownloadTimeoutMs`, 기본 300초)로 오케스트레이터가 둘 다 배선한다.
회귀 테스트 9건은 **가드를 지우면 테스트가 hang 으로 드러나도록** 설계했다(끝나지 않는
`fetch` 목 사용) — 실패가 아니라 정지로 드러나야 같은 결함을 다시 못 만든다.

### R9b — 합성 경로 전체에는 상한이 없었다

호출 단위 상한(API 30초, 다운로드 300초)이 다 있어도 "페이지 1건 처리"라는 합성 경로는
덮이지 않는다. `utils/deadline.ts` 의 `withDeadline` 으로 pull/push 각 1차·재시도 루프
4곳을 감쌌다(`advanced.itemTimeoutMs`, 기본 30분). 무한 정지가 **유한한, 그리고 보고되는
실패**로 바뀐다:

```
시간 상한 초과(1800초): pull AI Engineer/Project/어떤 노트.md
```

`Promise.race` 는 취소가 아니므로 상한을 넘긴 작업은 프로세스 종료까지 남는다 —
`utils/deadline.ts` 헤더에 그대로 적어 두었다. **한계 있는 누수를 무한 정지와 맞바꾼
것**이고, 그 교환은 의도된 것이다.

## R9d — 고친 줄 알았던 것이 실은 죽은 코드였다

R9c 를 배포하고 라이브 E2E 를 다시 돌리자 이번엔 **재시도가 로그에 보였다**. 그런데
기록된 대기값이 이랬다:

```
812, 729, 667, 543, 1408, 1251, 1630, 3072, 2742, 2981, 5517 (ms)
```

전부 `retryBaseDelayMs · 2^attempt · (0.5~1.0)` 격자 위에 정확히 떨어진다. 즉 **429 를
11번 맞는 동안 `Retry-After` 경로는 한 번도 타지 않았다.** 노션이 429 에 `Retry-After`
를 안 실어 줄 리는 없으니 우리 쪽이 못 읽는 것이다.

SDK 를 열어 확인했다:

| 위치                         | 내용                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| `build/src/errors.d.ts:79`   | `readonly headers: SupportedResponse["headers"];`           |
| `build/src/errors.js:221`    | `headers: response.headers` — fetch 응답 헤더 **원본 전달** |
| `build/src/fetch-types.d.ts` | `SupportedResponse.headers: unknown`                        |

`headers` 는 fetch 의 **`Headers` 인스턴스**다. `Headers` 는 인덱스 접근에 항상
`undefined` 를 준다 — 값은 `.get()` 으로만 나온다. 그런데 `extractRetryAfter` 는
`headers?.["retry-after"]` 였다. **함수 전체가 죽은 코드였다.**

타입이 `unknown` 이라 타입체커도 못 잡았고, 테스트 7건이 전부 통과하고 있었다 —
테스트가 평범한 객체(`{ "retry-after": "3" }`)를 넘겼기 때문이다. 목이 실물과 다른
모양이면 테스트는 **버그를 증명하는 도구가 아니라 은폐하는 도구**가 된다. 그래서
회귀는 실제 `new Headers(...)` 로 잠그고, 첫 단언을 이렇게 뒀다:

```ts
const headers = new Headers({ "Retry-After": "3" });
// 이 단언이 이 테스트의 존재 이유다 — 인덱스로는 값이 안 나온다.
expect((headers as unknown as Record<string, string>)["retry-after"]).toBeUndefined();
expect(extractRetryAfter({ headers })).toBe(3000);
```

봉합은 두 갈래다.

1. **`readHeader(headers, name)`** — `Headers`·`Map`(둘 다 `get(name)` 계약)·평범한
   객체(대소문자 무관) 세 모양을 모두 읽는다. 커스텀 `fetch` 를 주입하면 실제로 객체나
   `Map` 이 올 수 있다.
2. **쿨다운 판정 기준 교정** — `retryAfterMs !== null` → `isRateLimited(error)`(status 429).
   헤더 유무로 판단하면 게이트웨이가 헤더를 떼어먹는 순간 쿨다운이 통째로 사라진다.
   429 인지 아닌지는 상태 코드가 답할 문제지 헤더가 답할 문제가 아니다.

뮤테이션(옛 구현 복원)으로 **6건 실패**를 확인했다 — 통과만으로는 잠금의 증거가 되지
않는다. R9c 의 기존 쿨다운 테스트도 헤더를 실물 `Headers` 로 바꾼 뒤 옛 구현에서
빨간불이 됐다. 그 테스트는 그동안 초록불이면서 아무것도 지키지 않고 있었다.

> **교훈**: 값을 못 읽는 버그는 예외를 던지지 않는다. `undefined` 로 조용히 폴백해
> "동작하는 것처럼 보이는 다른 경로"로 흘러갈 뿐이다. 폴백 경로가 그럴듯할수록
> (여기서는 지수 백오프) 더 오래 숨는다. **라이브 로그의 수치가 어느 코드 경로에서
> 나온 값인지 역산해 보는 습관**이 유일한 탐지기였다.

## R9e·R9f — 상한을 걸어 놓고 다수 경로를 빼먹었다

R9b 는 "항목 1건 상한"을 도입하면서 오케스트레이터의 페이지 루프 4곳
(`orchestrator.ts:297·322·585·619`)에 `withDeadline` 을 걸었다. 그런데 지정 볼트의
파일 구성을 세어 보면:

| 항목        | 개수 | R9b 시점 상한 |
| ----------- | ---- | ------------- |
| 일반 페이지 | 258  | ✅ 있음       |
| DB 행       | 629  | ❌ 없음       |
| 첨부        | 다수 | ❌ 없음       |

**보호받지 못하는 쪽이 오히려 다수였다.** "상한을 도입했다"는 사실이 "상한이 걸려
있다"는 착각을 만든 전형적인 경우다.

### R9e — DB 행

`DatabaseSyncer` 의 pull·push 행 루프. pull 은 `pullDatabasePage` 호출이 두 분기에
흩어져 있어 먼저 단일 호출 지점으로 정리한 뒤 상한을 걸었고, push 는 루프 본문이
100여 줄 인라인이라 `pushDatabaseRow` 로 떼어냈다.

떼어내면서 **카운터 증가·실패 기록을 전부 호출부로 옮겼다.** 상한에 걸린 행이
`created++` 는 하고 `upsert` 는 못 한 채 끊기는 상태를 구조적으로 불가능하게 만들기
위해서다. 대신 결과는 판별 유니온으로 돌려준다:

```ts
type PushRowOutcome =
  | { action: "created" }
  | { action: "updated" }
  | { action: "skipped" }
  | { action: "failed"; failure: FailedOperation };
```

`failed` 를 따로 둔 이유는 본문 push 실패만 의미가 다르기 때문이다 — 레코드를
`error` 로 내려 해시 전진을 막아야 하고(안 그러면 다음 push 에서 스킵되어 변경이
영원히 전달 안 됨), operation 도 `create` 가 아니라 `update` 다. 리팩터링이 이
의미를 바꾸지 않았는지는 별도 테스트로 못 박았다.

### R9f — 첨부

`FileHandler` 의 업로드 루프가 `pushFilesForFolder` 와 `pushAllFiles` 두 곳에 **같은
코드로** 나뉘어 있었고 둘 다 상한이 없었다. R9a 에서 image/file 핸들러의 같은
구조 때문에 이미 한 번 데였으므로, 이번엔 상한만 두 번 붙이는 대신 공통 본문을
`pushSingleFile` 하나로 합쳤다. 변경 없음 판정·슬롯·상한·실패 격리가 이제 한 곳에만
있다.

업로드에 상한이 필요한 이유는 다운로드와 같다: 호출 1건은 SDK 가 30초로 끊지만
멀티파트는 **파트 수만큼 호출이 늘어나는 합성 경로**라 전체로는 여전히 무한대다.

### 왜 DB 단위·페이지 단위에는 안 거는가

`pullAll` 의 `for (const dbConfig of databases)` 에는 상한을 걸지 않았다. 500행짜리
DB 가 오래 걸리는 것은 정지가 아니라 정상이고, 여기에 상한을 걸면 정상 작업을
끊는다. **상한의 올바른 입도는 "사용자가 세는 단위" 1건**이다 — 페이지·행·첨부.
그 아래(호출)는 SDK·다운로드 상한이, 그 위(DB·전체)는 아무것도 걸지 않는다.

### 사각지대 전수 확인

`grep -rn "withDeadline(" packages/core/src packages/cli/src` 로 보호받는 합성 경로가
6곳(페이지 pull·push 각 2 + DB 행 pull·push)임을 확인하고, `sync/`·`notion/` 의
`for...of` 루프를 전수로 훑어 네트워크 작업을 도는 나머지 루프가 모두 이 6곳 **안쪽**
이거나(첨부·이미지 처리는 페이지 처리 내부) 순수 메모리 연산임을 확인했다. 유일한
예외가 `fileHandler.pushAllFiles()` 였고 그것이 R9f 다.

## 진단 방법 (다음에 또 멈추면)

1. `pgrep -af nobsi` 로 PID 확인. `/proc/<pid>/status`(State/Threads/VmRSS),
   `cut -d' ' -f14,15 /proc/<pid>/stat`(CPU tick 2회 샘플), `ls -l /proc/<pid>/fd`.
2. `kill -USR1 <pid>` → 인스펙터가 127.0.0.1:9229 에 열린다.
3. CDP 로 붙어 **`process.getActiveResourcesInfo()`** 를 읽는다. `_getActiveHandles()`
   만 보면 타이머를 놓친다.
4. 타이머 정체가 필요하면 `Runtime.queryObjects` 에 `Timeout.prototype` 을 넘겨
   살아 있는 인스턴스를 전부 떠서 `_idleTimeout`/`_onTimeout.toString()` 을 읽는다.
   `_destroyed`·`hasRef()` 로 거른다 — GC 안 된 잔해와 `AbortSignal.timeout`(unref)이
   섞여 있다.

## 세 겹 상한 정리

| 상한                              | 대상                            | 기본값 |
| --------------------------------- | ------------------------------- | ------ |
| `advanced.timeoutMs`              | Notion API 요청 1건             | 30초   |
| `advanced.mediaDownloadTimeoutMs` | 미디어·첨부 다운로드 1회        | 300초  |
| `advanced.itemTimeoutMs`          | 페이지·DB 행·첨부 1건 전체 처리 | 30분   |

`itemTimeoutMs` 의 적용 범위가 R9e·R9f 로 넓어졌다. 설정 항목은 그대로다 — 사용자가
"항목 1건"이라고 이해하는 것과 코드가 상한을 거는 단위가 이제 일치한다.

| 대상 | 가드 제거 시                                    |
| ---- | ----------------------------------------------- |
| R9d  | 6건 실패(즉시)                                  |
| R9e  | 4건이 vitest 타임아웃(20.0초) — 정상 2건은 통과 |
| R9f  | 3건이 테스트 타임아웃(15.0초) — 기존 14건 통과  |

핵심 잠금 4건:

- **슬롯 반납**: 동시성 1에서 앞 요청이 백오프 중일 때 뒤 요청이 **먼저** 끝나야 한다.
  예전 구현에서는 순서가 뒤집힌다.
- **전역 쿨다운**: 429 직후 들어온 무관한 요청도 쿨다운 만료까지 기다려야 한다.
- **실 `Headers` 읽기**: 인덱스 접근으로는 값이 안 나온다는 것까지 단언으로 박았다.
- **지정 대기 존중**: 지수 백오프 상한(10ms)보다 훨씬 긴 `Retry-After: 0.3` 을 주고
  실제로 300ms 이상 기다리는지 시간으로 검증한다 — 못 읽으면 즉시 끝나 빨간불이 된다.

## R10 — 페이지 링크가 끊긴 채 남던 네 갈래

R9 봉합 후 지정 볼트를 비우고 받은 1193개 파일을 눈으로 훑다가, 본문에 `[[notion:26d2…]]`
라는 **사람이 읽을 수 없는 위키링크**가 그대로 남아 있는 것을 발견했다. 옵시디언은 이걸
`notion:26d2…` 라는 이름의 노트를 가리키는 끊긴 링크로 그리고, 클릭하면 그 이름의 빈
노트를 만들자고 한다 — 정보 보존이 아니라 볼트 오염이다.

한 갈래를 고칠 때마다 실볼트를 다시 받아 재니 다음 갈래가 드러났다. A → B 는 예상했지만
C 와 D 는 **측정이 알려 줬다** — 고쳤다고 믿은 수치가 안 움직이거나(C), 고치고 나서야
새 수치가 보였다(D).

브랜치: `fix/notion-id-link-alias`(R10-A) · `fix/notion-id-link-fallback`(R10-B·C·D).

### 배경 — 해소가 두 지점에서 일어난다

`[[notion:<id>]]` 는 최종형이 아니라 **중간형**이다. pull 1차 변환이 page mention 과 라벨
달린 Notion 페이지 링크를 전부 이 형태로 환원해 두면, id → 볼트 경로 역조회가 최종
`[[제목]]` 을 만든다. 그 역조회가 두 지점에서 돈다:

1. **변환 시점** — 페이지 하나를 마크다운으로 만들 때 (`resolveNotionIdWikilinks`)
2. **pull 마감** — 이번 pull 이 기록한 파일 전부를 다시 훑는 후처리 (`resolveNotionLinks`)

2번이 따로 필요한 이유는 **정방향 참조**다. A 가 B 를 가리키는데 B 가 같은 pull 의
*나중*에 만들어지면, A 를 변환하던 1번 시점엔 B 가 상태 DB 에 없어 해소가 실패한다.

### R10-A — 후처리가 별칭 형태를 아예 못 봤다

후처리는 공용 함수를 부르지 않고 **자기 정규식**을 들고 있었다:

```ts
content.replace(/\[\[notion:([a-f0-9-]+)\]\]/g, ...)   // 별칭 부분이 없다
```

`[[notion:<id>|별칭]]` 은 이 패턴에 걸리지 않는다. 결과: 정방향 참조 + 별칭이 겹친 링크는
**대상이 볼트에 실재하는데도** 영영 끊긴 채 남는다. 지정 볼트 실측이 그대로 갈라졌다 —
별칭 없는 형태는 13건 전부 해소, 별칭 형태는 대상이 볼트에 있는 2건이 미해소
(`__e2e_probe__/R2-link-embed.md` → `T24 대상 (1).md`, `T2-target.md`).

R9a(image/file 핸들러)·R9e(페이지/DB 행)·R9f(업로드 루프 2곳)와 **같은 결함군**이다 —
같은 계약이 두 경로에 있고 한쪽만 갱신이 빠졌다. 게다가 이 두 패스는 2026-06-02 Phase 1
에서 **M4(단일/후처리 패스 위키링크 불일치)** 로 이미 한 번 어긋난 적이 있다. 그때는
어긋난 사례를 맞췄고 경로는 둘로 남겨 뒀다 — 그래서 재발했다. 그래서 이번에도 사례를 고치는 대신
경로를 하나로 합쳤다: `converter/notion-id-links.ts` 를 유일한 해소 지점으로 만들고,
후처리는 그 함수를 부른다. 곁들여 두 가지를 같이 잠갔다.

- **id 표기 두 종류**를 다 받는다. 변환기는 압축형(32 hex), 상태 DB·API 는 하이픈형(36자)을
  준다. 한쪽만 받으면 다른 쪽 경로의 링크가 통째로 미해소로 남는다.
- **`[[X|X]]` 를 만들지 않는다.** 별칭이 대상 제목과 같으면 버린다. 뜻은 `[[X]]` 와 같은데,
  push 의 분기(별칭 유무로 mention/URL 링크를 가른다)를 헛돌게 해 mention 이어야 할 링크를
  평범한 URL 링크로 내보낸다.
  > 이 접기를 실볼트 자기별칭 45건의 처방으로 적었으나 **틀렸다**. 재빌드 후 실측에서
  > 45건이 그대로 남았고, 원인은 다른 경로였다 → R10-C. 여기 접기는 `[[notion:<id>|별칭]]`
  > 표기에만 걸린다.

### R10-B — 볼트 밖 페이지는 죽은 링크가 아니라 URL 로

해소를 다 시도해도 남는 것이 있다. 토큰이 접근 못 하거나 pull 대상이 아닌 페이지다.
지금까지는 중간형을 **그대로** 남겼는데, 이게 위의 끊긴 링크다. 실측 25건 / 16파일
(프론트매터 0건, 코드블록 안 0건).

같은 breadcrumb **한 줄 안에서** url 기반 링크는 이미 동작하는 `https://www.notion.so/<id>`
로 남아 있었다. 한쪽 경로만 죽은 링크를 만들던 비대칭이라 R10-A 와 같은 렌즈로 처리했다:

```ts
// 해소를 전부 시도한 뒤에만 부른다
degradeUnresolvedNotionIdWikilinks(content); // → [라벨](https://www.notion.so/<id>)
```

순서가 핵심이다. 격하를 해소보다 **먼저** 부르면 볼트에 실재하는 대상까지 외부 링크로
굳어 그래프뷰에서 끊긴다. 그래서 격하는 프론트매터 relation 해소까지 끝난 다음에만 돈다.

**왕복도 닫힌다.** 격하형이 Notion 에 실려 갔다가 다시 내려와도 1차 변환의
`NOTION_LABELED_PAGE_LINK_RE` 가 `[[notion:<id>|라벨]]` 로 환원하므로 id 가 살아 있고,
그 페이지가 나중에 볼트에 들어오면 그때 정식 위키링크로 해소된다. 라벨이 없던 mention 은
id 를 라벨로 쓰는데, 되돌아왔을 때 그 id 라벨을 **별칭으로 오인하지 않도록** 해소 쪽에서
되돌린다(`alias === compactId(id)` 이면 버린다). 안 그러면 `[[대상|26d2…]]` 로 굳는다.

한 가지는 **일부러 안 했다.** mention 라벨을 항상 별칭으로 보존하면(`rich-text-converter.ts:86`)
볼트 파일명이 Notion 제목과 다른 모든 링크가 `[[대상|다른 제목]]` 이 되고, push 가 이걸
별칭으로 읽어 mention 을 URL 링크로 격하시킨다. 이 볼트만 해도 dedup 접미사가 144건이라
대량 회귀가 된다. 바꾼 것은 **해소 실패 경로 하나뿐**이다.

### R10-C — 45건은 **세 번째** 경로였다

R10-A·R10-B 를 넣고 클린 슬레이트로 다시 pull 한 뒤 세 수치를 실측했다.

| 항목                | 전   | 후                | 판정    |
| ------------------- | ---- | ----------------- | ------- |
| `[[notion:…]]` 잔존 | 25건 | **0건**           | ✅      |
| notion.so URL 링크  | 0건  | **25건 / 16파일** | ✅      |
| `[[X\|X]]` 자기별칭 | 45건 | **45건**          | ❌ 무변 |

45건이 꿈쩍도 안 했다. 그 45건이 든 파일(`AI Engineer (1)/ETC/ETC.md` 등)을 열어 보니
breadcrumb 콜아웃이었고, 라이브 프로브로 Notion 원본 블록을 뜯어 보니 **page mention 이
아니었다**:

```
[callout] "Home" link=/p/36f13b18… + "  |  " + "ETC" link=/p/4c813b18… + …
```

라벨 달린 **상대 링크 텍스트 런**이다. 그래서 `[[notion:<id>]]` 중간형을 아예 거치지 않고,
후처리 안의 **다른** 정규식이 처리한다:

```ts
// orchestrator.ts — url 형 페이지 링크
content.replace(/\[([^\]]+)\]\(\/(?:p\/)?([a-f0-9]{32})...\)/g, (_m, text, id) => {
  return `[[${title}|${text}]]`; // ← 접기 없음
});
```

같은 함수 안에, 같은 계약을 이행하는 두 갈래가 나란히 있고 한쪽만 규칙이 빠져 있었다.
R10-A 가 고친 것 **바로 옆줄**이다. 세어 보니 이 접기 규칙은 네 곳에 복제돼 있었다 —
`notion-id-links.ts` · `enhanced-md-converter.ts` · `link-restore.ts` · 그리고 이 한 곳.
넷 중 하나가 빠진 것이니, 사례를 고치면 다섯 번째가 또 생긴다.

그래서 **위키링크를 뱉는 출구를 하나로 합쳤다** — `utils/wikilink-title.ts` 의
`formatWikilink(target, label?)`. 네 곳이 전부 이 함수를 부른다. 규칙은 한 줄뿐이다:
라벨이 없거나 대상과 같으면 `[[대상]]`, 다르면 `[[대상|라벨]]`.

빈 라벨(`""`)은 **접지 않는다**. `undefined` 도 `=== target` 도 아니라서 `[[대상|]]` 로
남는데, 이게 맞다 — `[](/p/<id>)` 같은 빈 라벨 링크를 `[[대상]]` 으로 바꾸면 원문에 없던
텍스트가 생겨 왕복이 안 닫힌다.

### R10-D — 격하도 한쪽 표기에만 걸려 있었다

R10-C 를 넣고 또 한 번 클린 슬레이트로 받아 실측했다. 세 수치는 다 맞았는데, 이번엔 재던
그물에 **네 번째 수치**가 걸렸다.

| 항목                      | 전   | 후                | 판정       |
| ------------------------- | ---- | ----------------- | ---------- |
| `[[notion:…]]` 잔존       | 25건 | **0건**           | ✅         |
| notion.so URL 링크        | 0건  | **25건 / 16파일** | ✅         |
| `[[X\|X]]` 자기별칭       | 45건 | **0건**           | ✅ R10-C   |
| 미해소 `/p/<id>` 상대링크 | —    | **89건 / 10파일** | ❌ 새 관측 |

상태 DB 와 대조해 성격부터 확정했다 — 89건의 대상 11개가 **전부** 상태 DB 에 없다(볼트 밖
페이지). 코드펜스 안은 0건이라 "일부러 남긴 예시 텍스트"도 아니다. 80건이 각주
(`[¹](/…?pvs=25#<blockId>)`)이고 9건이 순수 페이지 링크다.

그러니까 R10-B 가 고친 것과 **정확히 같은 상황**이다. 다만 표기가 다르다.

| 표기              | 해소 실패 시 | 옵시디언에서                        |
| ----------------- | ------------ | ----------------------------------- |
| `[[notion:<id>]]` | URL 로 격하  | 동작하는 링크 (R10-B)               |
| `[라벨](/p/<id>)` | **그대로**   | `p/<id>` 라는 없는 파일 → 끊긴 링크 |

R10-B 를 쓸 때 "한쪽 경로만 죽은 링크를 만들던 비대칭을 없앤다"고 적었는데, 없앤 건
비대칭의 **절반**이었다. 상대 url 표기의 해소는 오케스트레이터 안에 인라인으로 있었고
(R10-C 가 접기를 빠뜨린 바로 그 자리), 격하는 아예 없었다.

그래서 이번엔 사례가 아니라 **모듈 경계**를 고쳤다. `notion-id-links.ts` 가 표기별
해소·격하를 **한 쌍씩** 갖는다:

```
[[notion:<id>]]     resolveNotionIdWikilinks          degradeUnresolvedNotionIdWikilinks
[라벨](/p/<id>)     resolveNotionRelativePageLinks    degradeUnresolvedNotionRelativePageLinks
```

오케스트레이터에는 규칙이 한 줄도 남지 않는다 — 역조회 하나를 만들어 두 해소에 같이
넘기고, 격하는 배열을 돌린다. 표기를 하나 더 알게 되는 날 짝을 추가하면 되고, 한쪽만
추가하면 대칭 잠금이 잡는다.

**앵커는 살린다.** 89건 중 80건이 각주라, `#<blockId>` 를 버리면 각주 80개가 전부 같은
페이지 최상단으로 떨어져 각주 구실을 못 한다. 그래서 격하형은
`https://www.notion.so/<id>#<blockId>` 다. 대신 **해소** 쪽은 앵커를 예전처럼 버린다 —
Notion 블록 id 는 옵시디언 `[[노트#제목]]` 의 앵커가 아니라서 옮겨 붙이면 노트 안의
없는 제목을 가리키는 끊긴 링크가 된다.

고정점도 닫힌다. 앵커 없는 형태는 다음 pull 에서 `[[notion:<id>|라벨]]` 로 환원됐다가
R10-B 격하로 **같은 바이트**가 되고, 앵커 있는 형태는 환원 정규식이 id 뒤에 `)` 를
요구해 아예 매치되지 않는다. 어느 쪽이든 두 번째 pull 이 이 줄을 다시 건드리지 않는다.

덤으로 다섯 번째 복제도 하나 걷었다 — `resolveNotionIdWikilinks` 가 basename 을 직접
깎던 자리(`path.split("/").pop()…`)를 `wikilinkTitleFromPath`(M4 의 SSOT)로 바꿨다.
