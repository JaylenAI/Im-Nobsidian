# 2026-07-27 — R9: "pull 이 멈춘다"의 근본 원인 (재시도가 rate limit 슬롯을 점유)

R8(빈 칼럼 보존) 머지 후 지정 볼트에서 268페이지 전체 E2E 를 재검증하던 중,
`nobsi pull` 이 진행 로그를 멈춘 채 프로세스만 살아 있는 현상을 재현했다.
브랜치: `fix/download-timeout-guard`(R9a) · `feature/pool-item-timeout`(R9b) ·
`fix/retry-observability`(R9c).

## 증상

```
+ 어떤 노트.md [158/268] created
(이후 아무 출력 없음 — 17분 경과, 프로세스 살아 있음)
```

정지 지점이 **비결정적**이었다(1차 102/268, 2차 158/268). 관측값:

| 항목                  | 실측                                                           |
| --------------------- | -------------------------------------------------------------- |
| 프로세스 상태         | `S (sleeping)`, wchan `ep_poll`                                |
| CPU                   | utime 1301 / stime 121 tick — 샘플 간 **완전 정지**(≈13s/17분) |
| 네트워크 소켓         | fd 24개 중 **0개** (/dev/null·파이프·eventpoll·sync.db 뿐)     |
| stdout                | `writableLength: 0, needDrain: false` — 백프레셔 아님          |
| `_getActiveHandles()` | `{ Socket: 2 }`, `_getActiveRequests()` `[]`                   |

## 오독을 만든 API

처음에는 `_getActiveHandles()` 를 훑어 "대기 중인 타이머 없음"으로 결론냈다. **틀렸다.**
`_getActiveHandles()` 는 타이머를 보고하지 않는다. 같은 프로세스에 `process.getActiveResourcesInfo()`
를 물었더니:

```json
["PipeWrap", "PipeWrap", "Timeout", "Timeout", "Timeout"]
```

**Timeout 3개 = `advanced.concurrency` 기본값 3.** 워커 전원이 타이머 위에서 자고 있었다.
이어서 `Runtime.queryObjects` 로 살아 있는 `Timeout` 인스턴스를 전부 떠서 `_onTimeout`
소스를 읽어 어느 타이머인지까지 특정했다(진단 절차는 아래 §진단 방법).

## 근본 원인 — 백오프가 슬롯을 쥔 채 잔다

`NotionClient.withRateLimit` 이 이 모양이었다:

```ts
await this.sema.acquire();
try {
  ...
  return await this.executeWithRetry(fn); // ← 재시도 + sleep 전체가 이 안에서 돈다
} finally {
  this.sema.release();
}
```

`executeWithRetry` 는 실패 시 최대 60초(`MAX_RETRY_AFTER_MS`)를 자고 다시 던지기를
`maxRetries`(기본 5)회 반복한다. 즉 **재시도 1건이 rate limit 슬롯 하나를 최대 5분
점유**한다. 동시성 기본값이 3이므로 불운한 요청 3건이면 클라이언트 전체가 멈춘다 —
페이지 처리와 무관한 모든 API 호출까지 함께.

여기에 두 번째 문제가 겹쳤다: **재시도는 로그를 한 줄도 남기지 않았다.** 그래서 겉으로는
죽은 프로세스와 구분되지 않았고, 실제로 필자도 "무한 정지"로 오진했다. (아이러니하게도
`extractRetryAfter` 의 주석은 "재시도 대기는 실패해도 로그에 아무 흔적이 남지 않는다"고
이미 적어 두고 있었다.)

## 수정 (R9c)

```ts
for (let attempt = 0; ; attempt++) {
  await this.sema.acquire();
  try {
    await this.waitForTurn();          // 전역 쿨다운 + 최소 요청 간격
    this.lastRequestTime = Date.now();
    return await fn();
  } catch (error) {
    if (!isRetryable(error) || attempt >= this.maxRetries) throw error;
    backoffMs = ...;
    if (retryAfterMs !== null) this.cooldownUntil = ...;   // 429 = 전원 대기
    getLogger().warn(`Notion API 재시도 ${attempt + 1}/${this.maxRetries} — ...`);
  } finally {
    this.sema.release();               // ← 자기 전에 놓는다
  }
  await sleep(backoffMs);              // ← 슬롯 밖에서 잔다
}
```

- **백오프는 슬롯을 놓은 뒤.** 한 요청의 불운이 남을 막지 못한다.
- **429 는 `cooldownUntil` 전역 게이트.** rate limit 은 요청 하나가 아니라 워크스페이스
  전체에 걸린 신호다. 슬롯을 붙잡아 남을 막는 대신, 다 같이 보는 시각으로 함께 쉰다 —
  429 를 맞은 요청만 기다리게 두면 나머지 슬롯이 곧바로 다시 두드려 429 를 재생산한다.
- **모든 재시도를 경고로.** `Notion API 재시도 1/5 — 3750ms 대기 (status 429 · rate_limited · ...)`

## 같은 증상의 다른 경로 (R9a·R9b)

정지 원인을 쫓다가 같은 증상을 만들 수 있는 두 경로를 함께 막았다.

### R9a — 첨부 다운로드에 상한이 없었다

`image-handler.ts` 에는 다운로드 시간 상한 가드가 주석까지 달려 있었는데,
`file-handler.ts:141` 은 **맨 `await fetch(url)`** 이었다. 같은 로직이 두 벌 존재하면
한쪽만 빠지는 일이 실제로 일어난다는 표본. 상한 없는 `fetch` 는 타이머도 소켓도 없이
영원히 매달릴 수 있고, 그 사이 세마포어를 쥐고 있다.

공용 `utils/download-fetch.ts` 로 뽑아 양쪽이 위임하게 하고, 설정 한 개
(`advanced.mediaDownloadTimeoutMs`, 기본 300초)로 오케스트레이터가 둘 다 배선한다.
회귀 테스트 9건은 **가드를 지우면 테스트가 hang 으로 드러나도록** 설계했다(끝나지 않는
`fetch` 목 사용) — 실패가 아니라 정지로 드러나야 같은 결함을 다시 못 만든다.

### R9b — 합성 경로 전체에는 상한이 없었다

호출 단위 상한(API 30초, 다운로드 300초)이 다 있어도 "페이지 1건 처리"라는 합성 경로는
덮이지 않는다. `utils/deadline.ts` 의 `withDeadline` 으로 pull/push 각 1차·재시도 루프
4곳을 감쌌다(`advanced.itemTimeoutMs`, 기본 30분). 무한 정지가 **유한한, 그리고 보고되는
실패**로 바뀐다:

```
시간 상한 초과(1800초): pull AI Engineer/Project/어떤 노트.md
```

`Promise.race` 는 취소가 아니므로 상한을 넘긴 작업은 프로세스 종료까지 남는다 —
`utils/deadline.ts` 헤더에 그대로 적어 두었다. **한계 있는 누수를 무한 정지와 맞바꾼
것**이고, 그 교환은 의도된 것이다.

## 진단 방법 (다음에 또 멈추면)

1. `pgrep -af nobsi` 로 PID 확인. `/proc/<pid>/status`(State/Threads/VmRSS),
   `cut -d' ' -f14,15 /proc/<pid>/stat`(CPU tick 2회 샘플), `ls -l /proc/<pid>/fd`.
2. `kill -USR1 <pid>` → 인스펙터가 127.0.0.1:9229 에 열린다.
3. CDP 로 붙어 **`process.getActiveResourcesInfo()`** 를 읽는다. `_getActiveHandles()`
   만 보면 타이머를 놓친다.
4. 타이머 정체가 필요하면 `Runtime.queryObjects` 에 `Timeout.prototype` 을 넘겨
   살아 있는 인스턴스를 전부 떠서 `_idleTimeout`/`_onTimeout.toString()` 을 읽는다.
   `_destroyed`·`hasRef()` 로 거른다 — GC 안 된 잔해와 `AbortSignal.timeout`(unref)이
   섞여 있다.
