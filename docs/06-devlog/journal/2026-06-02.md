## 1. Phase 1 범위 — relation 충실도 5결함(M1~M5)과 cover-URL

Notion→Obsidian pull 후 frontmatter/본문의 링크가 실제 파일을 못 가리키거나
UUID 그대로 남는 결함군. 이번 Phase는 **M2·M3·M4 + cover-URL + relation 후처리**를 봉합.

### M4 — 단일 패스와 후처리 패스의 위키링크 텍스트 불일치 ⭐

- **증상**: 같은 페이지가 변환 단일 패스(`resolvePageId`)에서는 StateDB 원시 제목
  (`.title`)으로, 후처리 패스(`resolveNotionLinks`)에서는 파일 basename 으로 해소돼
  서로 다른 `[[..]]` 텍스트가 생성. 원시 제목에 슬래시·콜론 등 파일명 금지문자가
  있으면 단일 패스 링크가 실제 파일을 못 가리키는 깨진/이중 위키링크가 됐다.
- **수정**: SSOT 유틸 `utils/wikilink-title.ts` 신설 —
  `wikilinkTitleFromPath(obsidianPath)` 가 `.md` 제거 + basename 추출을 단일 규칙으로
  강제. `orchestrator`·`database-syncer` 의 `resolvePageId` 람다와
  `resolveNotionLinks` 의 `idToTitle` 빌드가 **모두 이 함수를 통과**.

### M3 — 후처리 대상 경로를 슬라이스로 추정 → 실측 ⭐

- **증상**: pull 후 링크 후처리 대상(`writtenPaths`)을 "synced 상태 db-row 중
  마지막 N개" 슬라이스로 추정. 정렬·기존행 혼입 탓에 엉뚱한 파일을 후처리하거나
  갓 쓴 행을 놓쳐 링크가 미해소로 남았다.
- **수정**: `DatabaseSyncResult` 에 `writtenPaths: string[]` 추가. `pullDatabase`
  루프가 실제 기록된 행 경로(`pullDatabasePage` 의 `{action:"written", path}`)를
  수집해 반환. orchestrator 의 두 수집 지점(설정 DB `pullAll`, 디스커버리
  `pullDiscoveredDatabases`)이 슬라이스 대신 `dbResult.writtenPaths` 를 그대로 사용.

### M2 — 디스커버리 전용 조기 반환이 링크 후처리를 건너뜀 ⭐

- **증상**: 본문 페이지 변경 0 + 설정 DB 0 인 핫패스(Test 볼트)에서, 디스커버리된
  DB 행을 기록(`writtenPaths` 채움)하고도 `resolveNotionLinks` 없이 조기 반환 →
  그 행들의 본문 링크·frontmatter relation 이 UUID 그대로 잔존.
- **수정**: pull()의 모든 종료 경로를 단일 `finalize(created, updated, deleted)`
  헬퍼로 모음 — `resolveNotionLinks(writtenPaths)` + 메타 3종 마킹 + `PullResult`
  조립을 한 곳에서. 디스커버리 조기 반환과 메인 반환이 모두 이 헬퍼를 경유.
  (부수효과: 조기 반환의 imageCount/fileCount 하드코딩 0 도 실측값으로 교정)

### cover-URL — 원격 URL 을 위키링크로 잘못 래핑

- **증상**: DB 행 cover 처리에서 이미지 다운로드가 비활성/실패해 원격 `https://` URL이
  그대로 돌아올 때도 `[[https://..]]` 로 감싸 존재하지 않는 파일을 가리키는 깨진 링크.
- **수정**: 다운로드가 **로컬 첨부 경로로 치환했을 때만** `[[..]]` 로 감싸도록 가드
  추가(`!/^https?:\/\//i.test(resolved)`). 원격 URL 이면 평문 URL 로 보존.

### relation 후처리 (이전 세션 산출물, 본 커밋에 동봉)

- `sync/frontmatter-link-resolver.ts` — frontmatter 의 relation/people 원시 UUID를
  `[[제목]]` 으로 해소하는 순수 헬퍼(gray-matter 캐시 회피 위해 fresh 객체 생성).
  `resolveNotionLinks` 후처리에 배선됨. 변환 시점엔 대상 페이지가 미등록이라 UUID로
  남지만, 이 post-pass 시점엔 id→title 맵이 완성돼 해소.

## 7. Phase 2 — P0 relation 잔여 봉합 (M1 페이지모드 resolver + M5 대괄호)

> 분기 `fix/p0-relation-residual`. Phase 1 의 잔여 P0(relation churn) 봉합 + 방어적 대괄호 봉합.

### M1 — 페이지 모드 pull 의 relation/people 이 매 pull 마다 raw UUID 로 재생성 ⭐

- **증상**: 페이지 모드(비 DB) pull 에서 relation/people 속성이 `[[제목]]` 이 아니라
  raw Notion UUID 로 프론트매터에 기록 → 후처리(`resolveNotionLinks`)가 매번 다시
  `[[제목]]` 으로 고쳐 쓰는 **2-write churn**. 즉 멱등이 깨진다.
- **원인**: 페이지 모드는 `notionClient.extractProperties()` → `client.propertyMapper`
  를 쓰는데, 이 mapper 에는 `WikilinkResolver` 가 **한 번도 주입된 적이 없다**. DB 모드는
  `orchestrator.propertyMapper`(resolver 주입됨)·DatabaseSyncer(자체 주입 mapper)를 써서
  이미 면역이었다 — 그래서 그동안 페이지 모드에서만 잔존.
- **해결(Design B, SSOT)**: orchestrator 생성자에서 **단일** resolver 객체를 만들어
  `this.propertyMapper` 와 `this.notionClient` 양쪽에 주입. client 에는 위임 메서드
  `setWikilinkResolver()` 추가(중복 헬퍼 없이 mapper 로 위임). resolver 의 `resolvePageId`
  는 raw 제목이 아니라 `wikilinkTitleFromPath(obsidianPath)` 로 해소해 M4 SSOT(파일명
  basename = 위키링크 텍스트)와 정합 유지.

### M5 — 제목 대괄호가 `[[..]]` 위키링크를 조기 종료 (방어적 봉합)

- **증상**: 제목에 `[`/`]` 가 있으면(예 "Attention [2017]") 생성 위키링크가
  `[[Attention [2017]]]` 이 되고, Obsidian 파서가 **첫 `]]`** 에서 끊어 링크 대상을
  "Attention [2017" 로 오인 → 깨진 링크. 빈도는 낮지만 객관적 문법 충돌.
- **원인**: `sanitizeFileName` 의 `INVALID_CHARS` 에 대괄호가 없어 파일명·basename 에
  대괄호가 보존됨. basename 에서 파생되는 위키링크 텍스트에도 그대로 새어 들어감.
- **해결**: 파일명 SSOT 인 `sanitizeFileName` 한 곳에서 대괄호를 `_` 로 치환
  (`WIKILINK_UNSAFE_CHARS` 상수 분리 — 파일시스템 무효 문자와 위키링크 무효 문자는
  관심사가 다름). `(`/`)` 매핑은 기존 "(2017)" 파일과 충돌 위험이 있어 배제, `_` 는
  충돌·멱등 모두 안전. 원본 제목은 frontmatter `title` 에 보존되므로 **무손실**.
  별칭 구분자 `|` 는 이미 `INVALID_CHARS` 가 처리함을 확인.
