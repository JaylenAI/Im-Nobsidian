핵심 통찰: **I1 충실도 하네스(B2)는 markdown 마커 파이프라인만** 통과시키고
`PropertyMapper`(실제 Notion DB 속성 경로)와 `BlockConverter`(martian↔notion-to-md)는
거치지 않는다. 즉 relation/date-end 속성과 toggle/callout/table 등 실제 블록 왕복은
B2 까지 **deep-equal 미검증** 상태였다. B3 는 이 두 표면을 잠갔다.

### 발견 (수정 아님 — 정직한 분류)

- **속성 READ/WRITE 형식 비대칭.** `toNotionProperties` 는 write 페이로드
  (`{select:{name}}`, `type` 필드 없음)를, `fromNotionProperties` 는 read 응답
  (`{type:"select", select:{…}}`)을 다룬다. 두 형식이 달라 충실도 검증은
  READ→from→to→WRITE 방향이어야 한다(직접 체이닝 불가). — 프로브 1차 시도에서 확인.
- **relation 은 해석기 유무와 무관하게 왕복.** 해석기 있으면 `[[Title]]`↔pageId,
  없으면 raw uuid 로 보존(미인덱싱 페이지도 손실 없음).
- **people 은 표시 지향(읽기 중심).** READ 시 사용자 이름으로 풀리지만, push 는
  user UUID 만 허용(이름으로 user 생성 불가 — Notion API 제약). created_by/
  last_edited_by 와 동일 범주. 라운드트립 대상에서 제외(🔴 분류와 일치).
- **files 의 name 은 URL 로 직렬화.** Bases 카드 image 렌더 호환을 위한 기존 합의
  (B2 이전). url 자체는 보존되므로 라운드트립 안전.

유발해 **중복(redundant)** 으로 결론. `pending_operations` 만 활성화.

  `fileSize` 포함. `uploadAndAppendImages` 가 append 직후 `registerFile` 로 공유
  레지스트리에 등록 → FileHandler 가 `getFileRegistry` 로 같은 첨부를 standalone
  중복 업로드하지 않음.
- 외부 URL(`isExternal`)은 업로드/등록 대상 아님 → 업로드 파일과 구분 보존.

**정직한 한계 기록:** 기본 push 는 `replace_content`(replacePageMarkdown)라
노트 본문을 매번 wipe 후 재작성한다. `file_upload` 은 1회용이므로 노트 텍스트가
바뀌면 임베드 이미지는 재업로드+재append 된다(블록 더블링/손실 아님 — 구조적 특성).
따라서 "중복 업로드 0" 은 (1) 무변경 재sync 스킵, (2) standalone 폴더 중복 차단
두 축에서 보장한다.

### B4-3 — I12 크래시 복구 WAL + 재개 reconcile

**STATE-FIRST WAL 설계** (`orchestrator.pushCreate`):

1. 페이지 생성 **전** 자리표시 `sync_state`(notion_page_id=NULL) + `pending_operations`
   (operation=create, payload={path,parentId,title}) 를 먼저 기록.
   인-런 재시도 시 `getIncompleteOpByState` 로 기존 op 재사용(중복 기록 방지).
2. `pushCreatePage` → 매핑 upsert(pending) → 이미지 → 최종 synced 트랜잭션.
3. 전 과정 완료 후 `markPendingCompleted(walOpId)`.

**재개 reconcile** (`push()` 시작 시 `recoverInterruptedPushOps`):

- state.notionPageId 존재 → 생성·매핑 끝, 완료 처리(잔여는 변경감지가 pushUpdate).
- notionPageId=NULL(Window A) → 부모에서 **제목으로 child_page 검색**
  (`findChildPageByTitle`, 휴지통/보관 제외) → 고아 페이지 입양(매핑 채움) or
  미발견 시 자리표시 제거(FK CASCADE 로 op 삭제) → 다음 push 가 새로 생성.
- push 종료 시 `clearCompletedOperations` 로 완료/실패 WAL 정리(무한 증가 방지).

**정직한 잔여 한계:** Notion 은 idempotency key 가 없어 "생성 적용 직후 같은 호출
내 재시도" 중복은 완전 차단 불가. 429 는 적용 전 거절이라 안전, 프로세스 재시작 후
재개는 검색-입양으로 차단. DB 모드는 child_page 검색 불가 → 자리표시 제거 후 재생성 폴백.
