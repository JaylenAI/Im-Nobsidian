## 1. 파일 시스템 엣지 케이스

### 1-1. 파일명 특수문자

| 케이스       | Obsidian 파일명                   | Notion 페이지 제목 | 처리                                                                                           |
| ------------ | --------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------- |
| 한글         | `프로젝트 기획.md`                | `프로젝트 기획`    | 정상                                                                                           |
| 이모지       | `🚀 로켓 프로젝트.md`             | `🚀 로켓 프로젝트` | 정상                                                                                           |
| 슬래시       | `AC/DC 분석.md`                   | `AC/DC 분석`       | Obsidian에서 슬래시는 폴더 구분자 → 파일명에 불가. Notion에서 pull 시 슬래시를 하이픈으로 치환 |
| 특수기호     | `C++ vs C#.md`                    | `C++ vs C#`        | 정상 (파일명 허용 문자)                                                                        |
| 매우 긴 이름 | 260자+ 파일명                     | 정상               | Windows MAX_PATH 제한 → 200자 초과 시 해시 접미사로 잘라내기                                   |
| 중복 이름    | `Projects/API.md`, `Notes/API.md` | 다른 Notion 페이지 | 경로 기반으로 구분, State DB에 전체 경로 저장                                                  |
| 점(.) 시작   | `.hidden-note.md`                 | 동기화 제외        | dotfile은 기본 무시                                                                            |

### 1-2. 빈 파일 / 프론트매터만 있는 파일

```
Case A: 완전히 빈 파일 (0바이트)
  → Push: 빈 Notion 페이지 생성 (제목만)
  → Pull: 프론트매터 없는 빈 .md 파일 생성

Case B: 프론트매터만 있는 파일
  ---
  tags: [draft]
  ---
  → Push: Properties만 있는 Notion 페이지 (본문 없음)
  → 정상 처리

Case C: 프론트매터 없는 파일
  # 그냥 마크다운
  내용 내용
  → Push: Properties 없는 Notion 페이지 (본문만)
  → 정상 처리
```

### 1-3. 심볼릭 링크

```
~/MyVault/
  Shared/ → /Users/shared/team-docs/ (symlink)
  Notes/ (일반 폴더)

처리:
  → symlink 감지 시 경고 로그 출력
  → 기본 동작: symlink 대상 파일을 일반 파일처럼 읽기 (resolve)
  → 설정으로 symlink 무시 가능
  → 주의: symlink 순환 참조 감지 필수 (A→B→A 무한루프 방지)
```

### 1-4. 동시 접근

```
Case: 동기화 중에 사용자가 파일 편집

처리:
  → Pull 중 파일 쓰기 전에 로컬 해시 재확인
  → 로컬이 Pull 시작 후 변경됐으면 → 쓰기 스킵 + 다음 sync에서 처리
  → Push 중 파일 읽은 후 전송 전에 해시 재확인
  → 전송 전에 또 변경됐으면 → 최신 버전으로 다시 읽기
```

## 2. 마크다운 엣지 케이스

### 2-1. 잘못된 YAML 프론트매터

```markdown
---
tags: [unclosed
status: active
this is broken
---

# 본문
```

```
처리:
  → YAML 파싱 실패 시 프론트매터 전체를 문자열로 취급
  → 본문만 Notion으로 변환
  → Properties는 빈 상태
  → 경고 로그: "YAML 파싱 실패: 프론트매터를 건너뜁니다"
  → 라운드트립: Pull 시 원본 프론트매터 문자열을 그대로 보존
    (preserve marker: obsinotion:preserve:broken-frontmatter)
```

### 2-2. 매우 큰 파일

```
Case: 10,000줄 마크다운 (약 3,000+ Notion 블록)

처리:
  → 100블록씩 청킹 → 30번 API 호출
  → 3 req/s 기준 약 10초 소요
  → 진행률 표시: [10/30] 블록 전송 중...
  → 중간에 실패 시: 이미 전송된 블록은 유지, 나머지만 재시도

Case: 20,000+ 블록 (Notion 페이지 한도 근접)
  → 경고: "파일이 너무 큽니다. Notion 페이지 한도에 근접합니다"
  → 그래도 전송 시도 (Notion API가 거부하면 에러 표시)
```

### 2-3. 깊은 중첩

```markdown
- 레벨 1
  - 레벨 2
    - 레벨 3
      - 레벨 4
        - 레벨 5
          - 레벨 6
            - 레벨 7
              - 레벨 8 ← Notion은 중첩 깊이 제한 없음 (API 기준)
```

```
처리:
  → Notion API는 중첩 제한 명시 없음 (children 재귀)
  → 그러나 3단계 이상은 한 번에 append 불가 → 단계별 생성
    1차: 루트 블록 + 1단계 자식
    2차: 각 1단계의 2단계 자식
    3차: 각 2단계의 3단계 자식...
  → 깊이 10 이상이면 성능 경고
```

### 2-4. 코드 블록 안의 마크다운

````markdown
```markdown
# 이건 코드 블록 안의 제목이지 실제 제목이 아님

**볼드도 아님**

- 리스트도 아님
```
````

````
처리:
  → 코드 블록 경계를 정확히 파싱 (``` 카운팅)
  → 코드 블록 내부는 plain text로 취급
  → Notion code block의 rich_text로 전송 (서식 없이)
  → 라운드트립: 완벽 보존
````

### 2-5. HTML 혼합 마크다운

```markdown
일반 마크다운 **볼드**

<div class="custom">
  <p>HTML 콘텐츠</p>
  <table>
    <tr><td>셀</td></tr>
  </table>
</div>

다시 마크다운 _이탤릭_
```

```
처리:
  → HTML 블록은 Notion에 직접 표현 불가
  → 전략: HTML 블록을 코드 블록(html 언어)으로 보존
    + preserve marker: obsinotion:preserve:html-block
  → 라운드트립: Pull 시 HTML 블록 원본 복원
```

## 3. Notion 엣지 케이스

### 3-1. 삭제된 페이지 참조

```
Case: Notion에서 페이지 A가 페이지 B를 멘션하는데, B가 삭제됨

처리:
  → Pull 시 mention의 page_id로 페이지 조회 → 404 반환
  → 매핑 테이블에서 해당 ID 확인
    → 매핑 있음: [[삭제된 페이지명]] + 경고 표시
    → 매핑 없음: [삭제된 페이지](broken-link) + 경고 로그
```

### 3-2. 권한 없는 페이지

```
Case: Integration에 공유되지 않은 페이지

처리:
  → API 응답: 403 Forbidden
  → 해당 페이지는 건너뛰기
  → 경고 로그: "접근 권한 없음: '비밀 프로젝트'.
    Notion에서 해당 페이지에 Integration을 연결해주세요."
  → 해당 페이지를 참조하는 mention은 텍스트 링크로 대체
```

### 3-3. Notion 서버 다운 / 점검

```
Case: API 응답 500, 502, 503

처리:
  → 지수 백오프 재시도 (1s → 2s → 4s → 8s → 16s)
  → 최대 5회 재시도
  → 5회 모두 실패 시:
    → 에러 메시지: "Notion 서버에 연결할 수 없습니다. 나중에 다시 시도해주세요."
    → 부분 동기화 결과 저장 (이미 성공한 파일은 유지)
    → 실패한 파일 목록을 State DB에 기록 → 다음 sync 시 우선 재시도
```

### 3-4. Rate Limit (429)

```
Case: 대량 동기화 시 초당 3회 초과

처리:
  → async-sema 세마포어로 사전 방지 (3 concurrent)
  → 그래도 429 발생 시:
    → Retry-After 헤더 확인 → 해당 시간만큼 대기
    → 헤더 없으면: 1초 대기 후 재시도
    → 진행률에 "속도 제한 대기 중..." 표시
```

### 3-5. 월간 API 한도 (Free 플랜)

```
Case: Free 플랜 월 10,000 요청 초과

처리:
  → 동기화 시작 전 예상 API 호출 수 계산
    → 파일 당 평균: 1 (properties) + ceil(블록수/100) (content)
  → 남은 쿼터와 비교
  → 초과 예상 시 경고:
    "예상 API 호출: 450건 / 남은 쿼터: 320건
     일부 파일만 동기화됩니다. 우선순위:
     1. 최근 수정된 파일
     2. 크기가 작은 파일"
  → 설정에서 쿼터 관리 대시보드 제공
```

## 4. 동기화 엣지 케이스

### 4-1. 파일 이동 / 이름 변경

```
Case A: 로컬에서 파일 이름 변경
  API-문서.md → API-가이드.md

처리:
  → chokidar가 'rename' 이벤트 감지 (delete + create)
  → State DB에서 이전 경로로 notion_id 조회
  → Notion 페이지 제목 업데이트 (PATCH /v1/pages/{id})
  → State DB 경로 업데이트
  → 새 파일로 push하지 않음 (중복 방지)

Case B: 로컬에서 폴더 이동
  Notes/API-문서.md → Projects/API-문서.md

처리:
  → Notion에서 페이지의 parent 변경 (PATCH /v1/pages/{id})
  → State DB 경로 업데이트
```

### 4-2. 동기화 중 네트워크 끊김

```
Case: Push 중 50/100 파일 전송 완료 후 네트워크 끊김

처리:
  → 이미 전송된 50개: State DB에 성공 기록
  → 실패한 50개: State DB에 "pending" 상태로 기록
  → 에러 메시지: "네트워크 오류로 50개 파일 동기화 실패"
  → 다음 sync 시: pending 파일만 우선 처리
  → 부분 전송된 페이지 (블록 일부만 전송):
    → 해당 페이지를 통째로 다시 전송 (idempotent)
```

### 4-3. State DB 손상

```
Case: sync.db 파일이 손상되거나 삭제됨

처리:
  → 시작 시 DB 무결성 검사 (PRAGMA integrity_check)
  → 손상 시:
    → 백업에서 복원 시도 (.obsinotion/sync.db.bak)
    → 백업도 없으면: DB 재생성
    → 경고: "동기화 상태가 초기화되었습니다.
      다음 sync는 전체 비교를 수행합니다 (시간이 걸릴 수 있음)"
  → 전체 비교: 로컬 파일 해시 vs Notion last_edited_time
    → 양쪽 비교 후 State DB 재구축
```

### 4-4. 타임존 차이

```
Case: 사용자가 여행 중 타임존 변경

처리:
  → 모든 시간을 UTC ISO 8601로 저장/비교
  → Notion API도 UTC 반환
  → 로컬 파일 mtime도 UTC로 변환 후 비교
  → 프론트매터의 date 필드: 사용자 입력 그대로 보존 (타임존 변환 안 함)
```

### 4-5. 여러 기기에서 동시 동기화

```
Case: 데스크톱 + 노트북에서 동시에 같은 Vault를 동기화

처리:
  → State DB는 로컬 파일이므로 기기별로 독립
  → 같은 Notion 페이지를 두 기기에서 동시에 push하면:
    → 나중에 push한 쪽이 이전 push를 덮어씀
    → Notion의 last_edited_time으로 감지 가능
  → 권장: 한 번에 한 기기에서만 동기화
  → 향후: lock 메커니즘 (Notion 페이지에 lock 속성 추가)
```

### 4-6. Notion에서 페이지를 다른 워크스페이스로 이동

```
Case: 동기화 중인 페이지가 Integration 범위 밖으로 이동됨

처리:
  → 다음 Pull 시 해당 page_id 조회 → 404
  → State DB에 "orphaned" 상태로 마킹
  → 경고: "Notion에서 '프로젝트A'를 찾을 수 없습니다.
    [1] 로컬 파일 유지 (동기화 해제)
    [2] 로컬 파일 삭제
    [3] 무시 (다음에 다시 확인)"
```

## 5. 변환 엣지 케이스

### 5-1. Notion rich_text 2000자 초과

```
Case: 한 paragraph 블록의 rich_text가 2000자 초과

Pull 처리:
  → Notion API가 자동으로 2000자씩 분할된 rich_text 배열 반환
  → 연결하여 하나의 마크다운 단락으로 합침

Push 처리:
  → 2000자 초과 단락 감지
  → 단어 경계에서 분할 (한국어: 문장 단위)
  → 여러 rich_text 객체로 전송
```

### 5-2. 위키링크 대상이 아직 동기화되지 않은 경우

```
Case: [[미래의 노트]]를 참조하지만 해당 노트는 아직 push 안 됨

처리:
  → 매핑 테이블에 없음
  → 일반 텍스트로 전송: "미래의 노트"
  → State DB에 "unresolved_link" 기록
  → 해당 노트가 push되면:
    → 매핑 테이블 업데이트
    → 참조하던 페이지들의 해당 부분을 page mention으로 업데이트
    (lazy resolution)
```

### 5-3. 순환 참조 위키링크

```
Case: A → B → C → A 순환 참조

처리:
  → 변환 자체에는 문제 없음 (각각 독립 페이지)
  → Push 순서: 의존성 그래프 구성 → 순환 감지 → 순환 고리 하나를 끊고 순차 push
  → 첫 라운드: A, B, C 페이지 생성 (위키링크는 텍스트로)
  → 두 번째 라운드: 매핑 테이블 완성 후 → 모든 위키링크를 mention으로 업데이트
```

### 5-4. 프론트매터 속성 타입 변경

```
Case: 같은 속성이 파일마다 다른 타입

파일 A: priority: 1           (number)
파일 B: priority: "높음"      (string)
파일 C: priority: true        (boolean)

처리:
  → 최초 push 시 첫 번째 파일 기준으로 Notion property 타입 결정
  → 타입 불일치 파일: 강제 변환 시도 (string으로 통일)
  → 경고 로그: "priority 속성의 타입이 일관되지 않습니다"
  → _schema.yml에 기대 타입 기록 → 이후 검증 기준
```

### 5-5. Notion에서 블록 순서 변경

```
Case: Notion에서 드래그로 블록 순서 변경

처리:
  → Notion API에서 blocks 조회 시 현재 순서대로 반환
  → Pull 시 마크다운을 새 순서로 재생성
  → Three-Way Merge에서 "이동"으로 감지
  → 로컬에서도 같은 부분 편집 안 했으면: 자동 반영
```

## 6. 보안 엣지 케이스

### 6-1. 토큰 노출

```
Case: .obsinotion/config.json이 git에 커밋됨

예방:
  → init 시 .gitignore에 .obsinotion/ 자동 추가
  → 이미 gitignore가 있으면 항목 append
  → 경고 배너: "config.json에 API 토큰이 있습니다.
    절대 git에 커밋하지 마세요."

감지:
  → push 전에 staged files 확인
  → .obsinotion/ 포함 시 abort + 경고
```

### 6-2. Notion 토큰 만료 / 폐기

```
Case: Integration이 비활성화되거나 토큰이 변경됨

처리:
  → API 응답 401 Unauthorized
  → 즉시 동기화 중단
  → 에러: "Notion 토큰이 유효하지 않습니다.
    설정에서 새 토큰을 입력해주세요."
  → 자동 재시도 안 함 (토큰 문제는 사용자가 해결해야 함)
```

## 7. 엣지 케이스 우선순위

| 우선순위 | 엣지 케이스        | 이유                  |
| -------- | ------------------ | --------------------- |
| 🔴 필수  | Rate limit 처리    | 모든 사용자가 겪음    |
| 🔴 필수  | 네트워크 오류 복구 | 안정성의 핵심         |
| 🔴 필수  | 충돌 감지/해결     | 데이터 손실 방지      |
